# Coordinator playbook — how `spec.coordinator` decides

This document IS the coordinator's COMMON brain — the procedure and the invariants that hold on every asset, whatever it is made of. What a particular kind of asset actually DOES — which documents define it, which steps run in which order, what closes each gate, which launch checkboxes exist — is not here: it lives in the asset's own type playbook and in the playbook of each tool the asset uses (Chapter 2). Every scenario the spec system needs to handle across assets — a change touching a feature, a report awaiting acceptance, a request needing a home, a bug an expert spotted — is decided by reading this playbook plus those, and acting through a small closed set of primitive verbs, never by bespoke script logic. A new scenario is a new chapter (or an edit to an existing one) in whichever of the three owns it, not a code change. `lazy-spec.drive` (the no-daemon session orchestrator) reads and follows the same set when driving an asset by hand.

## 1. Role, invariants, verbs, boundaries

**What the coordinator is.** One persona (`spec.coordinator`, agent + expert record in `lazycortex-specs`, sonnet-tier). Any state transition on any spec asset dispatches its job: read what changed, update `# Status brief` in plain product-language prose, check related assets, and act — but ONLY through the closed verb set below. Inter-asset interaction of every kind (change cascades, request routing, asset creation, acceptance cycles, decision escalation) goes through the coordinator; there is no bespoke script for any of it.

**Topology.** The daemon that dispatches the coordinator runs in its own checkout, named by `daemon.run_here` — not the checkout the operator edits in (a separate Obsidian vault clone, a separate working copy). Every gesture named in the trigger list below reaches the coordinator only as a commit the operator has already pushed and this checkout's daemon has already pulled in on a prior iteration; there is no dirty-tree signal to read here, because an uncommitted edit sitting in the operator's own checkout is invisible to this one. The coordinator's own answers travel the same path in reverse — a commit under its own bot identity, pushed by the daemon, pulled by the operator (or their vault's own sync) before it is visible to them.

**Triggers — the closed set of things that wake the coordinator:**

1. A commit by a non-`@bot.` author that has reached this checkout and touches the asset's folder outside an active review: the status note itself, or — on a grouped tick naming several changed members at once — a sibling doc that does NOT carry `review_active: true` (operator decision 2026-08-15: a sibling under active review is the review loop's own business, not a wake signal, until its review ends — the moment trigger 6 already covers). A commit that deletes a sibling doc counts too: the `lazy-spec.coordinator-deletes` routine wakes the asset's status note as an operator edit. When the whole asset folder was deleted, it wakes the owning product's level note instead. See § Self-suppression below for why a coordinator-authored (or any other bot-authored) commit never re-triggers itself.
2. *(No longer this coordinator's.)* Request routing reaching the terminal review group is `spec.catalog-coordinator`'s wake, on the catalog root's level note — see Chapter 9. The number is kept so the other six keep their names.
3. A non-empty `# Coordinator commands` section on an asset folder-note.
4. A ticked answer to one of the coordinator's own `[!question]` callouts.
5. A launch-checkbox job's terminal marker landing — `lazy-spec.gate-tick` clears the asset's `active_job` marker and raises `pending_wake: job-done` in the runtime sidecar in its place, and that raised flag is the whole wake: the `lazy-spec.collect` postman dispatches the coordinator on it directly, with no commit behind it, and the watch worker honours the same flag on any git item it handles first. It wakes the coordinator regardless of who authored any commit around it; the bot-suppression rule exists to ignore the coordinator's own idle re-triggers, not to hide a real state transition (see the `job-done` trigger token, `spec_keys.CoordinatorTrigger`). A wake that a higher-priority trigger preempts keeps its flag and fires on a later tick rather than being swallowed.
6. A sibling authored doc's `review_result` appearing or changing against the value this system last recorded for it — a review approval (or re-approval) landing on a defining document, a plan, or a report of this asset. The system documents of a product root and of the catalog root are NOT in this trigger's scope — they belong to `spec.catalog-coordinator`, which wakes on the same routine and follows `${CLAUDE_PLUGIN_ROOT}/references/lazy-spec.catalog-playbook.md`; a wake on one of those reaches the level note, never an asset. Wakes REGARDLESS of the sibling commit's own author, the same per-transition exemption as trigger 5: a commit that never touches `review_result` (an operator's prose edit, a writer's draft) simply carries no transition, so no separate author check is needed to exclude it. That same prose edit only reaches THIS coordinator via trigger 1 once the touched sibling is no longer `review_active: true` — while the review is active, neither trigger fires on it, and trigger 6 is the moment the wake resumes (see the `doc-transition` trigger token, `spec_keys.CoordinatorTrigger`).
7. `lazy-spec.drive` invoking it directly in the no-daemon session mode.

A no-op tick (nothing changed that the coordinator cares about) and automation on a halted asset do NOT wake it — halt silences automation, not the trigger check, but a halted asset's own automation stays dormant per § Halt below.

**Self-suppression.** The commit-author check that gates trigger 1 compares the folder-note's changed-file author against the `@bot.` substring — the same convention every existing bot identity in this plugin already uses (`lazy-spec.flip-gate@bot.invalid`, `lazy-spec.gate-tick@bot.invalid`, and the coordinator's own `spec.coordinator@bot.invalid`). An author whose email contains `@bot.` never re-triggers the coordinator on its own write — otherwise every coordinator-authored edit would wake a fresh coordinator job on itself.

**Where the two job markers live.** Neither is frontmatter. The asset's launch-checkbox job (`active_job`) and the coordinator's own job (`coordinator_job`), plus the `pending_wake` flag trigger 5 reads, live in a gitignored runtime sidecar at `<repo>/.runtime/lazy-specs.jobs.json`, keyed by the note's repo-relative path and written through the `mark-job` verb. Two consequences: an operator hand-editing a folder-note cannot break the mutex or lose a live job's record, because the markers are not in the note at all; and neither setting nor clearing one costs a commit, so only content — payload, `# History` lines, gates — still lands in git. Read them back with `note-check`, whose result carries the note's `job_markers` entry.

**One active job per asset.** Exactly as the launch-checkbox ladder enforces one active expert job per asset (the `active_job` marker), the coordinator itself runs at most one job per asset at a time. A second trigger while a coordinator job is already active on that asset waits for it to finish rather than dispatching a concurrent one.

**Hard invariants — unchanged by the coordinator's arrival:**

- The in-asset ladder (gates, checkboxes, dispatch, polling, halt) stays governed by the primitive verbs; the coordinator drives it through them, it never bypasses them.
- One active expert job per asset (the `active_job` marker) — the coordinator never queues a second job while one is outstanding.
- Halt (`spec_halted: true`) stops every automation layer built on top of the gates — checkbox dispatch, cascade dispatch, coordinator-driven automation — but never the five gate booleans themselves, and it never stops `# Coordinator commands` (an operator gesture always runs, halted or not — see Chapter 7).
- Gates do not gate themselves. `flip-gate` flips whichever gate it is called on, unconditionally; its one refusal is a cancelled asset (`spec_cancelled: true`), which accepts only the un-cancel `spec_cancelled --off` — no precondition table survives inside the primitive (see `lazy-spec.lifecycle-protocol.md` → "The single mutation channel"). The ORDER of the ladder is therefore the coordinator's own responsibility, held by its reading of the type and tool playbooks and enforced by nothing else: an out-of-order forward flip lands silently, with its `spec_<gate>_at` stamp and no complaint — nothing journals it.
- The "one active feature — one active change" lock is explicitly NOT an invariant. A new change may cancel or modify an older one in flight; deciding which is the coordinator's call (the `change` type playbook's conflicting-changes rule).

**The closed verb set.** The coordinator acts ONLY through these primitives, every call auditable through its own commit: `flip-gate` (including `--off` / `--halt`), `dispatch-job`, `cancel-job`, `submit` / `stop` (lazy-review), `note-history` (the one door into `# History` — the coordinator supplies the text, the verb picks the day group and the bullet; no persona and no code composes a history line by hand), plus the note-owning verbs that write frontmatter/sections under validation (`set-stage`, `promote-approved`, `note-set-key`, `note-check`), the pen's own commit (`commit-note`), and the three coherence verbs (`coherence-dispatch`, `coherence-resolve`, `coherence-dismiss` — Chapter 19). It never hand-edits a folder-note's YAML or body with a text editor — every mutation is a verb call, so the mutation is validated, logged, and auditable exactly like every other primitive in this system.

**What the coordinator's own pen writes.** Five surfaces, and nothing else:

- `# Summary` — the one-line description of what this asset is, inside its `<!-- spec:precis:* -->` markers (Chapter 11).
- `# Status brief` — its own prose, rewritten (not appended) on every invocation.
- `[!question]` callouts with `- [ ]` options, when it needs an operator decision.
- Locking `# Coordinator commands` blocks — writing progress marks into a mini-plan and clearing the finished block, one `note-history` line saying what the command did (Chapter 7).
- `# Attachments` — the registry of the asset's non-markdown attachments, one line per file naming the file and the document that owns it, tagged `#protected/spec/attachments` (Chapter 11's attachment registry).

None of these five land through a primitive verb, so none of them commit themselves — the coordinator lands them with one `commit-note` call before the job ends, and the verb owns the pathspec, the identity check and the `clean` / `dirty` report, its refusals arriving in `reason`. It matters here because a dirty tree at exit trips the runtime's `uncommitted_changes` halt (`lazy-core.expert-runtime-contract.md`) and strands the whole daemon tick, not just this asset.

**Icon repaint rides inside every hand commit.** The hand commit is one `commit-note --repaint` call, and `commit-note` does the repaint itself, folding it into the same commit.

**What the coordinator never touches, ever:**

- Launch checkboxes — it never ticks one. Ticking is exclusively an operator gesture (or, in `lazy-spec.drive`'s no-daemon mode, the operator's spoken word translated into a tick by the orchestrator on the operator's behalf — still their decision, never the coordinator's).
- A frontmatter field or body section it does not own per the layout protocol's canonical-writer table — same discipline every other spec-system component already follows.
- Another asset's or another expert's document body, outside the verbs listed above (a cascade fold, a proposal materialization, and a few other named exceptions are still verb calls, never freehand edits).

**Automation "by rule" is still verb calls, not new state.** When local rules say "run tests automatically" or similar, the coordinator satisfies that by calling `dispatch-job` directly — it does not tick a checkbox on the operator's behalf (ticking stays exclusive to the operator). A launch checkbox left hanging by a rule-driven dispatch is reconciled away by the ordinary reconciliation pass exactly like any other stale checkbox (an active-job guard removes it; nothing journals the removal). A race between an operator's tick and a rule-driven dispatch of the same unit of work is safe because dispatch is deduplicated by key (one dedup key → one job, regardless of which caller fired it first). No suppression flag is ever materialized in frontmatter for this (a `spec_auto`-style key was considered and rejected as unneeded — the checkbox flickering visible-then-gone for one tick is an acceptable cost, not a bug to engineer around).

### The architectural turn — the coordinator owns the folder note

The coordinator is not one more writer sharing the folder-note with `flip_gate` / `gate_tick` — it is the folder-note's owner in full:

- **The folder-note is the coordinator's channel**, and it brings the note to canonical form on every invocation — including recovering it from an accidental operator edit that broke its structure (a stray line dropped into `# Gates`, a checkbox mangled by hand). The note stays legible to every other consumer (the importer, iconize, the review scan, `lazy-spec.audit`) precisely because the coordinator, not the operator's raw edit, is what a downstream reader ultimately sees reflected back after the coordinator's own commit has been pushed by the daemon and pulled into whichever checkout that reader is looking at.
- **Frontmatter is a machine API.** It is written only by the validating verbs above; a script-level control (the tick worker, `lazy-spec.audit`) checks structure — the shape of the frontmatter and which sections exist — never content semantics. Content semantics (what a gate MEANS for a given asset type, whether a checkbox's precondition currently holds) is the playbooks' business, not the script's.
- **Gates are written and read by the coordinator through verbs.** What a gate means for a given asset is defined by that asset's type and tool playbooks (Chapter 2), not hardcoded per asset kind in script — a script-level "code profile" is explicitly not maintained going forward.
- **The runtime underneath stays scripted** — dispatch, polling, terminal markers, halt mechanics, review integration, import/push, dedup — these remain primitives the coordinator calls, exactly as documented in `lazy-spec.lifecycle-protocol.md`. Only the DECISION layer (which precondition to check, which checkbox to hang, when to cascade, when to escalate) moves into the playbooks.
- **A brand-new asset type costs zero lines of script.** Declaring the type with its playbook is the entire cost — see Chapter 10.

## 2. The input facts — asset type, tools, and their playbooks

**The first act of every wake is to read `spec_asset_type` and `spec_tools` from the status note's frontmatter.** An asset's folder is a PLACE, not a fact: it says where the operator filed the thing, and it takes no part in resolving what the thing is. Two assets in the same folder may carry different types, and a legally-typed asset may sit anywhere in the tree, including nested under another asset.

**The type playbook resolves from `asset_types.<name>.playbook`; each tool's playbook resolves from `tool_types.<name>.playbook`.** Both are ordinary reference keys, read through the ordinary resolver, so a consumer override — a file of the same name dropped in `.claude/references/` — works exactly as it works for every other reference this plugin ships. Declarations live under `products[<key>].asset_types` and `products[<key>].tool_types`, over the shipped defaults in `references/lazy-spec.asset-types.json` and `references/lazy-spec.tool-types.json`.

**A type carrying `alias_of` and no `playbook` of its own takes the base's playbook.** It borrows the playbook and NOTHING else: its folder, its icon, its start doc, and its default tools all stay its own (Chapter 10 § Aliases).

**`spec_asset_type: unknown` is a transitional state, not an error.** The ladder is not built on an unknown asset: no gate is evaluated, no launch checkbox hangs. The type is determined from the outcome of the FIRST document's review — what the approved document turns out to describe is what the asset is — and written with `note-set-key`. When the reading is genuinely undecidable, the coordinator raises a `[!question]` listing the declared types for the owning product and waits for the tick. A status note carrying no `spec_asset_type` key at all travels the same road: it is read as `unknown`, never guessed from the folder it sits in.

**An absent `spec_tools` key means "not determined".** The asset's own design-only flow — definition, review, whatever the type playbook declares — runs normally on it; only a release build that includes it stops on it, because the release implementer cannot tell which tools' work the asset needs. WHEN the tool set is determined, and from WHICH source, is named by the type playbook, not here; the coordinator writes the resulting list with `note-set-key`, and raises a `[!question]` with the candidate tools whenever the choice is not obvious from what the approved documents actually say. An EMPTY `spec_tools` list is a different fact — it is a determination, recorded: this asset needs no tool at all, and a release build that includes it goes on by that determination rather than stopping on it.

**A tool named in `spec_tools` with no declaration behind it is a finding, not a guess.** The coordinator never invents the missing tool's playbook, its report document, or its expert; it names the undeclared token in `# Status brief` and raises a `[!question]` for the operator to either declare the tool or correct the list.

**An asset's boundary is the folder whose folder-note carries `spec_role: status`.** Every scan the coordinator runs over an asset — sibling documents, proposals, reports — stops at a NESTED status note: what lies under it belongs to that asset, not this one.

**The files read at the top of the wake — this playbook, the type playbook, the playbooks of every tool in `spec_tools` — ARE the law of that wake.** Nothing else governs the decision; a rule that is in none of them is not a rule the coordinator applies.

## 3. Rule layers and priority order

The coordinator consults rules from six layers, closest-to-the-asset wins on any conflict:

1. **The playbook set** — this playbook (`lazy-spec.coordination-playbook.md`, plugin-shipped) PLUS the asset's type playbook PLUS the playbook of every tool in its `spec_tools`. Together they are the baseline behaviour for every scenario. Within the set, a conflict resolves by subject: on WORKFLOW — what step runs, in what order, what a gate closes on, which checkbox exists — the one closest to the asset wins (tool playbook > type playbook > this playbook); on PROCEDURE and INVARIANTS — the verb set, the pen surfaces, the trigger list, halt, dedup, the reconciliation discipline — this playbook wins, and a type or tool playbook that appears to override one of them is read as a mistake in that playbook, never as licence.
2. **The vault-wide operator doc** — one consumer-authored document, its path recorded under the `spec.coordination_rules` key in the `spec` settings section (`lazy-spec.config-protocol.md`). States what is allowed to run automatically across the whole vault (e.g. "tests may run without a tick") and any vault-wide override of playbook defaults. Injected into every coordinator job's context.
3. **Product guidelines, role `coordinator`** — `products[<key>].guidelines.coordinator` (plus the wildcard `"*"`), preceded by the catalog-wide `spec.guidelines` and the enclosing products' guidelines, the same mechanism that already feeds `planner` / `tester` / `developer` guideline files into launch-checkbox jobs (`lazy-spec.config-protocol.md` § `products[<key>].guidelines`), extended with a `coordinator` role key. Product-scoped context files for coordinator jobs on that product's assets.
4. **The product folder-notes' `# Coordinator rules` sections** — of every product enclosing the asset, outermost first, then the owning product's own; each is an operator-authored, persistent constraint set scoped to every asset under that product (e.g. "product A is fully automated, product B stays under full manual control" — the same coordinator, no config keys, decided purely by what each product's rules section says).
5. **Container folder-notes' `# Coordinator rules` sections** — operator-authored, persistent constraints scoped to every asset under that group folder. Every container note on the path from the product root down to the asset's own folder contributes a layer, read top-down so a deeper container overrides a shallower one; a container whose note has no such section — or no folder-note at all — contributes nothing, and that absence is never a warning.
6. **The asset folder-note's `# Coordinator rules` section** — operator-authored, persistent constraints scoped to this one asset. The coordinator reads it before every decision on that asset; scripts never touch it.

**Read contract.** Every coordinator job's context carries: the target asset's own folder-note (with its rules section), the folder-note(s) of every related asset the job concerns (`spec_targets`, source requests), the level notes of every product enclosing each of those assets, outermost first, then the owning product's own — each with its own `# Coordinator rules` section — every container folder-note between the target asset's product root and its own folder (the group-scoped rules layer, top-down), the sibling authored docs and reports the wake actually concerns (whenever the trigger or the ladder decision turns on their content), and, when the wake is a job finishing, that job's own `response.json` (resolved from the `job_markers` block `note-check` reports, under `.experts/.jobs/<expert>/<job_id>/response.json`). The coordinator makes no decision without having read the rules layers bearing on it.

**Where `# Coordinator commands` lives.** For this coordinator, only on asset folder-notes, never on container folder-notes — a command with no addressee asset is ambiguous and is refused. A level note (a product's or the catalog root's) carries its own `# Coordinator commands`, addressed to `spec.catalog-coordinator` (`lazy-spec.catalog-playbook.md`), never to this coordinator. `# Coordinator rules` (constraints, read-only to the coordinator) exists at the product, container, AND asset levels. See Chapter 7 for the command contract.

## 4. Gates as a mechanism

This chapter is the gate MACHINERY and nothing else — the booleans, their order, what a flip costs, how one goes back off. WHAT exactly closes a given gate on a given asset is the playbooks' business: the type playbook and the tool playbooks say it, and this chapter never repeats them.

**The six gates, in order:** `spec_design_done` → `spec_plan_done` → `spec_develop_done` → `spec_tests_passing` → `spec_built` → `spec_released`, plus the `spec_cancelled` overlay that freezes every gate in either direction while it is `true` (only the un-cancel `spec_cancelled --off` passes). Only a `release` note carries all six. Every other asset type is design-only: its note carries `spec_design_done`, `spec_released` and `spec_cancelled`, the four middle keys are absent from it (`flip-gate` refuses to turn one on there), and its `spec_released` is set by the release that ships it (`lazy-spec.release-playbook.md`), never by this coordinator — except on a `research` asset, where the approval of `research.md` closes it, and in a spec-only product, where the operator's word does (Chapter 17). Each gate's forward flip needs its predecessor true — a rule the coordinator holds, never the primitive: `flip-gate` checks no predecessor and lands an out-of-order flip silently (Chapter 1's invariant list). Turning a gate back OFF (`--off`) needs no precondition either way, and both directions are refused while the asset is cancelled, the un-cancel `spec_cancelled --off` alone excepted. Section keys and gate names are the ones the frontmatter actually carries; they never change with the decision layer, and no type invents a seventh — a design-only type simply does not carry the four middle keys.

**Who closes which gate.**

- `spec_design_done` is closed by the TYPE playbook — the definition of the asset belongs to the type, and the type playbook names the document and the stage its gate turns on. On a release note it is true from creation.
- `spec_plan_done`, `spec_develop_done` and `spec_tests_passing` exist on a release note only and are the release playbook's: the first step's `architecture.md` settled and `code-plan.md` absent, `approved` or `cancelled` for the plan gate, the accepted `code-report.md` and the merged build for the development gate, the accepted green `test-report.md` for the tests gate. Every release is tested by default; a product that waives testing with a line in its `# Coordinator rules` gets no tester job, and the release's `spec_tests_passing` closes together with `spec_develop_done`. The tool playbooks say what each tool's share of a build is; the release implementer delegates per `spec_tools`.
- `spec_built` exists on a release note only and closes by itself once `spec_tests_passing` is closed and the build is merged.
- `spec_released` — on a release and on every included asset — is set by that release's `Publish` tick, together with the asset's version tag. It is the readiness flag: `true` means published and ready for a downstream consumer, absent or `false` means not ready.

**Derived versus human-signal.** The design and plan gates are DERIVED — their precondition is fully computable from state the coordinator can read (sibling doc stages, the architecture's state), so the coordinator auto-flips them the instant it holds, no operator input needed. The development and tests gates of a release close on an accepted report — a review's verdict, not a document's existence. `spec_built` closes by itself on a release once the tests pass and the build is merged. `spec_released` — on a release and on every included asset — is the `Publish` tick's write through `release-publish`: the one operator gesture of the whole ladder is that tick.

**Stage promotion runs before any gate is evaluated.** On every wake, before touching a gate, the coordinator promotes every sibling authored document whose review just finalized approved (`review_result ∈ {approved, approved-with-concerns}`) from `spec_stage: draft` to `approved` with one `promote-approved <note>` call, never a hand edit. A document whose review finalized approved while it already stood at `approved` is a re-approval: its basename, taken from the `DOC_TRANSITION` payload, goes into the same call as `--transitioned <basename>`, which records this approval as the document's last (Chapter 19). Gate evaluation then reads the promoted state, not the stale one.

**A parked document is skipped by the walk, not by the wake.** A sibling at `spec_stage: deferred` is passed over by the promotion even when it carries an approved `review_result`, and it closes nothing: an asset gate whose precondition names that document stays open, because `deferred` is neither an approval nor an absence — the document exists and is simply not being worked on. A commit touching it DOES wake you, as an ordinary operator edit on the status note, so the gates, the `# Status brief` and the launch rows get put in order around it. What it never raises is a doc-transition off its own verdict; and you never edit the parked document itself.

**Downward reconciliation.** A gate already true goes stale when the thing that closed it stops holding — a governing document reappears un-accepted, or a release's build is reopened. The coordinator watches for that on every wake and flips the gate back off (`--off`, auto) the moment it fires; WHICH conditions count as a regression for a given gate is, again, the playbook that closed it. A downward flip commits atomically and the coordinator immediately re-runs its upward checks against the fresh state, so a dependent checkbox disappears the same cycle rather than lagging a tick.

**A re-approved start document of a released asset.** When the start document of a released asset of any type but `research` is re-approved — its `design.md`, or a bug's `bug.md` — so that the document's `spec_approved_at` — restamped on every re-approval, the stage staying `approved` — sits above the note's `spec_released_at`, turn that asset's `spec_released` off with `flip-gate --off --auto`: the asset re-enters the delta and waits for the next release with its new document, and the released version keeps the tag it shipped with.

**A re-approval lowers nothing else.** A re-approved document never moves the stage of another document and never turns off a gate another document closed: a `ui-design.md` or a `test-plan.md` stays `approved` when its asset's `design.md` is re-approved, a `design.md` stays `approved` when its asset's `vision.md` is, and an approved `research.md` stays `approved` when its research design is. Contradictions between documents are caught by the coherence check after approval (Chapter 19). Inside an open release a re-approval of an included asset's document reaches the build through `Rebuild` (`lazy-spec.release-playbook.md`), whose tick rolls back what the change touched.

**Halt.** `spec_halted: true` silences every automation layer built on the gates — checkbox dispatch, cascade dispatch, rule-driven dispatch — but never the five booleans themselves and never `# Coordinator commands`. A halted asset still reads its gates truthfully; it just stops acting on them.

## 5. Launch checkboxes as a mechanism

A launch checkbox is a checkbox row inside a `[!gate]` callout rendered into `# Gates` — text the coordinator writes and interprets, not a structure a script detects. WHICH checkboxes exist at all is the type and tool playbooks' business; there is no label table in this chapter and none belongs here.

**Callout shape — one callout per verb, the checkbox never shares a paragraph with prose.** A row is one `- [ ] <label>` line. The rows whose labels open with the same verb (the label's first word) share one `[!gate]` callout: the head line names the verb exactly as the labels write it, in every note language, the checkbox lines follow it directly, and the one footer line saying what a tick does sits behind a blank quoted line (`>`) of its own. No row carries a hint of its own. The blank line holds for every callout that carries a checkbox, `[!question]` options included (their attribution line is separated the same way, see "Operator communication" below). The reason is the rendering: a line that follows a checklist item without a blank line is that item's continuation, and Obsidian's task renderer shows an item's first line only, so the footer vanishes in reading view. The canonical callout:

```
> [!gate] Review
> - [ ] Review vision.md
> - [ ] Review design.md
>
> tick to open review: …
```

**Hanging and taking down a row by hand.** Hang a row either by adding its `> - [ ] <label>` line to its verb's callout or as a one-row `> [!gate] <label>` block of its own; write no hint beside it. Remove an enacted ticked row, or an un-ticked one whose precondition stopped holding, by deleting its checkbox line, and the callout with it when no row is left. A row's label is read off its checkbox line, never off the callout's head, and a note that still carries one block per row is read the same way.

**Reconciliation, every relevant invocation.** The coordinator hangs a fresh row the moment its precondition starts holding and no row exists yet; removes an un-ticked row the moment its precondition stops holding (including the asset going halted); and leaves a ticked row (`- [x]`) alone, because a tick is the operator's dispatch gesture and only the operator makes it. `spec_halted: true` overrides everything: no row hangs, and any already up come down, whatever the gates say.

**Ticking is an operator gesture, always.** The coordinator never ticks a box, on anyone's behalf, for any reason — a rule that says "run this automatically" is satisfied by calling `dispatch-job` directly (Chapter 1), never by forging the gesture.

**Dedup by key.** Dispatching a ticked box is a plain `dispatch-job` call, deduplicated by the key `<note-path>:<label>` — the status note's repo-relative path plus the checkbox's own label, the same shape `coordinator-dispatch` gives the coordinator's own job (`<note-path>:coordinator`). One key → one job, regardless of which caller fired it first, which is what makes an operator tick and a rule-driven dispatch of the same work safe to race.

**Where the implementation goes.** No `Start coding`, `Start data entry`, `Start documentation` or `Start testing` row hangs on any asset note: the implementation of every asset is a release's build, one job per build led by the product's release implementer (`resolve-product release-implementer`), who does its own tool's work and delegates every foreign tool in an included asset's `spec_tools` to that tool's expert (`lazy-spec.release-playbook.md`). The rows a release note hangs are `Write code-plan`, `Write test-plan`, `Rebuild` and `Publish`; the build jobs it dispatches by rule carry the labels `Revise architecture`, `Build` and `Test` for dedup. `Start research` is the research type's own writer-launch row (`lazy-spec.research-playbook.md`), not an implementation job. A level note's `Start release` is the one row that creates an asset.

**Resolving the job's expert.** Never a hardcoded per-label value. For an implementation-side checkbox the expert is resolved from the review class of the TOOL's declared `report_doc`; for a definition-side checkbox it is resolved from the review class of the result document's own type. The bundle's `protocols` come from the same place — the `review.protocols` section default plus that class entry's own `protocols` list, no reference ever named in prose.

**What the caller names, and what it never copies.** For a launch-checkbox dispatch there is no mechanical bundle assembly to hook, so the coordinator builds the bundle itself — and it builds a manifest, not a payload of text. The first thing it names is the destination: every job dispatched to write a catalog document carries `target_doc` in its `payload` — the repo-relative path of the document that job writes. The job returns only content, through its own `result/`, so the destination has to travel with the dispatch; the landing collector reads that key and refuses a job declaring none, leaving the document in the job's `result/` and the job undelivered. Name it on every document-writing dispatch, launch-checkbox and cascade fold alike (`lazy-spec.lifecycle-protocol.md` Part 3 § Dispatch). The bundle's `source` and `context` are lists of **repo-relative paths**: nothing is copied at dispatch, and the pump copies each named path into the job's own `source/` / `context/` when it claims the job, so the expert reads the tree as it stands at claim time rather than a snapshot of the tick that dispatched it. A path that no longer resolves at claim fails the job rather than starting it blind. Content that exists in no file at all — a rendered view, a computed digest — rides in `source_inline` / `context_inline` instead, each entry naming the file it becomes under the same bucket.

**Guidelines and decisions are named, never staged.** They ride in the `payload`, not in either bucket: `guidelines` carries the repo-relative paths of the product's effective `guidelines[<role>]` — the catalog-wide `spec.guidelines`, then the enclosing products', then its own — followed by the asset type's `asset_types[<type>].guidelines` and then `"*"`, and `decisions` carries the asset's own `decisions.md` followed by the owning product's — each omitted when the file does not exist, silently (never a warning, unlike a missing declared guideline path), since a registry is created lazily by its first recorded decision. The expert opens those files in the working tree; they are deliberately never copied, so a guideline edited between dispatch and claim is read as edited. This is the same fold-in the coordinator's own wake already gets mechanically (`gate_dispatch.collect_decisions_paths`).

**The review-launch row — the one label class no playbook declares.** Beside the dispatch labels a type or tool playbook declares, one `Review <file>.md` row hangs per markdown file of the asset whose `spec_doc_type` declares `review: true` and not `append_only: true`, and which does not carry `review_active: true` — in any stage except `cancelled`: `empty`, `draft`, `approved`, `rejected` and `deferred` alike. A `cancelled` document gets no row, because its work is abandoned. The condition is per-file and reads nothing but the document's own type declaration, its `review_active` flag and its `spec_stage`, which is why it belongs to this chapter's mechanism rather than to any playbook's vocabulary — and why canonical documents and attachments are gathered by exactly the same rule, with ownership playing no part in it. The row is permanent while the condition holds: it is the operator's own way into review, so no stage, gate or edit takes it down — only a review in progress does (or a halt, below), and it returns when the review ends. The append-only report journals (a release's `code-report.md` and `test-report.md`) never get one, because a report enters review only when the job writing it finishes (Chapter 6), never by a tick. A level note hangs the same rows for the level's own documents by the same rule (`lazy-spec.catalog-playbook.md` § 3).

**The verb writes the review rows; the coordinator does not.** `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> review-rows <note>` computes which documents the note owes a row and rewrites exactly those rows in `# Gates`: it hangs a missing row into the `Review` callout, takes down an un-ticked row whose document no longer qualifies by deleting its checkbox line, never removes a ticked row, writes the note only when a row moved or the layout changed, and commits nothing — the wake's own commit carries the change. Its JSON summary lists the documents `added`, `removed` and `kept` and says whether the note `changed`. Run it on every wake before reconciling the declared labels, and again right after enacting any tick. Apart from taking down the ticked row it has just enacted, the coordinator hangs and removes no `Review` row by hand. `<specs-cli>` is the specs plugin's `bin/lazycortex-specs` file, resolved and run as `lazy-spec.lifecycle-protocol.md` Part 2 describes.

**The verb also owns the section's layout.** It lays every launch row of `# Gates` — the `Review` rows and the `Write` / `Start` / `Rebuild` / `Revise` / `Publish` rows you hang yourself — out under `##` sub-headings in the note's language: `## Next step` (`## Следующий шаг`) for every row that moves the asset forward, `## Re-review` (`## Повторное ревью`) for a `Review` row of an already approved document, where a tick re-opens settled work, and last `## Conflicts` (`## Конфликты`) for the coherence check's conflict callouts, carried byte for byte (Chapter 19). Inside a group the rows follow the ladder: vision, use-cases, design, ui-design, architecture, test-plan, tech, code-plan, then the `Start` labels, then `Publish`; a `Write` or `Revise` row sits on its document's rung. The rows of one verb share one callout in that order, and the callouts follow the ladder position of their first row. The callout's head is the verb exactly as the labels write it, in every note language; its footer is the fixed line for `Write` and `Review`, in the note's language, and for any other verb the distinct hints its rows carried. A ticked row stays a ticked checkbox in its verb's callout; a group without rows gets no sub-heading; everything that is not a gate callout — the protected tag, the explainer, a halt callout — stays above the first sub-heading in its own order. Which rows exist is still yours and the type playbooks' business: hang and take down your own rows by hand as they say, and never write a sub-heading yourself. The rule that follows is that **every edit of `# Gates` ends with `review-rows`** — after hanging or taking down any row, run the verb once more so the section is folded into the grouped shape again.

- A ticked `Review` row is enacted with `Skill(lazycortex-review:lazy-review.submit, ...)` — the same verb the coordinator already uses to open a document for review directly. No `dispatch-job`, no `mark-job`, no `active_job`.
- The halted-asset override applies exactly as above: `spec_halted: true` takes every un-ticked row down — the verb owes a halted note nothing.
- No `# History` line for the enacted tick — opening a review is not a journaled event (the closed list is in `lazy-spec.status-note-protocol.md` Part 4).
- Only a tick opens a review through this row. An operator edit landing on a document outside review is an ordinary operator edit; the coordinator never answers it by opening a review.

**The `empty` and `deferred` cases — a tick that moves the stage first.** Two stages are not live. A document at `spec_stage: empty` was seeded and never worked on; a document at `spec_stage: deferred` is parked — the coordinator never promotes its stage, never edits it, and it closes no gate. Both exist, which is why no `Write <doc>` row hangs for either and no replacement is ever seeded in its place — the type playbooks' `Write` rows all read "the document doesn't exist". What hangs for them is this chapter's own `Review <doc>` block, on the ordinary per-file condition above.

Ticking it on either stage is the operator saying "pick this up", so the enactment is two calls in one commit rather than one: `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> set-stage <doc> draft` first — `draft` being the forward step out of `empty` and the exit from `deferred` that brings a document back (`cancelled`, the other one, abandons it) — and then the ordinary `Skill(lazycortex-review:lazy-review.submit, "<doc>")` this block class already performs. The document is live from that commit on, so the next wake reads it exactly as it reads any other draft in review. Neither call journals anything — a stage move and a review opening are not history events.

**A tick on a still-empty document launches nothing.** Before enacting any `Review` tick, read the document's body: when it holds no prose line outside headings, HTML comments, protected tags and auto markers, it is still the untouched template and there is nothing to review. Make no call — untick the row, leave the stage where it is, and say in `# Status brief` that the document is still empty and waits for the operator's text.

This closes a gesture gap: re-opening review on an already-approved document from Obsidian alone had no route before — every other entry into review needed a Claude session.

An asset whose every stage-bearing document is parked this way reads as `spec_state: deferred` — the whole asset is a parked backlog, whatever rows its note happens to hang. One live document among the parked ones is enough to take the asset off that state and back onto the ordinary table.

**`spec_released` — the publication flag.** Readiness for a downstream consumer is `spec_released` alone; there is no separate draft flag. It never closes on an asset's own wake: the `Publish` tick on the release note sets it on every included asset together with the version tag, and on the release itself once the production deploy, when one is declared, has succeeded (`lazy-spec.release-playbook.md`, "Release and Publish"). A research asset's closes with the approval of its `research.md`; in a spec-only product the operator's own word closes it (Chapter 17).

## 6. Opening review on a job's result

**The document arrives before the submit does.** A job never writes into the asset folder: it returns its result document as the first entry of its response's `result` array and every attachment after it. On the job's `DONE`, `lazy-spec.gate-tick` runs the `land-result` collector — it puts the document at its target path, each attachment beside it under its own basename, and commits exactly those paths under its own bot identity — and only then raises the `job-done` wake this chapter's submit answers. So the document the coordinator submits is already tracked. A job whose `result/` delivered nothing landed nothing: the coordinator marks it undelivered, exactly as it does today, and opens no review.

On the DONE of any job that WROTE a document, and before evaluating any gate, the coordinator calls `Skill(lazycortex-review:lazy-review.submit, "<result doc>")` on the document that job just produced: `submit` here, because the writing round already happened and only the review round is missing. The verb choice is that criterion, not a fixture — `submit` when the content is already written, `Skill(lazycortex-review:lazy-review.start, ...)` when the writer round itself is what is needed. Re-opening an already-finalized living doc so a writer folds carried-in material (Chapter 14's candidate legalization) is `start`'s case: a bare `dispatch-job` against a finalized, banner-carrying doc is no substitute — the runtime contract stops that writer at a file the system owns regions of, and the edit strands in the job's `result/` with nothing able to apply it.

This is the ONLY path a freshly-written document takes into review — reports included. There is no md-scan sieve left that discovers a new document on its own, so skipping this call strands the document at `spec_stage: draft` with no `review_active` and no forward path, forever.

A DONE whose `response.json` carries a `blocked` field wrote no document — there is nothing to submit, and Chapter 14's ladders apply instead.

## 8. Work-result acceptance cycle

A report entering review (opened by Chapter 6's submit call on its writing job's DONE) carries a different semantic than every other doc's review: this is not editing prose, it is **accepting a piece of work**.

**Comments or reject.** When the operator leaves comments on the report (through the ordinary review checkbox conveyor) or rejects it — either via the review loop itself, or via a `# Coordinator commands` entry — the coordinator dispatches a continuation job to the SAME expert that wrote it via `dispatch-job`: the comments and the existing report (the journal of prior iterations) ride in `context`, and the payload carries the SAME `branch` value the original launch-checkbox dispatch used. The expert continues the same journal rather than starting fresh. A new `DONE` re-submits the report; the cycle repeats until acceptance.

**The playbook rule the writer follows.** The class's main-writer NEVER rewrites the report itself in response to comments — a comment on a report means the underlying WORK needs redoing, not the journal's prose. The report is a record of what happened; fixing it by editing the words instead of the work would falsify the record.

**Approve = end of work on the branch.** Approving the report is the terminal act: the coordinator flips the human-signal gate that report answers for (Chapter 4 — an implementation report closes its tool's share of `spec_develop_done`, a `test` report closes `spec_tests_passing`), AND merges the branch — IF merging is permitted (the expert's own `merge: auto` operational setting, per `lazy-core.expert-runtime-schema.md` § Workspace, AND no rule layer in scope — vault doc, product rules, asset rules — overrides it to `ask`). When permitted, the coordinator runs the merge itself via `Bash(git merge <branch>)` against the daemon's base branch, ff or no-ff by what the merge actually resolves to, never forced; a conflict is never resolved by the coordinator — it asks the operator via `[!question]` instead. `merge: ask` (the default) or no expert setting at all means the coordinator always asks first, even on a clean merge. The runtime itself never merges — `expert_pump.py` only creates/checks out/restores the branch around a spawn; the merge decision and the `git merge` invocation both belong to the coordinator alone.

**Branch as workspace.** The report's implementation work lives on a job-scoped branch, enforced by the runtime whenever the dispatched expert carries `workspace: branch` (`lazy-core.expert-runtime-schema.md` § Workspace) — developer/tester classes are seeded with it (`lazy-spec.install` / `lazy-experts.install`). The coordinator computes the branch name `spec/<product>/<folder>/<slug>` — slash-separated, the product's compound-key as its own segment (removing both the product collision and the hyphen ambiguity a bare `<folder>-<slug>` join would carry) — from the asset's own token at the FIRST launch-checkbox dispatch and passes it as the payload's `branch` field; every continuation dispatch for the same asset passes that identical value back — the runtime's create-or-reuse check makes this idempotent, so the coordinator never needs to track "was this branch already created". The name is RECOMPUTED, not persisted anywhere — renaming an in-flight asset (moving its folder, changing its slug) silently orphans the branch computed under the old name; there is no reconciliation for this today. What happens to the branch after approve — merge, or something else — is the coordinator's call under the merge rules above, not a fixed script outcome.

**`branch` is a capability, only the coordinator activates it.** `workspace: branch` on the expert entry does not force every job onto a branch — the runtime only branches a dispatch whose payload actually names `branch`, and the coordinator is the ONLY caller that ever writes that field, only for a launch-checkbox dispatch and its continuations. The same developer/tester expert is also dispatched for ordinary review rewrites of unrelated documents (`review.coordinator`, an independent operator-facing flow) — those dispatches carry no `branch`, so they run on whatever is already checked out exactly as a `workspace: main` expert would, never refused for lacking one.

## 10. Asset types, tools, and the registry

**A new type costs zero script lines: a declaration plus a playbook.** The declaration — `products[<key>].asset_types.<name>` over the shipped defaults — carries `icon`, optional `color`, `playbook`, optional `alias_of`, optional `default_path`, `start_doc` as `"<file>:<doc_type>"`, and optional `default_tools`. The playbook it names is an ordinary reference describing the type's own flow. Nothing else exists to write: no per-kind branch in any script, no gate table, no folder special-case.

**A new tool costs the same: a declaration plus a playbook.** `products[<key>].tool_types.<name>` carries `playbook`, `report_doc`, and an optional `plan_doc`. That is the whole surface — the report document is what resolves the tool's expert (Chapter 5), the optional plan document is the release's plan for that tool, which a release's `spec_plan_done` waits on when it exists (`lazy-spec.release-playbook.md`).

**The coordinator invents neither a type nor a tool.** The allowed sets are exactly the shipped defaults ∪ the operator's declarations — nothing else. The coordinator spawns and materializes assets ONLY from the type registry: an `[!asset-proposal]` naming an undeclared type is refused with a `[!question]` to the operator, never a silent folder creation, and a routing spawn (Chapter 9) only ever offers declared types as spawn kinds. The same holds for tools: an undeclared token in `spec_tools` is reported, never resolved by guessing a playbook or an expert (Chapter 2). A brand-new type or tool is exclusively an operator act — the coordinator never creates one on its own, however obvious the need looks from inside a job.

**Aliases.** A type whose declaration carries `alias_of: <base>` is a full type of its own — a legal spawn kind like any other. What it borrows from the base is ONE thing: the base's playbook, and only when it declares no `playbook` of its own. Everything else stays its own — its own `default_path`, its own `icon` and `color`, its own `start_doc`, its own `default_tools`. `<base>` is a shipped or declared non-alias type other than `release` — a release is never an alias base; aliases never chain.

## 11. Summary, status brief and questions

**`# Summary`** carries the asset's one-line description — what this asset IS, in a single plain sentence written directly under the section's explainer line. An asset note carries no `<!-- spec:precis:* -->` markers and no stats region; the line itself is the whole section. It is the only thing a reader sees without opening the note, since Obsidian shows it in listings and on hover. `lazy-spec.create-asset` writes the first one at scaffold time; from then on the coordinator owns it and keeps it current.

**Description, never status.** The description says what the asset is about and never what stage it is at, what it waits on, or what happened last. Status is `# Status brief`'s job one section below, and a description that drifts into status goes stale on every gate flip. So rewrite it only on a wake where the asset's subject genuinely changed, and leave it exactly as it stands on a wake that merely moved a gate. Written in the note's resolved language, like every other narrative surface.

**`# Status brief`** is the coordinator's own prose section on the asset folder-note — plain product-language narration of what's happening, why (if) the asset is stalled, and what happens next. It is REWRITTEN on every coordinator invocation on that asset, not appended to — the brief always reflects the current state, never a running log (that role belongs to `# History`).

**Short, and about state — never a synopsis.** The brief is two to four sentences: what state the asset is in, what it waits on, what happens next. It never retells what a document contains — a reader who wants the design opens `design.md`, and a brief that summarises it goes stale on the document's first edit while doubling the surface a review has to keep honest. It never narrates the coordinator's own mechanics — which commit woke it, what that commit's subject said, which trigger fired; that is run-log material, not asset state. It names documents and operator controls by their visible labels (`design.md`, the `Review design.md` checkbox) and stays off engine vocabulary — gate keys, `spec_*` frontmatter names, `review_active` — because the operator reading the note is reading product state, not the implementation. When nothing changed since the last wake, one sentence saying so is the whole brief.

A sound brief reads like: "`design.md` is an operator draft awaiting review — tick `Review design.md` to start the cycle; until the design is approved, the later stages stand still." The failure mode to avoid opens with the commit that woke the coordinator, retells the design document section by section, confirms each recorded decision against it, and closes by observing that none of the gates moved.

**The explainer line survives the rewrite.** The single HTML-comment line (`<!-- ... -->`) sitting right under the section's `#protected/spec/status-brief` tag is the section's self-description, owned by the engine (`note_explainers.py`), not part of the brief — visible only in the editor, invisible in reading view. On every wholesale rewrite the coordinator keeps that line exactly where it is and writes its prose BELOW it — never deletes it, never rewords it. The same holds for the explainer lines under `# Gates` and every other generated section the coordinator re-renders.

**Language.** Written in the doc's resolved language (`lazy-spec.config-protocol.md` Part 3's five-rung chain: doc frontmatter → product `language` → `spec` section → vault default → `en` floor) — the same resolution every other narrative-prose spec surface already follows.

**Operator communication.** Only `[!question]` callouts with `- [ ]` options, dropped into the folder-note body, and ending with the coordinator's own attribution as the callout's LAST quoted line: `> — spec.coordinator`, separated from the last option by a blank quoted line (`>`) — the block shape Chapter 5 fixes for every checkbox-carrying callout. A tick on one of those options is trigger 4 (Chapter 1) — it wakes the coordinator with the answer, the same loop the launch checkboxes already use for dispatch. The attribution line is structural, not decorative: `lazy-spec.coordinator-watch`'s ANSWER trigger only reacts to a ticked block ending in that exact line, so a ticked `[!question]` an expert dropped in its own report, or one an operator authored by hand without the coordinator's own pen, never wakes the coordinator (4a debt — before this line existed, ANY ticked `[!question]` anywhere in the body fired ANSWER, coordinator-authored or not).

**Retiring an answered question.** On handling a ticked answer, the coordinator removes the answered `[!question]` block from the folder-note before finishing — recording the chosen option with one `note-history` line — never leaves it in place ticked. A ticked question left standing re-fires the same trigger on every subsequent wake, which is a live loop hazard, not a hypothetical one: the `lazy-spec.coordinator-watch` worker stamps a content fingerprint of the ticked block (`spec_coordinator_answered`, worker-internal, never written through `note-set-key`) once a dispatch on it succeeds, so an *identical* ticked block never re-fires — but that fingerprint only suppresses a re-fire of the SAME text; it does not remove the block, and it is not a substitute for the coordinator actually clearing it. Removing the block is still the coordinator's own obligation, both for note hygiene and because a stray ticked question the operator did not mean to re-answer is confusing to read.

**Update cadence.** Before deciding or acting on any invocation, the coordinator re-derives the brief from current state — it never trusts a stale brief as an input to its own reasoning, only as what it is about to overwrite.

### `spec_state` — the same judgement, in one word

The brief says what is happening in prose; `spec_state` says the same thing in one token so the file explorer can paint the asset folder without anyone opening the note. **The coordinator writes it through `note-set-key` on every wake that rewrites the brief**, from the same reading of current state — the two never disagree, because they are one judgement rendered twice.

The value is whichever of these fits first, read top to bottom:

| Value | The asset is |
|---|---|
| `deferred` | parked: every stage-bearing document of the asset sits at `spec_stage: deferred` — nothing else about the note is consulted |
| `waits-operator` | holding a launch checkbox or a `[!question]` the operator has not ticked; automation is standing |
| `awaiting-release` | a design-only asset whose start document is approved and which no open release lists in `spec_includes` — it waits for `Start release`, or for an open release's `Rebuild` |
| `in-release` | a design-only asset an open release lists in `spec_includes` |
| `in-review` | carrying a sibling document with `review_active: true` |
| `implementation` | a release tracking its build, or holding `spec_develop_done` open with everything before it closed |
| `testing` | a release tracking its test run, or holding `spec_tests_passing` open with everything before it closed |
| `done` | past `spec_released` — for a design-only asset, published by a release |
| `draft` | none of the above — the design is still being written |

The order is the point: an asset that is both waiting on a tick and holding an open gate reads as `waits-operator`, because that is the one a person can act on. `deferred` sits above it because a fully parked asset hangs rows that would satisfy the `waits-operator` condition without anyone actually waiting, and reading a parked backlog as an operator's queue is exactly the wrong signal to paint. A partly parked asset — one live document beside parked ones — is not `deferred`; it reads from the rows below like any other, and its parked documents simply close nothing.

`spec_halted` and `spec_cancelled` are NOT values of this key. They are their own frontmatter flags, and the registry paints them over whatever `spec_state` says — so the coordinator leaves the state token describing the work, not the freeze.

### The attachment registry

`# Attachments` is the coordinator's own pen, tagged `#protected/spec/attachments`, and it lives on the same folder-note as the brief. It carries one line per NON-markdown attachment of the asset — a link to the file and the document that owns it. Attachments are asset-type-independent, so this rule is the general one and no type or tool playbook restates it.

- **Reconciled on the wake raised by the commit that created the file.** When that commit is a job's own, the owning document is the job's result document, read from its `request.json` — the coordinator does not guess.
- **A markdown attachment is never listed here.** Its ownership lives in its own `spec_owner_doc` frontmatter, and duplicating it would create two sources of truth that can disagree.
- **A markdown attachment's `spec_stage` is reconciled here instead.** The key is a mirror of the owner's stage (`lazy-spec.file-roles-protocol.md` § Attachments): on any wake, the `promote-approved` call of Chapter 4 brings an attachment whose stage differs from its owner's — a newborn attachment with no stage yet, or one whose own review just finalized while the owner moved — to the owner's current `spec_stage` and `spec/<stage>` tag, and its path rides in this wake's own commit. The one exception is an attachment currently carrying `review_active: true`: the review cycle owns the file, and the doc-transition wake its finalize raises is where the catch-up lands.
- **A file whose owner cannot be established is unattributed, and unattributed goes to the operator.** Created by hand, or by a job whose result document does not sit in this asset — either way the coordinator raises the ordinary `[!question]` callout on the folder-note, offering the asset's own documents as the tick options. The ticked answer arrives on the existing answer trigger; no new mechanism is involved.
- **A markdown file of the asset carrying no `spec_doc_type` is escalated the same way**, with the product's declared document types as the tick options. It is a separate question from the ownership one and may need asking even when ownership is clear: the two keys record different facts, and a file can be missing either.
- **A registry line whose file no longer exists is removed** on the next reconciliation.

## 16. Operational notes

**Dual git-watch on one spec-doc commit is expected, not a bug.** A single commit touching a spec document can legitimately fire both the wiki's own scan routine and the terms-dictionary's scan routine (each watches overlapping but distinct file sets for its own curation purpose) — this is normal, do not "fix" it by trying to merge the watches.

**The `folder_note: false` invariant must not break silently.** The coordinator's ownership of every asset / product / group folder-note requires NO coordination with the wiki or terms-curation subsystems ONLY because every wiki scope's `folder_note: false` setting (enforced by `scope.py`, including on relink) already excludes folder-notes from wiki curation. This is presently a side effect of that scope filter's design, not a contract the wiki subsystem has explicitly committed to preserving. Treat this note as the tripwire: if a refactor on either the coordinator side or the wiki side ever touches `folder_note` handling, re-verify this invariant before assuming it still holds.

**A spec wiki scope must exclude the append-only journals.** A `/lazy-wiki.configure` scope covering spec content should carry every tool's append-only report journal (`**/code-report.md`, `**/test-report.md`, `**/data-report.md`, `**/docs-report.md`, and whatever a declared tool adds with `append_only: true`; a stage-bearing report such as the `research` tool's `research.md` is content and is never excluded) in its `exclude_paths` — each is an append-by-a-running-job doc, and without the exclusion the wiki curator re-fires on every append.

## 18. Cycling — recognising a loop before the daemon does

Long autonomous stretches are the point of this system: an asset may legitimately travel definition → plan → implementation → tests with dozens of bot commits and no operator between them, and the daemon's loop detector halts only on literally repeated identical diffs. Semantic cycling — motion without progress — is YOURS to catch, because only you can compare intentions. Check on every wake, before acting; the inputs are in front of you (gate booleans, the folder-note's `# History`, your own previous commits on the asset).

The signals, each sufficient on its own:

- **Same dispatch, unchanged cause.** The job you are about to dispatch matches a dedup key you already dispatched on a previous wake for this asset, AND the condition that justified it (the gate state, the doc's stage, the finding it answers) is unchanged since that dispatch completed. A job that ran and moved nothing will not move anything the second time.
- **Gate ping-pong.** A gate you flipped is off again (downward reconciliation) and the cause of the regression is materially the same one your previous forward flip answered — two of your own wakes are undoing each other.
- **Your own echo.** Your intended verb sequence equals your previous wake's (same verbs, same keys, same targets) and no operator gesture, no expert payload, and no sibling-asset change landed between the two wakes. A wake with no new input must not repeat the old output.

On any signal: do NOT act the repeat. Write a `[!question]` callout on the asset's folder-note naming the repetition concretely — which action, how many times, what failed to change — with `- [ ]` options (retry once / operator intervenes / halt the asset via `flip-gate --halt`). Then rewrite `# Status brief` to say the asset is paused on a suspected cycle and commit; your own `coordinator_job` marker is the watch worker's to clear on its next invocation, never yours. One asset pauses; the daemon and every sibling keep running. Never resolve a suspected cycle by trying harder.

The daemon's patch-id loop detector remains the incorruptible backstop BENEATH you: if your own judgment is what's broken, the daemon halts on the identical diffs you leave behind.

## 19. Coherence

**One path for every contradiction.** A contradiction between two documents of the catalog — two documents promising incompatible things — has one route and no other: after every approval and every re-approval of a document, the coherence check compares it with its nearest neighbours. Nothing else looks for contradictions. A re-approval never returns a dependent document to work, never lowers a stage and never turns a gate off on the grounds that something it was written from has changed (Chapter 4) — the one gate a re-approval does turn off is the re-approved start document's own asset's `spec_released`, which sends that asset back into the delta (Chapter 4, "A re-approved start document of a released asset"); a build does not look for them either (`lazy-spec.release-playbook.md`, "The build").

**Who runs it.** The coordinator of the note whose document just turned `approved` — this one for an asset's document, `spec.catalog-coordinator` for a system document of a level. The trigger is a `CoordinatorTrigger.DOC_TRANSITION` whose `review_result` turned approved — a first approval or a re-approval alike. A document still at `draft` is promoted to `approved` first (Chapter 4). A document already at `approved` is being re-approved: the same `promote-approved` call restamps it, its basename passed as `--transitioned`, so the approval moment the check compares is this one — no separate `set-stage` restamp follows. Then run `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> coherence-dispatch <doc>` once. It collects the neighbours and dispatches one job to the `spec.coherence-checker` expert, printing `{"checked", "neighbours", "job_id"}` — with `"dropped": <n>` added when neighbours were left out over the size budget — or `{"checked", "status": "skipped", "reason": "no-neighbours"}` when the document has none, or `{"checked", "status": "skipped", "reason": "over-budget", "dropped": <n>}` when not even the first neighbour fits the budget — each an ordinary outcome, not a finding. The verb never writes the folder-note. On the `over-budget` skip, append the drop to `# History` yourself through `note-history`, as part of your wake commit: `coherence check of <doc>: <n> neighbour(s) dropped over the size budget`, in the note's language. On a queued check, the dropped count travels with its `coherence_jobs` entry, and the `# History` line `lazy-spec.gate-tick` writes when the result lands names it: `coherence check of <doc>: <c> conflict(s), <n> neighbour(s) dropped over the size budget`. The job is tracked in the note's own `coherence_jobs` runtime sidecar list (`{doc, expert, job_id}` per checked document), apart from the `active_job` marker: it blocks no launch job on the same note, a launch job never blocks it, it hangs no row, and the wake carries on with its gates and rows at once. A second dispatch for a document already listed replaces its entry; a skip — `no-neighbours` or `over-budget` — retires the entry already listed for that document, so a check of the replaced text never lands. On the job's `DONE`, `lazy-spec.gate-tick` runs `coherence-apply` on its own, which hangs the callouts and commits them under the `lazy-spec.coherence` bot identity, and journals one `# History` line naming the document and the number of conflicts. It raises no wake; the coordinator has no part in the apply. A failed apply is logged in `# History` and changes nothing else; the next approval of the document runs the check again. A callout's reference to a document since deleted or cancelled is pruned automatically, never by hand.

**What is compared.** Every authored document with a stage takes part: `vision.md`, `use-cases.md`, `design.md`, `ui-design.md`, `tech.md`, `architecture.md`, `test-plan.md`, a research design and its report. The append-only journals (`code-report.md`, `test-report.md`) and a release's own `code-plan.md` do not. A neighbour counts only when it is `approved`: a draft will still change, and its own approval runs the check against everything already approved. A released asset's documents take part like any other — consistency matters whether or not the asset has shipped.

**Who the neighbours are.** `coherence-dispatch` collects them, never by reading links by hand: the wiki engine's neighbours of the document — its See-also targets and the nodes whose See-also point at it — united with the product hierarchy — the system documents of the document's own product, its parent product and its nested products — and filtered to the approved documents above. One check sends at most 150 KB of neighbour text: the neighbours are taken in priority order — the wiki's first, then the level documents of the document's own product, then those of its parent and nested products, each group in sorted order — until the next document would exceed the budget, and that document and every one after it are dropped; a document is sent whole or not at all. The checker reports only the conflicts the checked document is a party to. Without a wiki scope over the catalog only the hierarchy answers, so two neighbouring assets are never compared, and `lazy-spec.audit` reports that once as an INFO advising a wiki scope.

**What a conflict looks like.** A document is INNER to a folder-note when it lies in that note's folder, and OUTER to it otherwise. `# Gates` carries a `## Conflicts` group after `## Next step` and `## Re-review`, laid out by `review-rows` like the other two. It holds one callout per inner document and per essence: a `[!warning]` whose title links the documents the inner one disagrees with — inner or outer — whose body is one short sentence naming the contradiction, followed by two boxes, `Resolve here` and `Not a conflict`, and a closing comment naming the inner document. The same conflict hangs a mirror callout on the folder-note of every document in its title, where that document is the inner one. Two inner documents of one note that disagree with each other give two callouts, one for each. A note holding at least one callout carries `spec_conflicted: true`; the verbs keep the key, never the coordinator.

**The two boxes.** A tick on either reaches the coordinator as an operator edit of its note (Chapter 1, trigger 1).

- `Resolve here` sends this inner document — and no other — back to its writer, then through its review. Run `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> coherence-resolve <note> <doc>`: it takes down the ticked callout — that one essence — and its mirrors on the other notes, leaving `<doc>`'s other callouts in place, and prints `{"doc", "conflicts": [{"essence", "with"}]}`. Then write ONE `> [!todo] #review/command` callout into the document naming each essence and the documents in its `with`, telling the writer to fix only these contradictions and add nothing else, and open its review at the writer round with `lazy-review.start`. The review's coordinator carries the command out as the round's input (`lazy-review.doc-review-protocol.md`), and the review then runs as any other. That callout is the one write either coordinator ever makes into a document's body for this — the asset coordinator's `sibling-doc-waiver` and the catalog coordinator's single exception name it. The other documents of the conflict are not touched.
- `Not a conflict` takes down the ticked callout — that one essence — and its mirrors with the same essence on the other notes; the document's other callouts stay. Run `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> coherence-dismiss <note> <doc>`: it records each pair in `spec_conflict_dismissed` on both notes together with both documents' approval moments, and the check does not raise that pair again until one of the two documents is re-approved.

Both verbs refuse with `nothing-ticked` when no callout of `<doc>` carries the ticked box; that is a stale wake, not an error to report. A resolved document is checked again on its next approval, and whatever conflicts remain hang until they are fixed or dismissed.

**A conflict blocks nothing.** The `## Conflicts` group never holds a gate shut, never takes a row down and never stands in the way of `Rebuild` or `Publish`; `spec_state` ignores it. Its one visible effect is the colour: a folder with an open conflict is painted fuchsia (`#f0abfc`), which outranks every work-state colour, the operator's waiting one included, and yields only to a halted asset's red. `# Status brief` names an open conflict in one sentence — which documents disagree — and never retells its essence.
