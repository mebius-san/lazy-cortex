# The release build — protocol

This is the law of the implementer inside a release's `Build` job and its continuations, and of the same implementer discussing the build's `code-report.md` under review (The report under review, below); every such dispatch names it in `protocols` (`lazy-spec.release-type.md`, "The build"). The release is built as one product: nothing on an included asset or on its type says who builds it, and no asset is ever built on its own.

`<core-cli>` stands for the core plugin's `bin/lazycortex-core` file — the copy under `~/.claude/plugins/cache/lazycortex/lazycortex-core/<version>/` that `~/.claude/plugins/installed_plugins.json` records as installed, or `plugins/claude/lazycortex-core/` in a checkout that authors the plugin. Every verb runs through the interpreter, `"${LAZYCORTEX_PYTHON:-python3}" <core-cli> <verb>`: the file carries no exec bit and is not on `PATH`.

## What the build delivers

The deliverable of a build is **the product, whole and working**: changed and added files in the product repository — code, data, documentation, interface, text, whatever the approved designs call for — that pass the repository's own checkers and runners. The unit tests of the changed code are part of the same deliverable. The `code-report.md` document is the journal of what was done, never the deliverable itself — it only presents the work for acceptance.

The build's work counts toward the release's `spec_develop_done`, never toward `spec_tests_passing`: the deployed product is tested later, in the testing stage (`lazy-spec.test-job.md`). An asset note carries neither gate — implementation is the release's business, and the asset's own ladder ends at the approval of its start document.

## What the build reads

- **The plan.** `code-plan.md` of the release when it is `approved`: its tasks, in order, over the product as a whole. With the plan waived — a line in the owner's `# Coordinator rules`, or the release's `code-plan.md` at stage `cancelled` — the source is the start documents of the included assets instead (`lazy-spec.release-type.md`, "The plan comes first, or its waiver").
- **The specialists.** `context/specialists.json`, `{"key", "specialists": [{"role", "expert", "agent", "aspects", "material", "guidelines", "origin"}]}`: the product's specialists, one entry per role, each naming the expert that makes that material, the agent registered for that expert, the reference keys of that expert's aspects — its domain craft, as its `experts` entry declares them —, and the guideline paths of that role — the enabled plugins' canon for the role first, then the product's; an entry is repo-relative or an absolute path into a plugin tree, read in place either way. The coordinator computes it on every dispatch; it is the only list of specialists the build knows, and an empty list is a product with none.
- **The type guidelines.** `context/type-guidelines.json`, `{"release", "assets": [{"asset", "type", "base_type", "guidelines"}]}`: one entry per included asset, each with its type, the shipped type that type borrows its playbook from through `alias_of` (`base_type`, the type itself when it declares no alias), and the repo-relative paths its type declares in `asset_types.<type>.guidelines` — for a content type, the schema its records are written against (`lazy-spec.content-type.md`). The coordinator computes it on every dispatch with `release-type-guidelines`; an entry with an empty list is a type that gives the build nothing to write against.
- **The context.** The product's `architecture.md` and `tech.md`, the `tech.md` of every product that owns an included asset, every included asset's folder (design, test cases, its `decisions.md`), the product's own `decisions.md`, and — inside an open release with earlier builds — the change list. A member of `spec_includes` cancelled since it was included is in none of these.
- **The guidelines.** The payload's `guidelines`: the paths for the implementer's own role — the enabled plugins' canon first, then the product's guidelines for the role and its wildcard guidelines. An entry is repo-relative or an absolute path into a plugin tree; the implementer reads each in place.

No build revises the product's root `architecture.md`: it is brought up to date on the product note before the release starts (`lazy-spec.release-owner-playbook.md` § 4).

## The implementer and the specialists

The implementer is the expert the product's `release.implementer` names (`resolve-product release-implementer`). It makes itself the material of its own role. Every other material comes from a specialist, and roles are symmetric: a product made of data has a data expert as its implementer and orders the code from the `developer` specialist.

- **Which tasks go to a specialist.** A `code-plan.md` task that names `Specialist: <role>` is made by the specialist of that role; every other task is the implementer's own.
- **The waived plan.** With no plan the implementer does the planner's part: from the included designs it decides which material its own role does not make, and orders each from the entry of `context/specialists.json` whose `material` covers it.
- **The order.** For each such task the implementer launches a child agent of the entry's `agent`. It hands over the entry's `expert` as the key the child runs as — the `<self>` its memory folder `.memory/<self>/` resolves to —, the task — what to make —, the folder of the working tree to put it in, the design of the asset the material comes from, that asset's `decisions.md` and the product's `decisions.md`, so the material does not drift from a choice already on record, the entry's `guidelines`, that asset's `guidelines` from `context/type-guidelines.json` — its schema, for data —, and the files of the entry's `aspects`, each key resolved with `"${LAZYCORTEX_PYTHON:-python3}" <core-cli> resolve-ref --category aspects <key> …`, so the chosen expert's domain craft reaches the material and two experts of one role in different domains do not make the same thing; all as paths the specialist reads. An aspect key that does not resolve ends the job with `outcome: error`, named in the failed `#### build <k>` entry, exactly as a missing specialist does. One child agent serves one task.
- **The order carries its run contract.** The child agent starts from its persona and never reads this protocol, so the implementer writes the run contract into the order itself, ahead of the task, as the child's protocol for this order: write only into the named folder of the working tree and edit no other file of the product; never commit, never create or switch a branch; no `result/`, no review loop, no report document and no other delivery route — the material in the named folder is the whole delivery, and the child's answer names what it put there. The order states that this contract outranks, for this order, every delivery, commit, branch and review rule of the persona, including Principles the persona calls rules — "commit each task", "edit in place on your job's branch and commit", "mockups travel through `result/`, never into the working tree" do not apply to it, and it outranks the same rules of the handed aspects, their write-scope rules included — an aspect's "write nothing outside `result/`" or "outside `.experts/.jobs/<self>/<job-id>/` and `.memory/<self>/`" gives way to the named folder for this order, while writing a memory note under `.memory/<self>/` through `/lazy-memory.write` stays allowed. The persona's craft — how to make the material well — still applies, and so do the aspects' craft and memory. The contract covers the work, never the memory: a child whose aspects include `lazycortex-core:lazy-memory.persona-aspect` reads `.memory/<self>/` before it starts and records what it learned through `/lazy-memory.write` in the same run as its delivery. That skill writes under `.memory/<self>/` and commits the note on its own under the memory-bot identity; that commit is the memory mechanism's, not the child's, and breaks nothing. A result that breaks the contract — a commit of the work, a branch, a file outside the folder other than the memory note — is not integrated: the implementer records the breach in the `#### build <k>` entry and orders the material again under the same contract.
- **The integration.** The implementer places the material — data in the place the project's schema defines for its entity, any other material where `architecture.md` or the plan's task puts it; the order's folder is a working folder, and the implementer moves the material from it into that place —, wires it into the code, the layout or the data it belongs to, and verifies it with the repository's own checkers and runners. It answers for the whole product after the build being whole and working, the specialists' material included; a specialist's result it cannot integrate goes back, with what is wrong, to a specialist of the same role, under the same rules as the first order.
- **A missing specialist.** A task that names a role absent from `context/specialists.json`, or — with the plan waived — a material no entry and not the implementer's own role makes, ends the job with `outcome: error`. The failed build's `#### build <k>` entry names each such task and the missing role; the implementer never makes that material itself and never picks another expert in its place.

## The material and the design

- **No schema, no data.** An included asset whose entry reads `base_type` `content` — the type `content` itself or a type declared `alias_of: content` — needs a schema to write its records against. When its entry in `context/type-guidelines.json` holds no path — the type declares none, or every declared file is missing — the build ends with `outcome: error` before any of that asset's data is written, and the failed `#### build <k>` entry names the asset and its type. Neither the implementer nor a specialist infers the format from existing data.
- **Decisions, not values.** A design states decisions, never values. Whoever writes the data chooses every concrete value so that the data expresses those decisions; the reason for a value lives in the data — in the schema's own comment field where it has one — and never goes back into the design.
- **The project's validators.** Schemas, linters, data loaders and doc checkers run through the product repository's own runner on the material before the build reports. A red validator is unfinished work, not a finding for review; the `#### build <k>` entry records each run and its outcome, and a validator that fails or cannot run ends the build as The environment and the checks says, below.
- **Material against the design.** This holds for every material — code, data, documentation, mockups, text. Material that fails a decision of the approved design is a defect in the work and is fixed by work: it is brought to express the design. A disagreement with a decision of the design itself — no material can express it, the schema forbids it — is an objection to the design: the implementer records it in the `#### build <k>` entry, and it travels back into the design through the design's own review, never silently into the material. Material made "the way it should be" against an approved design is the same finding, even when its maker is right.

## Unit tests

The implementer writes every automated test that lives in the project for the code the build changes, as the plan lays them out, and runs them green before it reports. The testing stage writes no test into the repository: it only runs the deployed product and reports. The framework and the command the product's `tech.md` names; where the tests sit and the seams they reach the code through come from `architecture.md`. Their run is journaled in `code-report.md`, and no test document stands between the design and that work.

## The environment and the checks

**The build works only in the environment its job was given.** It never changes settings: it sets no environment variable — `VIRTUAL_ENV`, `LAZYCORTEX_PLUGIN_DIRS` or any other —, uses no other virtual environment and no other plugin version, and edits no checker configuration; a workaround an earlier entry of the journal records is no exception. A plugin, a path or a virtual environment that cannot be found stops the build, and its error is reported verbatim. A settings problem is fixed by the operator or by the plugin, never by the build.

**A failed check fails the build.** A checker, a validator or a unit-test run that fails or cannot run ends the build with `outcome: error` and the exact error text, in the response's `error.message` and in the build's `#### build <k>` entry. A check wrapper that cannot create its virtual environment inside the job's sandbox is such a check. A build with a failed check never ends in success: it never returns `outcome: edited`.

**Goals are verified by what the product does.** Each goal of the plan is checked by a behaviour test that runs, or by the command itself run against the product. "A test with this name exists" is never a goal check: a search for test names or a grep over a test file proves only that text exists.

## Builds and the journal

**Builds are incremental.** Inside an open release the implementer does only what changed since the previous implementation build that stands; the change list arrives in the job context, and the earlier builds are in `code-report.md` (`lazy-spec.release-type.md`, "The change list"). The responsibility stays the whole product's: the build brings the product to a working state entirely, while redoing only what the change list names.

**Each build runs on its own branch**, the `branch` the dispatch names — the coordinator takes it from the build registry and never composes it; the branch forks from the `branch_from` the dispatch carries, the previous build's unmerged branch or, when it is null, the base branch. Every continuation of the same build runs on the same branch.

**The journal.** Result is the release's `code-report.md`, written by the job itself. The build's `#### build <k>` entry, `<k>` the `spec_build` value its dispatch names, records the tasks done, each specialist's material and where it was placed, every validator run with its outcome, the unit-test run, and the problems left open. A deviation the entry names is a departure from the plan; an outcome the plan itself predicted, such as a first test run failing because the code it tests does not exist yet, is no deviation and is not listed as one. When the journal exists its path is in the job's `context`, and the job returns it whole: every entry of an earlier build intact, plus this build's entry. The entry is written for the operator: each check is stated in plain words — what it checked and how it ended —, with no bare tool name left unexplained, no internal name of a plan step and no raw command output in place of a result. The entry never records a plugin path, a plugin version or an environment variable. The list of what was not done holds only work the current plan owed the build; a step the plan no longer contains is not mentioned. A build that finishes returns `outcome: edited` with the journal as the first `result` entry — `edited` is the success value (`lazy-spec.expert-signals-protocol.md` § `outcome` values). A build that cannot finish returns `outcome: error` together with the journal holding the failed run's entry.

**One current entry per build, newest first.** The first run of build `<k>` opens its `#### build <k>` entry first in the journal, right under the document's title, above the entries of every earlier build, which stay below it unchanged. Every continuation of the same build rewrites that entry whole, in place, instead of adding a second one, so `#### build <k>` always holds one entry stating what the build has done so far and which problems are still open. The entries of earlier builds are never rewritten. The history of the continuations is in git.

**An open problem carries a box to send it back.** Each problem the entry leaves open that a continuation can fix — a review finding left unfixed, a task not finished — is its own task line, `- [ ] <problem> #review/send-back`, one problem per line, outside any code fence and any callout. A check that failed or could not run is never such a problem of a finished build: it ends the build with `outcome: error` (The environment and the checks, above). The operator ticks the problems to be fixed. A tick is a mark in the text and starts nothing by itself: only the operator's decision on the report starts work, and a ticked line then belongs to the continuation's task (The acceptance cycle, below). A step the implementer cannot carry out inside a job — one `code-plan.md` gives to a person, such as a manual check after the merge — gets no box: it is a plain bullet saying it is left to a person. When a continuation rewrites the entry, a problem it fixed leaves the open list and is recorded as done; a ticked problem it could not fix stays open on a new unticked line saying what was tried; an unticked problem stays open on its line exactly as it was.

## What "done" means

The release's `spec_develop_done` closes when its `code-report.md` is **accepted by review** — `review_result` reads `approved` or `approved-with-concerns` and `review_active` is not `true` — while the journal holds the `#### build <spec_impl_build>` entry, and the branch `build-<spec_impl_build>` is merged. The journal carries no stage, so the verdict is never compared with `spec_impl_build_at`: `lazy-review.submit` clears an older verdict, and a verdict present after the build's report was submitted belongs to that build; the coordinator flips it with `flip-gate --auto` (`lazy-spec.release-type.md`, "The gates of the build"). Not "the job returned DONE", not "the code is committed": a job's terminal marker only opens review on the fresh report, and it is the accepted report that closes the gate.

That one report covers the whole build, every specialist's material included, so there is no second report for the gate to wait on.

## Staleness

The source of the report is `code-plan.md` of the release. A plan re-approved after `code-report.md` was accepted moves nothing by itself: the report keeps its stage-less journal form and the release's gates stay as they are; the next build continues the implementer against the re-approved plan, which opens the next `#### build <k>` entry in the journal and re-submits it.

A re-approved design of an included asset hangs `Rebuild`, and its tick rolls the build back: both release plans return to `draft` from `approved` (a `cancelled` `code-plan.md` is the waiver and stays), and `spec_develop_done`, `spec_tests_passing` and `spec_built` turn off (`lazy-spec.release-type.md`, "Rebuild").

## The report under review

The implementer discusses its own report. The coordinator submits every `code-report.md` with the release implementer as the document's writer (`lazy-review.submit --expert`), so the main-writer rounds of its review are this implementer's. The writer's duties in such a round are the review protocol's (`lazycortex-review:lazy-review.doc-review-protocol`, "A report's main round"). This protocol adds what is particular to a build's report:

- **The build's code is read from its branch, never checked out.** `context/build-branch.json` holds the record `build-registry get` prints for the release — the current build's `build`, `branch` and `branch_from`. The writer reads the build's code with `git show <branch>:<path>` and its changes with `git diff <base>...<branch>`, `<base>` the record's `branch_from`, or, when that is null, the base branch the project's `daemon.git.base_branch` setting names. It never checks the branch out, never creates or switches a branch, never commits, and changes no file of the product, no check and no validator: the report is the only file it returns.
- **The verdict is measured against the plan the build ran from.** `plan_verdict` is `sufficient` when every remark can be carried out under the approved `code-plan.md`, `new-plan` when at least one remark does not fit it. With the plan waived (What the build reads, above) the verdict is always `sufficient`: there is no plan for a remark to fall outside, so every remark goes to a continuation of the build.

## The acceptance cycle

Review of a `code-report.md` is acceptance of the **work**, not copy-editing of a text. It ends in one of the operator's two decisions on the report — accept it as it is, or fix it by the remarks — and the path of a fix follows from the writer's last `plan_verdict`:

- **Accepted as it is.** The review approves the report, its finalize removes the discussion block, and the build closes as What "done" means says, above.
- **Fixed, the plan sufficient.** The review closes with `review_result: sent-back` and the report keeps its discussion block: the block is the work order. The coordinator dispatches a **continuation of the same build** to the same implementer, on the build's own `branch`, under every rule of a build — this protocol, the specialists, the type guidelines, `code-report.md` named in its `context` — so the work builds on top of what is already there instead of restarting on a clean slate. The continuation's task is the discussion block and the ticked lines of the current build's entry, `- [x] <problem> #review/send-back`, and nothing else: it carries those remarks out in the product, re-runs the validators and the unit tests the fixes touch, and redoes nothing else of the build. A remark that turns out to need a plan the build does not have is not carried out: the continuation does the rest and names that remark among the open problems of the entry, and the operator decides on it at the report's next review. The continuation rewrites the current build's entry whole (One current entry per build, above) and returns the report **without** the discussion block. The build number and the branch stay the same; only `Rebuild` or a new plan starts a new build. A continuation that ends with `outcome: error` does not fail the build: the build stays open, its branch keeps the code the report was reviewed on, and the next build, once the operator ticks `Rebuild`, starts from that branch.
- **Fixed, a new plan needed.** The review closes with `review_result: sent-to-plan`, and no continuation runs: the remarks go into `code-plan.md` through the plan's own review, and once the plan is approved again the build is closed as not accepted and the next build runs from the plan alone (`lazy-spec.release-type.md`, "A report sent to the plan"). The task of a build is the plan or the report's remarks, never both. With the plan waived there is no plan to rewrite: a `sent-to-plan` is handled exactly as a `sent-back`, and the continuation of the bullet above runs.
- A remark that the material diverges from the design takes the fork of "Material against the design", above. A remark on a specialist's material goes back, inside the continuation, to a specialist of the same role through the implementer, under the same rules as the first order.
- A continuation that rewords the report without touching the work goes around the cycle, not through it. The entries of earlier builds are never rewritten, and git keeps the history of the redos.
- Until the report is accepted the release's `spec_develop_done` stays shut no matter how much work already sits in the repository.
