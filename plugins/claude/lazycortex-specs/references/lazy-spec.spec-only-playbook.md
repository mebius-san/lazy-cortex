# Spec-only mode — conditional chapter of the coordination playbook

Extracted chapter 17 of `lazy-spec.coordination-playbook.md`, loaded on demand: read this file when the owning product's record in the job's `payload["product"]` carries `mode: "spec-only"`. Every "Chapter N" cross-reference below names a chapter of that common playbook.

**Activation.** `products[<key>].mode: "spec-only"`, set by `/lazy-spec.product-config`'s wizard; absence means full mode (the ordinary ladder this playbook and the type playbooks describe). `_build_bundle` folds the owning product's whole record — mode included — into every coordinator job's `payload["product"]` unconditionally, so the profile check below never needs a separate settings read. The profile is a property of the PRODUCT, not of any asset type: it applies to every asset under that product whatever its `spec_asset_type`.

**The ladder is the one every asset runs.** A spec-only asset walks exactly the design-only ladder of full mode: its type's starting document → review → operator approve → `spec_design_done`. Its status note carries the same three gates — `spec_design_done`, `spec_released`, `spec_cancelled` — and its type playbook's checkboxes hang by their own rules, unchanged. This chapter changes nothing in a type playbook.

**The one difference — there are no releases.** A spec-only product has no release ladder: `Start release` never hangs on the product note, no delta is computed, and no release ever picks an asset up. `spec_released` therefore flips true only on the operator's explicit word — a ticked `[!question]` option, or a `# Coordinator commands` entry — once the defining document is approved; the coordinator never derives it from document state and no `Publish` tick ever writes it. A `research` asset is the one exception: the approval of its `research.md` closes `spec_released` exactly as in full mode (`lazy-spec.research-playbook.md`).

**Readiness.** `spec_released` is also the readiness flag: `true` means "this asset is published and ready for a downstream consumer to pick up", absent or `false` means not ready — today another repo's `lazy-spec.upstream-tick`, when it configures this repo as one of its `spec.upstream` sources, but the meaning is not tied to that path. In full mode the publishing release closes it; in a spec-only product the operator's word above closes it — never automatically the moment the defining document approves, except on a `research` asset, whose `spec_released` closes with the approval of its `research.md`.
