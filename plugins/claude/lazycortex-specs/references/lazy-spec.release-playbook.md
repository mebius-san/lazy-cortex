# Release type playbook — the product's unit of implementation

This document is the law for `spec.coordinator` on any status folder-note carrying `spec_asset_type: release`. Every other asset type is design-only: its ladder ends at the approval of its start document, and everything that turns approved designs into a working product — the plan, the code and data and documentation, the tests, the deploy, the version — happens here, inside a release. One release is open per product at a time, and one implementer answers for the whole product inside it.

A release runs in three stages, and the operator starts each one with a tick on the release note: the plan and the implementation (`Write code-plan`, `Build`), the test plan and the testing (`Write test-plan`, `Test`), the publication (`Publish`). The coordinator dispatches no job of a stage before its tick.

## What this type is

`spec_asset_type: release` lives under `releases/` of the product that owns releases — the outermost product in its chain whose record declares a `source` (`lazy-spec.config-protocol.md`). The folder and the note are the release's sequence number with leading zeros to five digits: `releases/00001/00001.md`, `releases/00002/00002.md`. The next number continues from the highest one in `releases/` and in `releases/archive/`, whatever its width. Creating the next release moves every closed release still in `releases/` into `releases/archive/`, its folder and note re-padded to five digits (`releases/001/` becomes `releases/archive/00001/`), in the same commit; a release is never moved when it is published or cancelled, so the last closed one stays beside the open one until the next is created. The version is a key, never part of the name.

The note is an ordinary `status` note with the full ladder — `spec_design_done` (true from creation: a release has no design of its own), `spec_plan_done`, `spec_develop_done`, `spec_tests_passing`, `spec_built`, `spec_released`, plus `spec_cancelled` — and two keys of its own: `spec_version`, a bare SemVer such as `1.5.0`, mirrored by the tag `release/1-5-0`; and `spec_includes`, the wikilinks to the status notes of the assets the release carries. A release is **open** while `spec_released` and `spec_cancelled` are false; a published or cancelled release is closed. A published release never changes again; a cancelled one changes again only through its un-cancel, which the verb allows while no other release of the owner is open and the release has not been moved under `releases/archive/` (Cancellation, below).

**An included asset** is a member of `spec_includes` that is not cancelled. A member cancelled after it was included stays listed, but the next build and the next test run leave it out: it is dropped from every `Build` and `Test` source and context list below, and from the sources a release plan is derived from (`seed-doc --refresh-sources`). A member's cancel wakes the open release's note, which checks its `Rebuild` reasons again (Rebuild, below). The cancel is not a `Rebuild` reason on its own, and the next build, whatever starts it, no longer includes the cancelled member. A release plan, though, must not prescribe it, and that is a state check run on every wake of the release note, not only on the wake the cancel raised: every `approved` `code-plan.md` or `test-plan.md` whose `spec_source_docs` lists a document of a cancelled member returns to `draft` — its sources derived again with `seed-doc --refresh-sources <plan>`, which leaves the cancelled member out, and its review opened at the writer round, as Rebuild step 3 does. A returned `code-plan.md` turns off `spec_plan_done`, `spec_develop_done`, `spec_tests_passing` and `spec_built`; a returned `test-plan.md` turns off `spec_tests_passing` and `spec_built`. No build and no test run is made from a plan that still prescribes a cancelled member.

Documents of the release folder, all opt-in on disk: `code-plan.md` (`code-plan`, the planner's), `test-plan.md` (the `test` tool's plan — the tester's composed plan from the product's standing `test-plan.md`, the included assets' test cases and the regression), `code-report.md` and `test-report.md` (append-only journals, one `#### build <k>` entry per run), `decisions.md`, and flat attachments such as build logs. The product's own `architecture.md` and `test-plan.md` sit at the product root and belong to the product coordinator; a release reads them and never writes them, and the release folder never carries a copy.

`<specs-cli>` stands for the specs plugin's `bin/lazycortex-specs` file — the copy under `~/.claude/plugins/cache/lazycortex/lazycortex-specs/<version>/` that `~/.claude/plugins/installed_plugins.json` records as installed, or `plugins/claude/lazycortex-specs/` in a checkout that authors the plugin. Every verb runs through the interpreter, `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> <verb>`: the file carries no exec bit and is not on `PATH`.

## Creation

Nothing creates a release on its own. An asset's approval — its `spec_design_done` or `spec_cancelled` changing value, either way, or its start document re-approved — sends the owner's level note an `asset-approved` hop that re-hangs rows, rewrites the product's `# Status brief` and at most cancels an open release whose every `spec_includes` member is cancelled or released (`lazy-spec.catalog-playbook.md` § 5); the operator decides when a release starts.

**The delta.** `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> release-delta <product-key>` lists what the next release would carry: every asset of the owner and of the design-only products nested under it, of any type but `release` and `research`, whose start document is `approved`, whose `spec_released` and `spec_cancelled` are false, and — for a `change` — whose `spec_cascade_done` is true. The same call names what is held back and why (`cascade-pending`, `no-start-doc`) and the open release, if any, and two facts a release waits on: `architecture.behind`, the delta's assets whose start document was approved after the product's `architecture.md` (every one of them while that document exists and is not approved, none when the product has no `architecture.md` file), and `conflicted`, the notes of the delta's assets and of the product's levels that carry an open coherence conflict. The order of work inside the release is the implementer's.

**The architecture is the product's, settled before the release.** No build revises `architecture.md`. It is brought up to date on the product note, by the `Revise architecture` row (`lazy-spec.release-owner-playbook.md` § 4), and a release starts only from an architecture approved after every design it carries. **A product without an architecture document.** When the owner's `# Coordinator rules` declare that the product carries no architecture document, no rule of this playbook waits on `architecture.behind`. Call `release-delta <product-key> --no-architecture` and `release-scaffold --refresh <release-note> --no-architecture` in such a product: with the flag the verbs report nothing in `architecture.behind` even while an `architecture.md` file exists. Without an `architecture.md` file `release-delta` reports nothing behind on its own.

**`Start release`.** The product coordinator hangs this row on the product note while the delta is non-empty, no release is open, `architecture.behind` is empty and `conflicted` is empty (`lazy-spec.release-owner-playbook.md` § 2). On the tick it creates the release with `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> release-scaffold <product-key> --bump <part>` — the folder, the note with `spec_includes` filled from the delta, the version — and wakes this coordinator once with `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> coordinator-dispatch --release-start <release-note>`, the one downward hop a level ever makes. The `release-start` wake is where this playbook begins: reconcile the rows of the release note (below), rewrite `# Status brief` and write `spec_state` (Status brief, below). The wake dispatches no job.

**The version.** The product coordinator judges `<part>` itself, over the whole delta, in all three places — the asset types are a hint, not a rule; a delta of fixes is a patch, a delta that adds behaviour is a minor, a delta that breaks what consumers rely on is a major. The previous version is read from the manifest the product record names in `release.manifest` (`plugin.json`, `package.json`, `pyproject.toml`, `manifest.json`), else from the highest `spec_version` among the product's published releases, else the first release is `0.1.0`. The operator overrides the version with a line in the release note's `# Coordinator commands`; enact it with `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> release-version <release-note> --set <version>`, which also sets `spec_version_pinned`; from then on the operator's version outranks any recomputation — a `--bump` is a noop while the version is pinned — until the next command. The verb refuses on a published release: a published version is frozen. The version stands first in the note's description and in `# Status brief`.

## The build

A build is one implementation job, dispatched by this coordinator through the ordinary `dispatch-job` route (`lazy-spec.coordination-playbook.md` Chapter 5 — `target_doc` named, paths not copied, dedup by note path plus label), and it never starts on its own: the operator's tick on `Build` starts the first one, the tick on `Rebuild` every later one. Builds are numbered within the release from 1. Every run of the implementer or the tester opens its `#### build <k>` entry in `code-report.md` / `test-report.md`, `<k>` the `spec_build` value the dispatch names — the number the gates read (The gates of the build; Staging and tests, step 3).

**The note records the last build.** Every build start — the `Build` dispatch, and every build a `Rebuild` tick starts (Rebuild, below) — writes its keys through `note-set-key` on the same wake, after the dispatch: `spec_build`, the number of this build (the previous value plus one, `1` for the first), and `spec_build_at`, the moment of this build start; an implementation build also writes `spec_impl_build` and `spec_impl_build_at`, the same number and moment, while a test-only build (Rebuild, step 4) writes only `spec_build` and `spec_build_at`, so `spec_impl_build` keeps naming the build whose code stands. Every `Test` dispatch writes `spec_test_dispatched_at`, the moment of that dispatch (Staging and tests, below). Every dispatch under the label `Build` writes `spec_build_job`, and every dispatch under the label `Test` writes `spec_test_job`: the job id of that dispatch, written through `note-set-key` in the dispatch commit, right after `mark-job`. A `Rebuild` reason reads them to tell whether a failed job is the last one of its kind (Rebuild, below). The same wake that starts a build clears `spec_rebuild_owed`. A continuation of a build or of a test run changes none of these keys except `spec_build_job` / `spec_test_job`. Every moment is ISO 8601 UTC, `YYYY-MM-DDTHH:MM:SSZ`, taken with `date -u +%Y-%m-%dT%H:%M:%SZ`; `note-set-key` refuses any other shape. "The last build" everywhere in this playbook is the build `spec_build` names, "the last implementation build" the one `spec_impl_build` names, and "after the last build" means later than `spec_impl_build_at` for a design, a plan or a `ui-design.md`, and later than `spec_test_dispatched_at` for a test-only document (Rebuild, below).

**One job at a time.** Every `dispatch-job` against the release — a `Build`, a `Test`, the build a `Rebuild` tick owes, a continuation of the acceptance cycle — is followed at once by `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> mark-job <release-note> active '{"checkbox": "<label>", "expert": "<name>", "job_id": "<id>"}'`, the label `Build` or `Test`. While the note's `active_job` is set no second job is dispatched: the due one waits for the `job-done` wake (`lazy-spec.launch-checkbox-protocol.md` § Dispatch).

**The change list.** An implementation build after the first is handed the list of what changed since the last implementation build that stands: by default since `spec_impl_build_at`; after a `Build` job that ended `error`, `dead` or `cancelled`, or whose result never landed (`unlanded: true`) — a build whose branch never merged — since the last implementation build whose `spec_develop_done` closed and whose branch `build-<k>` merged into the product's main branch, or everything when the release has no such build. The first build gets no list: it builds everything.

**The dispatch order of a build.** For an implementation build: compute the change list (above), dispatch the job with that list, `mark-job` it, then write `spec_build_job`, `spec_build`, `spec_build_at`, `spec_impl_build` and `spec_impl_build_at`. A test-only build dispatches no implementation job and writes `spec_build` and `spec_build_at` alone (Rebuild, step 4).

**The plan comes first, or its waiver.** A build runs from an approved `code-plan.md`. The plan is waived in two ways only: a line in the owner's `# Coordinator rules` saying its releases carry no code plan, or this release's own `code-plan.md` at stage `cancelled`. An absent plan is neither: it holds the build until the operator ticks `Write code-plan` or declares the waiver. Call the plan **settled** when `code-plan.md` is `approved`, or waived either way.

**The build reads no contradictions.** Contradictions between documents are caught by the coherence check after approval (`lazy-spec.coordination-playbook.md` Chapter 19). An open conflict holds `Start release` on the product note; once the release is open it blocks neither the build nor the publication.

**One implementation job, no per-tool rows.** Label `Build`; the expert is the release implementer the coordinator resolves with `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> resolve-product release-implementer <product-key>` for the product that owns the release — the record's explicit `release.implementer` when set, else the first expert registered in `experts` from the product's `release.implementer_chain`, else from the repository's `spec.release.implementer_chain` (`lazy-spec.config-protocol.md`); a product chain replaces the repository chain entirely, and a chain with no registered expert yields no implementer. Source is `code-plan.md` when it is `approved`, else — the plan waived — the start documents of every included asset (a cancelled member left out); context is the product's `architecture.md` and `tech.md`, every included asset's folder (design, test cases, decisions; a cancelled member's folder left out), the product's guidelines for the implementer's role and its wildcard guidelines, and — inside an open release with earlier builds — the change list (above), handed over as an inline context file; `target_doc` is the release's `code-report.md`. **The journal travels with the job.** When `code-report.md` exists, its path is named in the `context` of every `Build` dispatch and of every continuation, and the job returns the whole journal: every earlier entry intact, plus the new `#### build <k>` entry. A dispatch that leaves the journal out gets back a journal holding only the new entry, and the landing overwrites the history with it. **Each build runs on its own branch.** The payload names `branch`, `spec/<product>/releases/<n>/build-<k>` — the release's own token by the rule of `lazy-spec.coordination-playbook.md` Chapter 8 (Branch as workspace), with `<k>` the number this build writes into `spec_build` and `spec_impl_build` — on this dispatch and on every continuation of the same build. The previous build's branch is already merged, so a build never reuses it. A `Build` dispatch without `branch` runs on the current checkout and commits straight into the base branch, so the field is never omitted.

**A failed build is still a build.** An implementer that cannot finish returns `outcome: error` and its `code-report.md` with the failed run's `#### build <k>` entry; the collector lands the journal all the same (`lazy-spec.expert-signals-protocol.md` § `outcome` values). On the `job-done` wake the finished job is read from `last_job` — the wake's payload `last_job`, or `job_markers.last_job` in the `note-check` answer, never `active_job`, which the poller has already cleared — `{checkbox, expert, job_id, outcome, marker}`, plus an optional `unlanded: true` on a job whose result never landed — one a cancel retired, a `done` job `gate-tick` dropped because the release was cancelled, or a job whose landing was refused: `outcome` is the job's own `response.json` `outcome` (the marker stands in when the job left no response naming one), `marker` is the job bundle's terminal marker lowercased (`done`, `dead`, `cancelled`), and the job's `response.json` carries the detail. `outcome` is the field that tells a failed job: `error`, `dead` or `cancelled` is a job that ended without a report to accept. On `outcome: error` the coordinator does not submit `code-report.md` into review: it names the failure in `# Status brief` from the journal entry, and the failed build is a `Rebuild` reason (Rebuild, below).

**Delegation is mandatory.** For every included asset the implementer reads `spec_tools`: the work of its own tool it does itself; for every foreign tool it launches a child agent with that tool's expert — the main writer of the review class named by the tool's `report_doc` (`lazy-spec.config-protocol.md`, `tool_types`) — hands it the asset's design and that tool's guidelines, and never writes that content itself. The implementer alone answers for assembling the result, for the product being in a consistent working state as a whole, and for `code-report.md`; a release carries no `data-report.md` and no `docs-report.md`. The implementer is responsible for the whole product, not for the delta: it builds the delta and brings the product to a working state entirely, but inside an open release it redoes only what the change list (above) names.

**Unit tests are the implementer's, inside this job.** The implementer writes the unit tests of the code it changes and runs them green before it reports; their run is journaled in `code-report.md`, and no test document stands between the design and that work. The unit-test framework and the command that runs it come from the product's `tech.md`, and where the tests sit and the seams they reach the code through come from `architecture.md`. The `test` tool, the tester and every `test-plan.md` cover a different thing — the deployed product (Staging and tests, below).

**The rows of a release note.** Reconciled on every wake like every other note's (`lazy-spec.coordination-playbook.md` Chapter 5); the `Write` rows run the seed-then-start flow every `Write` row runs (`lazy-spec.feature-playbook.md`, "Seed-then-start"). An absent `test-plan.md` is "no plan needed", and a release `test-plan.md` at stage `cancelled` counts as absent: the tester works without a release plan, and testing still runs. A cancelled plan does not end planning: `Write test-plan` hangs over it as over an absent file, and its tick seeds a fresh plan that replaces the cancelled file. Until that new plan is written the cancelled one still counts as absent, and `Test` may run without a release plan. Any other present plan, of either kind, is "intent to plan" and must clear review before the job that reads it is dispatched. An absent `code-plan.md` is never "no plan needed" (The build, above).

| Checkbox | Appears when | On tick |
|---|---|---|
| `Write code-plan` | the release is open AND `code-plan.md` doesn't exist AND the owner's `# Coordinator rules` do not waive the code plan | seed `code-plan.md:code-plan`, then the seed-then-start flow |
| `Build` | the release is open AND no build has been dispatched in it yet (no `spec_build`) AND the plan is settled (The build, above) AND `release-delta` reports `architecture.behind` empty, or the owner's `# Coordinator rules` declare no architecture document (Rebuild, "Before the first build") | dispatch the implementation job (The build, above) |
| `Write test-plan` | the release is open AND `test-plan.md` doesn't exist AND the owner's `# Coordinator rules` do not waive testing AND no `Test` job has been dispatched for the current build yet (Staging and tests, below); a `test-plan.md` at stage `cancelled` counts as not existing here, so the row hangs over it too. After a `Rebuild` the row hangs again for each new build, until that build's `Test` is dispatched | seed `test-plan.md:test-plan` — over a `cancelled` file with `--replace-cancelled`, which replaces it — then the seed-then-start flow |
| `Test` | the release is open AND `spec_develop_done` closed AND the staging deploy of the current build succeeded, or no `staging` is declared AND no `Test` job has been dispatched for the current build yet AND the owner's `# Coordinator rules` do not waive testing AND the release's `test-plan.md` is absent, `cancelled` or `approved` (Staging and tests, below) | dispatch the tester job (Staging and tests, step 2) |
| `Rebuild` | the release is open AND a first build has been dispatched (`spec_impl_build_at` is set) AND `spec_rebuild_owed` is not set AND at least one reason of Rebuild (below) holds — and, for a reason that is a new or re-approved design, only once `release-delta` reports `architecture.behind` empty, or at once when the owner's `# Coordinator rules` declare no architecture document | `release-scaffold --refresh`, the version recomputed upward, the source-table rollback, the next build once the plan is settled (Rebuild, below) |
| `Publish` | the release is open AND `spec_built` closed AND `spec_released` still false AND `spec_rebuild_owed` is not set AND — a `staging` declared, whether or not testing is waived — the latest staging-deploy line for exactly the current `spec_build` is a success | `release-publish` (below) |

A `Write` row is named after the document's stem, never its file name: `Write code-plan`, `Write test-plan`. Only a `Review <file>.md` row carries the extension, and `# Status brief` names every row exactly as it hangs.

**The gates of the build.** `spec_plan_done` closes once the plan is settled: `code-plan.md` is `approved` or `cancelled`, or the owner's `# Coordinator rules` waive the code plan. An absent plan without that waiver keeps it open. `spec_develop_done` closes once `code-report.md` is accepted — its `review_result` reads `approved` or `approved-with-concerns` and its `review_active` is not `true` — while the journal holds the `#### build <spec_impl_build>` entry, and the branch `build-<spec_impl_build>` (The build, above) is merged into the product's main branch by the same route a code job's branch merges today. A report journal carries no stage and no approval moment, so its verdict is never compared with a build key: `lazy-review.submit` clears an older verdict when the build's report goes into review, and a verdict present after that submit belongs to that build. `spec_tests_passing` and `spec_built` are this ladder's too (Staging and tests, below). All four are derived: flip each with `flip-gate --auto` the moment its condition holds, and back off with `--off --auto` the moment it stops holding. Each closes only while the gate before it on the ladder is closed: `spec_develop_done` only while `spec_plan_done` is, `spec_tests_passing` only while `spec_develop_done` is, `spec_built` only while `spec_tests_passing` is. A plan returned to `draft` therefore keeps every later gate down, even while the earlier build's report and branch would satisfy them.

**The acceptance cycle** is the `code` tool's (`lazy-spec.tool-code-playbook.md`): a reviewer's comment on `code-report.md` means redo the work; the redo is a continuation to the same implementer on the same build branch, with `code-report.md` named in its `context`; the journal is append-only.

## Staging and tests

This stage tests the deployed product, never the code in isolation: the unit tests were written and run inside the build (The build, above), and the tester neither writes nor repeats them.

Once `spec_develop_done` is closed, the staging deploy runs once per build number on its own, and the tester at most once per build number, on the operator's `Test` tick. `# History` is the record: the staging deploy of build `<k>` leaves the line `release-deploy --build <k>` writes, naming the build, and the `Test` dispatch of build `<k>` the one `note-history` line you land naming the build; a build whose number already carries a line gets that step never again, on any later wake.

1. When the product record declares `release.deploy.staging`, run `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> release-deploy <release-note> staging --build <k>`, `<k>` the value of `spec_build`. The verb runs the target's command, keeps its output in a log file and writes the outcome, naming the build, to the release's `# History`; that line is the deploy's once-per-build record, and you land no line of your own for it. A failed deploy stops here: name it in `# Status brief` and hang no `Test` row; the failed deploy is a `Rebuild` reason as soon as it fails (Rebuild, below), and the build that tick starts deploys again.
2. The `Test` row hangs once the staging deploy of build `<k>` succeeded — at once when no `staging` is declared — while no `Test` job has been dispatched for build `<k>` and the release's `test-plan.md` is absent, `cancelled` or `approved`; a present plan not yet approved keeps the row down, and `# Status brief` says so. The coordinator never dispatches the tester without that tick. On the tick dispatch the tester — label `Test`; the expert is the main writer of the `test-report` review class; source is the release's `test-plan.md` when it exists and is not `cancelled`, else the included assets' start documents and their test cases; context is the product's root `test-plan.md`, the included assets' folders, the product's guidelines for the tester's role and its wildcard guidelines, the `staging` address when the target declares one, and `test-report.md` when it exists; a cancelled member is left out of both lists; `target_doc` is the release's `test-report.md`. The job returns the whole journal: every earlier entry intact, plus the new `#### build <k>` entry. The payload names `branch`, `spec/<product>/releases/<n>/test-<k>`, with `<k>` the build number, and every continuation of that run — a redo after a reviewer's comment — passes the same `branch` and names `test-report.md` in its `context` again. The tester tests the product against `staging`, or against a local instance it brings up itself inside the job when no `staging` is declared, and records the run as `#### build <k>`. Right after the dispatch, `mark-job` the job with the label `Test` (The build, "One job at a time"), write `spec_test_job` and `spec_test_dispatched_at` through `note-set-key`, and land the `note-history` line naming the build.
3. `spec_tests_passing` closes once `test-report.md` is accepted — its `review_result` reads `approved` or `approved-with-concerns` and its `review_active` is not `true` — while the journal holds the `#### build <spec_build>` entry, the run of the current build, and that entry is green — the `test` tool's own rule (`lazy-spec.tool-test-playbook.md`); `lazy-review.submit` clears an older verdict when the run's report goes into review, so a verdict present after that submit belongs to that run. It is derived: flip it with `flip-gate --auto`, and back off with `--off --auto`. A red run is an ordinary outcome: the report records it, `# Status brief` names the failing cases, and a red run accepted by review is a `Rebuild` reason — a defect found here is fixed by the implementer in the next build, never by the tester.
4. `spec_built` is derived: flip it with `flip-gate --auto` once `spec_tests_passing` is closed and the branch `build-<spec_impl_build>` is merged, and back off with `--off --auto` the moment either stops holding. There is no operator gesture for it. The one tick the operator has is `Publish` (below).

Every release is tested by default. A product may waive testing, as it may waive any other step, with a line in its `# Coordinator rules`. Then neither `Write test-plan` nor `Test` hangs, no tester job is dispatched, and the release's `spec_tests_passing` closes together with `spec_develop_done`. A declared `staging` deploy still runs, and `Publish` hangs only once the staging deploy of the current build has succeeded; a failed one hangs `Rebuild` instead (Staging and tests, step 1).

## Rebuild

An open release is never rebuilt on its own. On every wake check the reasons — a design, a plan or a `ui-design.md` read against `spec_impl_build_at`, a test-only document against `spec_test_dispatched_at`:

- the delta holds an approved asset not yet in `spec_includes`;
- an included asset's start document was re-approved after `spec_impl_build_at`;
- an included asset's `ui-design.md` is new or re-approved after `spec_impl_build_at`;
- an included asset's `test-plan.md` is new or re-approved after `spec_test_dispatched_at` — before the current build's `Test` dispatch the new or re-approved test cases simply feed that `Test`;
- the release's own `code-plan.md` was re-approved after `spec_impl_build_at`;
- the release's own `test-plan.md` was re-approved after `spec_test_dispatched_at` — before the last build's `Test` dispatch the re-approved plan simply feeds it;
- the last `Build` or `Test` job ended without an accepted report — `last_job.outcome` is `error`, `dead` or `cancelled`, or `last_job` carries `unlanded: true`, whatever its `outcome` — while no job is active (`active_job` unset) and `last_job.job_id` equals `spec_build_job` for a `Build`, `spec_test_job` for a `Test` — for a `Test` only while `spec_test_dispatched_at` is later than `spec_build_at`, so a test-only rebuild that has just started a new build number does not hang the row again for the run of the build before it. A job that died (`dead`) has also halted the release (`spec_halted`, by `gate-tick`): the row hangs on nothing while the halt stands, and the `dead` reason surfaces on the first wake after the operator lifts it. A refused landing marks the job `unlanded: true` and halts the release the same way, and its reason too surfaces once the halt is lifted. The reason's kind is `last_job.checkbox`: a `Build` job needs an implementation build, a `Test` job is test-only;
- the last build's test run is red and accepted by review;
- the latest staging deploy line for the current build (`spec_build`) in `# History` is a failure.

Any one of them hangs the `Rebuild` row on the release note, and `# Status brief` names each of them. A re-approval wakes this note on its own: a `review_result` turning approved on a stage-bearing document of a member of the open release raises `release-start` on this note, and a re-approved start document also raises `asset-approved` on the owner's level note, though no gate crossed — a re-approval is a restamp of `spec_approved_at`, the stage staying `approved`. Four of them are test-only: a new or re-approved test-cases document of an included asset, the release's own `test-plan.md` re-approved, a failed or unlanded `Test` job, and a failed staging deploy; every other reason needs an implementation build. While `spec_rebuild_owed` is set the row does not hang: a ticked `Rebuild` is still waiting for its plan (step 4, below), and a plan re-approval that settles that owed build is not a reason. The release's own plans are the reason it never publishes a build made from a plan that has since changed. Test cases and the UI design of an included asset stay open to writing and re-approval during the release; `Rebuild` is how they reach the next build, with no `change` needed. A new or re-approved design reaches `Rebuild` through the architecture: while `release-delta` reports the asset in `architecture.behind`, the row does not hang for it, `# Status brief` says the release waits for `Revise architecture` on the product note, and the product coordinator wakes this note with `--release-start` on the wake where the revised `architecture.md` is approved (`lazy-spec.release-owner-playbook.md` § 4). When `release-delta` reports `architecture.behind` empty — the product has no `architecture.md` file, or its `# Coordinator rules` waive the architecture and the call carries `--no-architecture` — there is no such wait: the product coordinator wakes this note with `--release-start` on the `asset-approved` wake of an approved asset that is not a member (`lazy-spec.catalog-playbook.md` § 5). **Before the first build there is no `Rebuild`.** A reason that arises while no build has been dispatched (`spec_impl_build_at` unset) hangs no `Rebuild` row and needs no tick; the coordinator acts on it on the wake it sees it. With no build keys yet, "re-approved after" is read against the `spec_approved_at` of each approved release plan the document feeds: a start document, a design or a `ui-design.md` approved after an approved `code-plan.md` or `test-plan.md` is a reason for that plan, a test-cases document approved after the approved `test-plan.md` is a reason for `test-plan.md`, and the product's `architecture.md` approved after an approved `code-plan.md` is a reason for `code-plan.md`. An approved delta asset not yet in `spec_includes` enters it on that wake through steps 1–3 below — `release-scaffold --refresh`, the version recomputed upward, the rollback of the approved plans to the writer round — with no `spec_rebuild_owed` set and no build started; every other reason returns the affected approved plan to `draft` as step 3 does — its sources derived again, its review opened at the writer round. `Build` stays down until the plan is settled again (The build, above), and while `release-delta` reports `architecture.behind` non-empty: no first build is made from designs the product's architecture has not caught up with. A product whose `# Coordinator rules` declare no architecture document is exempt from that hold (The architecture is the product's, above). Without the tick the release stands as built, and everything new waits for either `Rebuild` or the next release. `Rebuild` and `Publish` may hang side by side: `Publish` ships what was built and tested, `Rebuild` pulls the new approvals in.

On the tick, set `spec_rebuild_owed` to `true` through `note-set-key`, then:

1. `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> release-scaffold --refresh <release-note>` adds the new delta members to `spec_includes` and drops nobody already listed; in a product whose `# Coordinator rules` declare no architecture document, add `--no-architecture`.
2. Recompute the version over the full composition, upward only: when the delta as it now stands warrants a higher part than the one the release carries, `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> release-version <release-note> --bump <part> --product <product-key>`; an operator-set version is left alone — while `spec_version_pinned` is set the `--bump` call is a noop.
3. Roll back only what the reasons touched. A plan returns to `draft` only from `approved` — a `cancelled` `code-plan.md` is the plan's waiver and stays. Every returned plan has its sources derived again from the release as it now stands — `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> seed-doc --refresh-sources <plan>`, which rewrites the plan's `spec_source_docs` and `## Docs` list from the current `spec_includes` by the same rule `seed-doc` applied when it seeded the plan — and then its review opened at the writer round at once, `Skill(lazycortex-review:lazy-review.start, "<plan>")`; a returned `code-plan.md` also turns `spec_plan_done` off, `flip-gate <release> spec_plan_done --off --auto`. Per reason:
   - a newly included asset, a re-approved start document, or a new or re-approved `ui-design.md`: both release plans return to `draft`, and `spec_develop_done`, `spec_tests_passing` and `spec_built` turn off;
   - a new or re-approved test-cases document: the release's `test-plan.md` returns to `draft`, and `spec_tests_passing` and `spec_built` turn off;
   - the release's own re-approved `code-plan.md` turns `spec_develop_done`, `spec_tests_passing` and `spec_built` off, its own re-approved `test-plan.md` turns `spec_tests_passing` and `spec_built` off, and the plan itself stays `approved`: it is the plan the next build runs from;
   - a red accepted test run turns `spec_develop_done` off;
   - a failed or unlanded `Build` or `Test` job or a failed staging deploy turns nothing off beyond what is already open.
4. Start the next build of the same folder. The `Rebuild` tick is the operator's go-ahead for it, and `spec_rebuild_owed` carries that go-ahead across wakes. An un-cancel that set `spec_rebuild_owed` (Cancellation, below) owes this step with no tick: its reason is the unlanded `last_job` the cancel retired, so a `Build` job owes an implementation build and a `Test` job a test-only one. When at least one reason needs an implementation build, dispatch the implementation job (The build, above) on this wake once the plan is settled after the rollback; when the rollback returned `code-plan.md` to `draft`, dispatch it on the wake where the plan is settled again, with no second tick; while `active_job` is set — a continuation or a `Test` still running — the owed build waits for its `job-done` wake. The implementer gets the change list (The build, "The change list") — measured from the last build that closed and merged when a failed or unlanded `Build` job is among the reasons — and the dispatch writes all four build keys (The build, "The dispatch order of a build"). When every reason is test-only, no implementation job runs and the code of the last implementation build stands. Start the build on the wake where a returned `test-plan.md` is `approved` again — or on this wake when none was returned — by writing `spec_build` and `spec_build_at` alone, never `spec_impl_build` or `spec_impl_build_at`, and clearing `spec_rebuild_owed`, and its staging deploy runs under the new number and the `Test` row hangs again for it (Staging and tests, above); the rebuild dispatches no tester itself.

## Release and Publish

The `Publish` row hangs once `spec_built` is closed and `spec_released` is still false. The row carries no hint of its own. When the target declares a `staging` address, `# Status brief` names it as the place to check the build before publishing.

On the tick run `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> release-publish <release-note>`. The verb refuses a cancelled release, one whose `spec_plan_done` is not `true`, one whose `spec_develop_done`, `spec_tests_passing` or `spec_built` is not closed, one whose `spec_rebuild_owed` is set, one whose product declares `staging` while the latest staging-deploy line for exactly the current `spec_build` is not a success — no such line, or a later failure — whether or not testing is waived, and, before any review stop or deploy, one whose product names a manifest whose version cannot be replaced unambiguously (the version missing, repeated or not a string, or the file not valid JSON). A refusal leaves nothing behind: a review the verb already stopped gets its bytes back and its wake raised again, and nothing is left uncommitted. It publishes exactly the `spec_includes` that was built and tested, passing over a member cancelled since it was included; everything approved after `spec_impl_build_at` waits for the next release. When the product declares `release.deploy.production` the verb deploys there first: a failed deploy writes one line to the release's `# History`, changes nothing else, and the `Publish` row returns for a retry once the operator has looked at the log. A publish whose commit fails after a successful production deploy rolls the publish commit back and commits that deploy's `# History` line alone; the error result carries `"deployed": true`, `# Status brief` names it, since production already runs the build, and a later `Publish` deploys production again. On success — or at once, when no `production` target is declared — the verb stops every review still open in the release folder and, on each member of `spec_includes`, compares against `spec_impl_build_at`: a cancelled member is skipped; a member whose start document is not `approved`, or whose start document or `ui-design.md` was approved after `spec_impl_build_at`, gets the version tag and keeps `spec_released` false — a re-approved member whose note reads `spec_design_done: true` is painted `awaiting-release`, and every other such member keeps the `spec_state` its own coordinator painted; every other member gets `spec_released: true` with its moment and the version tag. It sets `spec_released: true` with its moment on the release, whose own `spec_built` closed before the row hung (Staging and tests, step 4), writes the version into the manifest when the product names one, and lands the whole set in one commit. Its answer on success is `{"outcome": "published", "version", "assets", "reapproved", "unbuilt", "cancelled", "manifest"}`: `assets` the members released, `reapproved` the members tagged but left unreleased because a later approval was not built, `unbuilt` the members tagged but left unreleased, in the state their own coordinator painted, because their start document is missing, not approved or carries no `spec_approved_at`, so their change was never built, `cancelled` the members skipped; `deploy-failed` and `refused` carry their own keys (`target`, `exit_code`, `log`; `reason`). The release is frozen from that commit on: its version, its members and its documents never change again, `review-rows` hangs no row on it, and any later edit, however small, goes into the next release.

Publication wakes the owner's level note once, after the publish commit, with `release-published` (`lazy-spec.catalog-playbook.md` § 5): it only recomputes the delta, hangs or takes down `Start release` and rewrites the product's `# Status brief`. Each member the publish wrote gets one `release-member` wake on its own note, which only re-reads its state and rewrites its `# Status brief` and `spec_state` (`lazy-spec.coordination-playbook.md` § 1). Nothing else is woken: the product's `design.md` is the intent the build was made against, and contradictions between documents are caught by the coherence check after approval (`lazy-spec.coordination-playbook.md` Chapter 19). An included asset whose start document or `ui-design.md` was approved after `spec_impl_build_at` ships its tested old design: it gets this version's tag but keeps `spec_released` false and, its note reading `spec_design_done: true`, stands in `awaiting-release` with its new design, for the next release.

## Cancellation

An operator cancels a release like any asset, through `spec_cancelled` on its note; a cancelled release is closed, blocks no new release, and its members return to `awaiting-release`. The cancelling call, `flip-gate <release> spec_cancelled`, first stops the review of every document in the release folder, then moves every staged one to `cancelled`, stripping each moved document's `#status/<state>` callout through the review plugin's `strip-status` verb (no commit), repaints the members with `spec_design_done: true` `awaiting-release` and clears the note's `pending_wake`, and cancels a running build or test job last, all in the same commit, so no document of a cancelled release waits for an approval and no job of it lands (`lazy-spec.doc-stage-protocol.md` § Transitions); a job the cancel kills is recorded as `last_job` with `outcome: cancelled`; each repainted member then gets a `release-member` wake. When a review cannot be stopped or the job cannot be cancelled, the whole cancel is refused with nothing written: the reviews already stopped in the call get their bytes back and their wakes raised again, nothing is left uncommitted, and the release stays open as it was. A cancel refused or crashed after it has already killed the job leaves `active_job` null, that job recorded as `last_job` with `outcome: cancelled`, and `pending_wake: job-done` raised on this note, so the coordinator sees the job gone; the result names it as `killed_job`. A failed `cancel-sweep` keeps the job retired the same way, without a wake. A job the cancel retired without landing carries `unlanded: true` in `last_job`, and the cancel stamps that record `retired_by_cancel: true` — the mark that this cancel, not an earlier failure, left the job unfinished. The cancel is refused the same way on a published release and on a release under `releases/archive/`. The flip of `spec_cancelled` wakes this note once more. On that wake the coordinator takes the rows down and leaves `spec_state` describing the work as the coordination playbook prescribes for `spec_cancelled`. It sends no hop itself: the crossing of `spec_cancelled` raises on the owner's level note the same `asset-approved` hop an asset's cancellation raises (`coordinator_dispatch.py`), so the product recomputes the delta and hangs `Start release` again. `spec_cancelled` is written only through `flip-gate`; a crossing the verb did not make is repaired as the coordination playbook says (`lazy-spec.coordination-playbook.md` § 4, "A cancel the verb did not make"). The product coordinator cancels a release itself, through the same `flip-gate` call, when every member of its `spec_includes` is cancelled or released (`lazy-spec.catalog-playbook.md` § 5). The next release computes its version afresh from the last published version (Creation, above), never from the cancelled one. A published release is never cancelled. The operator lifts a cancellation with `flip-gate <release> spec_cancelled --off`: it returns each document the cancel marked to the stage the cancel recorded — `empty`, `deferred` and `rejected` back as they were, `draft` staying `draft`, `approved` to `draft` with its review opened at the writer round — resumes the reviews it marked, turns off every derived gate whose document it took out of `approved` — a `code-plan.md` taken out of `approved` turns off `spec_plan_done`, `spec_develop_done`, `spec_tests_passing` and `spec_built`, a `test-plan.md` alone `spec_tests_passing` and `spec_built` — sets `spec_rebuild_owed` only when `last_job` is the job this cancel retired — it carries `retired_by_cancel: true` and `unlanded: true`, and its `job_id` equals `spec_build_job` or `spec_test_job` — and drops the `retired_by_cancel` stamp, so the build or test run that job never finished is owed and starts with no second tick — that `last_job` is the `Rebuild` reason the owed build runs on, an implementation build for a `Build` job and a test-only one for a `Test` job (Rebuild, step 4); an earlier unlanded failure — a refused landing, a dead job — carries no stamp, owes nothing on the un-cancel, and keeps waiting for the operator's `Rebuild` tick — wakes this note's coordinator, repaints the members with `spec_design_done: true` `in-release` and wakes each of them with `release-member`, and the release is open again; the flip wakes the owner's level note with the same `asset-approved` hop. The un-cancel is refused, with nothing written, while another release of the same owner is open, and on a release that sits under `releases/archive/`. `spec_halted: true` takes every row down and dispatches nothing new — no build, no deploy, no `Test` — and touches neither the gates nor `# Coordinator commands`. A job already running is not stopped: it finishes and lands, and its `job-done` wake waits until the halt is lifted.

## Status brief

Rewrite `# Status brief` on every wake, the version on the first line, then the rung and the last build: "1.5.0 — build 2 tested on staging, waiting for `Publish`". Name the `staging` address when there is one, what waits for the operator (`Build`, `Test`, `Publish`, `Rebuild`, a failed deploy's log, a present `test-plan.md` not yet approved that keeps `Test` down, a halt raised by a `Build` or `Test` job that died — the `dead` job becomes a `Rebuild` reason only once the operator lifts the halt), and what waits outside the release — the approvals that would come in on `Rebuild`, the assets held back from the delta and why. The product note's own brief mirrors the current release's state the same way (`lazy-spec.catalog-playbook.md` § 7).

`spec_state` follows the table of `lazy-spec.coordination-playbook.md` Chapter 11 as it stands for every asset, read top to bottom: `waits-operator` while any of the rows `Write code-plan`, `Build`, `Test`, `Rebuild` or `Publish` hangs unticked, or a `Review <doc>` row of a document that is not `approved` hangs, or a `[!question]` is open; a `Review <doc>` row of an `approved` document, the `## Re-review` group, does not count toward it, and neither does the optional `Write test-plan` — the release is tested without a release plan when nobody ticks it; otherwise `in-review` while a plan or a report is in review, `implementation` while a build runs, `testing` while the tester job a `Test` tick dispatched runs, `done` only after publication. A release that was just opened hangs `Write code-plan`, or `Build` when the code plan is waived, beside the optional `Write test-plan`, and is `waits-operator`, never `implementation`: no build runs in it yet, and the release template seeds that value. The iconize registry paints the release folder from it.
