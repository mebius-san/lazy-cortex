# Release type playbook — the product's unit of implementation

This document is the law for `spec.coordinator` on any status folder-note carrying `spec_asset_type: release`. Every other asset type is design-only: its ladder ends at the approval of its start document, and everything that turns approved designs into a working product — the plan, the code and data and documentation, the tests, the deploy, the version — happens here, inside a release. One release is open per product at a time, and one implementer answers for the whole product inside it.

## What this type is

`spec_asset_type: release` lives under `releases/` of the product that owns releases — the outermost product in its chain whose record declares a `source` (`lazy-spec.config-protocol.md`). The folder and the note are the release's sequence number with leading zeros: `releases/001/001.md`, `releases/002/002.md`. The folder is never renamed; the version is a key, not a name.

The note is an ordinary `status` note with the full ladder — `spec_design_done` (true from creation: a release has no design of its own), `spec_plan_done`, `spec_develop_done`, `spec_tests_passing`, `spec_built`, `spec_released`, plus `spec_cancelled` — and two keys of its own: `spec_version`, a bare SemVer such as `1.5.0`, mirrored by the tag `release/1-5-0`; and `spec_includes`, the wikilinks to the status notes of the assets the release carries. A release is **open** while `spec_released` and `spec_cancelled` are false; a published or cancelled release is closed and never changes again.

Documents of the release folder, all opt-in on disk: `code-plan.md` (`code-plan`, the planner's), `test-plan.md` (the `test` tool's plan — the tester's composed plan from the product's standing `test-plan.md`, the included assets' test cases and the regression), `code-report.md` and `test-report.md` (append-only journals, one `#### build <n>` entry per run), `decisions.md`, and flat attachments such as build logs. The product's own `architecture.md` and `test-plan.md` sit at the product root and belong to the product coordinator; a release reads them and the architect revises the first one, but the release folder never carries a copy.

`<specs-cli>` stands for the specs plugin's `bin/lazycortex-specs` file — the copy under `~/.claude/plugins/cache/lazycortex/lazycortex-specs/<version>/` that `~/.claude/plugins/installed_plugins.json` records as installed, or `plugins/claude/lazycortex-specs/` in a checkout that authors the plugin. Every verb runs through the interpreter, `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> <verb>`: the file carries no exec bit and is not on `PATH`.

## Creation

Nothing creates a release on its own. An asset's approval — its `spec_design_done` or `spec_cancelled` changing value, either way — sends the owner's level note an `asset-approved` hop that re-hangs rows, rewrites the product's `# Status brief` and at most cancels an open release whose delta has emptied (`lazy-spec.catalog-playbook.md` § 5); the operator decides when a release starts.

**The delta.** `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> release-delta <product-key>` lists what the next release would carry: every asset of the owner and of the design-only products nested under it, of any type but `release` and `research`, whose start document is `approved`, whose `spec_released` and `spec_cancelled` are false, and — for a `change` — whose `spec_cascade_done` is true. The same call names what is held back and why (`cascade-pending`, `no-start-doc`) and the open release, if any. The order of work inside the release is the implementer's.

**`Start release`.** The product coordinator hangs this row on the product note while the delta is non-empty and no release is open. On the tick it creates the release with `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> release-scaffold <product-key> --bump <part>` — the folder, the note with `spec_includes` filled from the delta, the version — and wakes this coordinator once with `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> coordinator-dispatch --release-start <release-note>`, the one downward hop a level ever makes. The `release-start` wake is where this playbook begins: start the first build (below).

**The version.** The product coordinator judges `<part>` itself, over the whole delta, in all three places — the asset types are a hint, not a rule; a delta of fixes is a patch, a delta that adds behaviour is a minor, a delta that breaks what consumers rely on is a major. The previous version is read from the manifest the product record names in `release.manifest` (`plugin.json`, `package.json`, `pyproject.toml`, `manifest.json`), else from the highest `spec_version` among the product's published releases, else the first release is `0.1.0`. The operator overrides the version with a line in the release note's `# Coordinator commands`; enact it with `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> release-version <release-note> --set <version>`, and from then on the operator's version outranks any recomputation until the next command. The verb refuses on a published release: a published version is frozen. The version stands first in the note's description and in `# Status brief`.

## The build

A build is two steps in sequence, dispatched by this coordinator through the ordinary `dispatch-job` route (`lazy-spec.coordination-playbook.md` Chapter 5 — `target_doc` named, paths not copied, dedup by note path plus label). Builds are numbered within the release from 1; every run of the implementer or the tester opens its `#### build <n>` entry in `code-report.md` / `test-report.md`.

**1. The architect revises the product's architecture against the delta.** The first step runs once per build, on the `release-start` wake after `Start release` or after a `Rebuild` tick, over every included asset at once. It is one job: label `Revise architecture`; the expert is the main writer of the `system-architecture` review class; source is the product's root `architecture.md`, context is every included asset's folder (its design first) and the product's `tech.md`; `target_doc` is the product's `architecture.md`. A product that declared in its `# Coordinator rules` that it carries no architecture document skips this step.

The job returns the document unchanged or revised. Unchanged means the architecture already covers the delta. A revised document lands on the product root through the job-done collector, as any job result does, and re-enters review (Chapter 6): it is the product coordinator's from the moment it lands. On the wake where its review reaches a verdict, the product coordinator wakes this note once more with `--release-start`. Every wake of this note, whatever its trigger — `release-start`, a job's `DONE`, a review verdict, an operator edit, a command — reads where the current build stands before it decides anything: whether the build's first step is still pending or done, and the architecture's verdict. A build with no first step yet runs the first step; a first step whose job has finished with the architecture unchanged or its revision `approved` goes on to the implementation job; a rejected revision cancels the build (below); any other state waits for the next wake. Never re-dispatch the first step of a build that already ran it.

This step does not look for contradictions between the product's documents and the assets' documents: contradictions between documents are caught by the coherence check after approval (`lazy-spec.coordination-playbook.md` Chapter 19), and a conflict blocks neither the build nor the publication.

**A reject cancels the build.** When the operator rejects the revised `architecture.md` (`review_result: rejected`), the build is cancelled: the implementation job is not dispatched, the release stays open, the `Rebuild` row hangs on the release note again, and `# Status brief` names the rejected document. There is no rollback: the next `Rebuild` starts with the architect again.

**2. One implementation job, no per-tool rows.** Label `Build`; the expert is the release implementer the coordinator resolves with `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> resolve-product release-implementer <product-key>` for the product that owns the release — the record's explicit `release.implementer` when set, else the first expert registered in `experts` from the product's `release.implementer_chain`, else from the repository's `spec.release.implementer_chain` (`lazy-spec.config-protocol.md`); a product chain replaces the repository chain entirely, and a chain with no registered expert yields no implementer. Source is `code-plan.md` when it exists, else the start documents of every included asset; context is the product's `architecture.md` and `tech.md`, every included asset's folder (design, test cases, decisions), the product's guidelines for the implementer's role and its wildcard guidelines, and — inside an open release with earlier builds — the list of what changed since the last build, handed over as an inline context file, with the earlier builds' entries already in `code-report.md`; `target_doc` is the release's `code-report.md`. The job runs on its own branch.

**Delegation is mandatory.** For every included asset the implementer reads `spec_tools`: the work of its own tool it does itself; for every foreign tool it launches a child agent with that tool's expert — the main writer of the review class named by the tool's `report_doc` (`lazy-spec.config-protocol.md`, `tool_types`) — hands it the asset's design and that tool's guidelines, and never writes that content itself. The implementer alone answers for assembling the result, for the product being in a consistent working state as a whole, and for `code-report.md`; a release carries no `data-report.md` and no `docs-report.md`. The implementer is responsible for the whole product, not for the delta: it builds the delta and brings the product to a working state entirely, but inside an open release it redoes only what changed since the last build.

**Unit tests are the implementer's, inside this job.** The implementer writes the unit tests of the code it changes and runs them green before it reports; their run is journaled in `code-report.md`, and no test document stands between the design and that work. The unit-test framework and the command that runs it come from the product's `tech.md`, and where the tests sit and the seams they reach the code through come from `architecture.md`. The `test` tool, the tester and every `test-plan.md` cover a different thing — the deployed product (Staging and tests, below).

**The rows of a release note.** Reconciled on every wake like every other note's (`lazy-spec.coordination-playbook.md` Chapter 5); the `Write` rows run the seed-then-start flow every `Write` row runs (`lazy-spec.feature-playbook.md`, "Seed-then-start"). An absent plan is "no plan needed"; a present one is "intent to plan" and must clear review before the job that reads it is dispatched.

| Checkbox | Appears when | On tick |
|---|---|---|
| `Write code-plan` | the first step is settled for this build AND `code-plan.md` doesn't exist | seed `code-plan.md:code-plan`, then the seed-then-start flow |
| `Write test-plan` | `spec_develop_done` closed AND `test-plan.md` doesn't exist AND the owner's `# Coordinator rules` do not waive testing (Staging and tests, below) | seed `test-plan.md:test-plan`, then the seed-then-start flow |
| `Rebuild` | the delta holds an asset not in `spec_includes`, an included asset's start document was re-approved after the last build, an included asset's `test-plan.md` or `ui-design.md` is new or re-approved since the last build, the release's own `code-plan.md` or `test-plan.md` was re-approved after the last build, or the operator rejected the revised `architecture.md` of the build's first step (above) | `release-scaffold --refresh`, the version recomputed upward, the source-table rollback, the next build |
| `Publish` | `spec_built` closed AND `spec_released` still false | `release-publish` (below) |

**The gates of the build.** `spec_plan_done` closes once the first step is settled for this build (the architecture returned unchanged, or its revision `approved`) and `code-plan.md` is absent, `approved` or `cancelled`. `spec_develop_done` closes once `code-report.md` is accepted by review (approved-with-concerns counts) and the job branch is merged into the product's main branch by the same route a code job's branch merges today. Both are derived: flip them with `flip-gate --auto` the moment the condition holds, and back off with `--off --auto` the moment it stops holding.

**The acceptance cycle** is the `code` tool's (`lazy-spec.tool-code-playbook.md`): a reviewer's comment on `code-report.md` means redo the work; the redo is a continuation to the same implementer on the same branch; the journal is append-only.

## Staging and tests

This stage tests the deployed product, never the code in isolation: the unit tests were written and run inside the build (The build, above), and the tester neither writes nor repeats them.

Once `spec_develop_done` is closed:

1. When the product record declares `release.deploy.staging`, run `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> release-deploy <release-note> staging`. The verb runs the target's command, keeps its output in a log file and writes the outcome to the release's `# History`. A failed deploy stops here: name it in `# Status brief` and dispatch no tester; the operator fixes the target and the next build redeploys.
2. Dispatch the tester by rule, without a tick — label `Test`; the expert is the main writer of the `test-report` review class; source is `test-plan.md` when it exists, else the included assets' start documents and test cases; context is the product's root `test-plan.md`, the included assets' folders, the product's guidelines for the tester's role, and the `staging` address when the target declares one; `target_doc` is the release's `test-report.md`. The tester tests the product against `staging`, or against a local instance it brings up itself inside the job when no `staging` is declared, and records the run as `#### build <n>`.
3. `spec_tests_passing` closes once `test-report.md` is green AND accepted by review — the `test` tool's own rule (`lazy-spec.tool-test-playbook.md`). A red run is an ordinary outcome: the report records it, `# Status brief` names the failing cases, and the next build is the implementer's — a defect found here is fixed by the implementer in the next build, never by the tester.
4. `spec_built` closes by itself once `spec_tests_passing` is closed and the build's branch is merged: there is no operator gesture for it. The one tick the operator has is `Publish` (below).

Every release is tested by default. A product may waive testing, as it may waive any other step, with a line in its `# Coordinator rules`. Then no tester job is dispatched, and the release's `spec_tests_passing` closes together with `spec_develop_done`. A declared `staging` deploy still runs, and `Publish` hangs after it.

## Rebuild

An open release is never rebuilt on its own. On every wake compare the delta against `spec_includes`: an approved asset not yet listed, an included asset whose start document was re-approved after the last build, an included asset whose `test-plan.md` or `ui-design.md` is new or re-approved since the last build, or the release's own `code-plan.md` or `test-plan.md` re-approved after the last build, hangs the `Rebuild` row on the release note, and `# Status brief` names each of them. The release's own plans are the reason it never publishes a build made from a plan that has since changed. Test cases and the UI design of an included asset stay open to writing and re-approval during the release; `Rebuild` is how they reach the next build, with no `change` needed. A build cancelled by a reject in its first step hangs `Rebuild` too (The build, above). Without the tick the release stands as built, and everything new waits for either `Rebuild` or the next release. `Rebuild` and `Publish` may hang side by side: `Publish` ships what was built and tested, `Rebuild` pulls the new approvals in.

On the tick:

1. `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> release-scaffold --refresh <release-note>` adds the new delta members to `spec_includes` and drops nobody already listed.
2. Recompute the version over the full composition, upward only: when the delta as it now stands warrants a higher part than the one the release carries, `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> release-version <release-note> --bump <part> --product <product-key>`; an operator-set version is left alone.
3. Roll back only what the change touched: a re-approved test-cases document of an included asset returns the release's `test-plan.md` to `draft` and turns `spec_tests_passing` and `spec_built` off; a re-approved design, or a newly included asset, returns both release plans to `draft` and turns `spec_develop_done`, `spec_tests_passing` and `spec_built` off; a new or re-approved `ui-design.md` of an included asset returns both release plans to `draft` and turns `spec_develop_done`, `spec_tests_passing` and `spec_built` off; a new test-cases document of an included asset returns the release's `test-plan.md` to `draft` and turns `spec_tests_passing` and `spec_built` off; the release's own `code-plan.md` re-approved after the last build turns `spec_develop_done`, `spec_tests_passing` and `spec_built` off, and its own `test-plan.md` re-approved after the last build turns `spec_tests_passing` and `spec_built` off — the plan itself stays `approved`, since it is the plan the next build runs from.
4. Start the next build of the same folder — the architect's first step, then the implementer, exactly as the first build ran; the implementer gets the list of what changed since the last build.

## Release and Publish

The `Publish` row hangs once `spec_built` is closed and `spec_released` is still false. The row carries no hint of its own. When the target declares a `staging` address, `# Status brief` names it as the place to check the build before publishing.

On the tick run `"${LAZYCORTEX_PYTHON:-python3}" <specs-cli> release-publish <release-note>`. The verb publishes exactly the `spec_includes` that was built and tested; everything approved after the last build waits for the next release. When the product declares `release.deploy.production` the verb deploys there first: a failed deploy writes one line to the release's `# History`, changes nothing else, and the `Publish` row returns for a retry once the operator has looked at the log. On success — or at once, when no `production` target is declared — the verb, on every included asset's note, sets `spec_released: true` with its moment and adds the version tag; it sets `spec_released: true` with its moment on the release, whose own `spec_built` closed before the row hung (Staging and tests, step 4), writes the version into the manifest when the product names one, and lands the whole set in one commit. The release is frozen from that commit on: its version, its members and its documents never change again, and any later edit, however small, goes into the next release.

Publication wakes the owner's level note once, after the publish commit, with `release-published` (`lazy-spec.catalog-playbook.md` § 5): it only recomputes the delta, hangs or takes down `Start release` and rewrites the product's `# Status brief`. Nothing else is woken: the product's `design.md` is the intent the build was made against, and contradictions between documents are caught by the coherence check after approval (`lazy-spec.coordination-playbook.md` Chapter 19). An included asset whose design was re-approved after the build ships its tested old design: it gets this version's tag and at once stands in `awaiting-release` again with its new design, for the next release.

## Cancellation

An operator cancels a release like any asset, through `spec_cancelled` on its note; a cancelled release is closed, blocks no new release, and its members return to `awaiting-release`. The product coordinator cancels a release itself when its delta has emptied — every included asset cancelled or carried away — and the next release takes the version this one held. A published release is never cancelled. `spec_halted: true` takes every row down and silences the build and the deploys, never the gates and never `# Coordinator commands`.

## Status brief

Rewrite `# Status brief` on every wake, the version on the first line, then the rung and the last build: "1.5.0 — build 2 tested on staging, waiting for `Publish`". Name the `staging` address when there is one, what waits for the operator (`Publish`, `Rebuild`, a failed deploy's log), and what waits outside the release — the approvals that would come in on `Rebuild`, the assets held back from the delta and why. The product note's own brief mirrors the current release's state the same way (`lazy-spec.catalog-playbook.md` § 7).

`spec_state` follows the table of `lazy-spec.coordination-playbook.md` Chapter 11 as it stands for every asset: `implementation` while a build runs, `testing` while the tester runs, `in-review` while a report is in review, `waits-operator` while `Publish` or `Rebuild` hangs, `done` only after publication. The iconize registry paints the release folder from it.
