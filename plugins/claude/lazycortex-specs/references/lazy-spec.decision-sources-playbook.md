# Decision sources — conditional chapter of the coordination playbook

Extracted chapter 14 of `lazy-spec.coordination-playbook.md`, loaded on demand: read this file when a job's `DONE` carries a `blocked` field, when a produced document carries `[!decision-candidate]` markers, or when a decision-source question is open on the asset. Every "Chapter N" cross-reference below names a chapter of that common playbook.

**Decisions live only in living docs.** An asset's defining documents, an asset's or a level's `vision.md`, and the product's `tech.md` and `architecture.md` are the only sources a decision can be promoted FROM. A plan is a decomposition of decisions already made elsewhere; a report is a journal. Both are mortal by design — a plan dies with the build it planned, a report is an append-only record — so neither is ever a decision's source of truth. The test: a decision is something that must outlive the plan that used it; anything that dies along with the plan was a decomposition detail, not a decision.

**`[!decision-candidate]` is a signal, not a record.** When an expert producing code, data, or a report takes a product call its job wasn't told to make ("used X instead of Y"), and that call passes the weight test of `${CLAUDE_PLUGIN_ROOT}/rules/lazy-spec.decisions.md` § 2, it is a candidate for a decision. An expert writing a document under review raises no candidate: a product fork it cannot settle is a `[!question]`, and a call about the document itself it settles silently. A candidate is never a decision on its own — legalizing it means editing the living doc through that doc's own review, nothing else counts. The expert drops the marker only in the report or journal it is itself writing. On the job's `DONE`, the coordinator sees any `[!decision-candidate]` markers in the produced document; a disputed one goes to the operator as a `[!question]` rather than being auto-applied.

**Legalizing an accepted candidate — the route depends on the living doc's state.** A living doc still inside an active review loop needs nothing special: the candidate reaches it through the loop's own rounds — the operator's tick reopens the main round, the writer folds the verdict by its protocol obligation, and the loop's finalize refuses the document while any candidate is still in the body. A living doc already finalized (`review_result` stamped, banner carried) re-enters the loop at the WRITER round: the coordinator carries the accepted candidate blocks — ticks included — into the living doc under its sibling-doc-waiver, then calls `Skill(lazycortex-review:lazy-review.start, "<living doc>")`; the class's writer folds the carried, already-answered callouts by its ordinary round obligation, and the edit lands through the review loop like any other round. Never a bare `dispatch-job` against a finalized doc: the runtime contract stops that writer at a file the system owns regions of, the edit strands in the job's `result/`, and neither review verb can apply it after the fact (`submit` opens review on the current text with no writer round).

**The planner's missing-decision ladder — three rungs, all on existing mechanics:**

1. **`planner_review`** — a validation slot in the defining documents' review classes (mirroring how `developer_review` / `tester_review` already work) that checks whether the doc carries enough decisions to decompose into a plan at all, BEFORE a planner job is even dispatched.
2. **Mid-write question — signalled in the planner's OWN doc, carried across by the coordinator.** If the planner discovers a gap while actually writing the plan, it never writes into the source doc itself — the expert-side canon (`lazy-core.markdown-style.md`'s callout and tag registry) forbids a `[!question]` in a sibling doc, full stop, and that prohibition is never waived for an expert. Instead the planner drops its `[!question]` in the plan it is already writing (or, when it cannot even start, sets the `blocked` field on its own `response.json` — rung 3 below). On that job's `DONE`, the COORDINATOR reads the question and is the one that carries it across: it writes the SAME question into the SOURCE doc and re-submits that doc into review (`Skill(lazycortex-review:lazy-review.submit, ...)`) — a cross-file write the coordinator is licensed to make under its own `sibling-doc-waiver` (Chapter 15's cross-doc exemption), never something the planner does directly.
3. **Last resort — the `blocked` outcome.** A planner job that cannot proceed at all reports a blocked-on-missing-decision outcome (format: signals protocol, Chapter 15); the coordinator drives the round trip back up the chain — carrying the blocking reason into the source doc exactly as rung 2 does, then re-review, then the planner is redispatched — the same generalized counter-check shape a change's cascade convergence uses, applied here to a plan blocked on an absent decision.
