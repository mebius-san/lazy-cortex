# Flip a Gate

Thin Claude wrapper over the gate-flip primitive `bin/flip_gate.py`. The gate model — the flat booleans (`spec_design_done` and `spec_released` on a design-only asset, the six-gate linear S0..S6 ladder on a release), and what the primitive mutates — lives in `${CLAUDE_PLUGIN_ROOT}/references/lazy-spec.lifecycle-protocol.md`. This skill never restates it.

**The flip is unconditional.** The primitive refuses only an unknown gate name, a gate the note's own `spec_role` ladder does not carry, opening one of the four middle gates on a design-only note, and any flip while the target asset is cancelled (`spec_cancelled: true`) other than the un-cancel `spec_cancelled --off`. The cancel itself, `spec_cancelled` turned on, also stops the review of the asset's documents and removes their banners through the review plugin's `strip-status` verb (no commit), moves its staged documents — the start document (`design.md`, `bug.md`) included — to `cancelled`, on a release repaints the members with `spec_design_done: true` `awaiting-release` and wakes them, and cancels the asset's running job last, recording it as `last_job` with `outcome: cancelled`, `unlanded: true` and `retired_by_cancel: true`, in the same commit; it is refused with nothing written when a review cannot be stopped or the job cannot be cancelled, and on a published release or one under `releases/archive/`; a cancel refused or crashed after it has killed the job leaves `active_job` null, that job recorded as `last_job` with `outcome: cancelled`, raises `pending_wake: job-done`, and names it as `killed_job` in the result. The un-cancel returns each document the cancel marked to the stage it had — `empty`, `deferred` and `rejected` as they were, `draft` and `approved` to `draft`, an `approved` one with its review opened at the writer round — resumes the reviews it marked, turns off every derived gate whose document it took out of `approved` — on a release a `code-plan.md` taken out of `approved` turns off `spec_plan_done`, `spec_develop_done`, `spec_tests_passing` and `spec_built`, a `test-plan.md` alone `spec_tests_passing` and `spec_built` — on a release sets `spec_rebuild_owed` only for the job this cancel retired — a `last_job` carrying `retired_by_cancel: true` and `unlanded: true` whose `job_id` equals the release's `spec_build_job` or `spec_test_job` — and drops that stamp; an earlier unlanded failure (a refused landing, a dead job) carries no stamp and keeps waiting for the operator's `Rebuild` tick, and repaints the members with `spec_design_done: true` `in-release` and wakes them, then wakes the asset's own coordinator, and is refused with nothing written on a release while another release of the same owner is open or when it sits under `releases/archive/`. Beyond that there is no readiness precondition table it checks on its own. Deciding WHEN a gate is ready to move is `spec.coordinator`'s job, reasoning from `${CLAUDE_PLUGIN_ROOT}/references/lazy-spec.coordination-playbook.md`; this skill (and the primitive underneath it) trusts whoever called it to have already made that call. The operator confirmation in step 2 below exists precisely because a human invoking this skill directly has not necessarily gone through that reasoning — the confirmation is the human's own check, not a stand-in for a removed precondition.

## Input

1. **Asset** — a status folder-note path, asset directory, or any path/slug the product resolver can map to one asset folder under `<spec_path>` at any depth. Resolve the product per `${CLAUDE_PLUGIN_ROOT}/references/lazy-spec.config-protocol.md` → Resolving a Product, then narrow to the single asset directory.
2. **Gate** — one of `spec_design_done`, `spec_plan_done`, `spec_develop_done`, `spec_tests_passing`, `spec_built`, `spec_released`, or the overlay `spec_cancelled`, which abandons the asset together with its documents. The four middle gates exist on a `release` note only: on a design-only note (every other `spec_asset_type`, or none) the primitive refuses to turn one on (`design-only` refusal) — `spec_released` there is the publishing release's write, and only a repair ever calls `--off` on a stale middle key.
3. **`--off`** (optional) — regress the gate true→false instead of flipping it on.
4. **`--auto`** (optional) — skip the confirmation question (`spec.coordinator` and other non-interactive callers pass this). Without it, this is an interactive operator action.

## Process

### 1. Resolve the asset

Map the input to exactly one asset directory. If the input is ambiguous (matches more than one product or asset), prompt the operator to pick via `AskUserQuestion` (options = the candidate asset directories) — context first: where (`/lazy-spec.flip-gate · Step 1 — Resolve the asset`), found (the candidate asset directories `<input>` matched), why asking (the flip targets exactly one asset), answers (one option per directory — the flip proceeds on it; nothing persisted); header "Asset", question "Which asset does `<input>` mean for flipping `<gate>`?", each option's description its product and category. If nothing resolves, refuse with a message naming the input.

### 2. Confirm the flip

Unless `--auto` was passed, ask a single `AskUserQuestion` to confirm:

```
Context (print before asking):
- Where: /lazy-spec.flip-gate · Step 2 — Confirm the flip; target <asset-dir>/<slug>.md
- Found: <gate> currently <true | false>; the other gates <the note's other gate booleans>; spec_cancelled false
- Why asking: flipping a gate is the recorded progression signal, and the primitive performs the mutation unconditionally once confirmed — it does not itself check whether the gate's usual readiness condition holds; a release's build gate (`spec_develop_done` / `spec_tests_passing` / `spec_built`) or `spec_released` asserts that external work (an accepted report / green tests / merge / publication) actually happened, and this confirmation is the human's own check
- Answers: `yes` — runs the flip now, the asset advances one notch along its ladder (or regresses when `--off`), the folder-note's `spec_<gate>_at` stamp records the moment (dropped on `--off`), no history line; on `spec_cancelled` turned on, `yes` also stops every review in the asset folder and removes its banner, moves every staged document — the start document included — to `cancelled`, on a release repaints the members with `spec_design_done: true` `awaiting-release` and wakes them, and cancels the running job last, all in one commit or not at all; on `spec_cancelled --off`, `yes` returns each document the cancel marked to the stage it had (`empty`, `deferred`, `rejected` as they were; `draft` and `approved` to `draft`, an `approved` one with its review opened at the writer round) resumes the reviews it marked, turns off every derived gate whose document it took out of `approved`, and wakes the asset's coordinator (on a release, also turning off `spec_develop_done`, `spec_tests_passing` and `spec_built` when `code-plan.md` left `approved` — `spec_tests_passing` and `spec_built` when only `test-plan.md` did — setting `spec_rebuild_owed` only for the job this cancel retired — `last_job` stamped `retired_by_cancel: true`, `unlanded: true`, its `job_id` equal to `spec_build_job` or `spec_test_job` — and dropping that stamp, repainting the members with `spec_design_done: true` `in-release` and waking them); `no` — no-op, asset unchanged (`skipped-per-user-choice`). See: `${CLAUDE_PLUGIN_ROOT}/references/lazy-spec.lifecycle-protocol.md`, `${CLAUDE_PLUGIN_ROOT}/references/lazy-spec.coordination-playbook.md`
AskUserQuestion: header "Flip <gate>", question "Flip <gate> to <true | false> on <product>/<path>?", options `yes` / `no`, each with a one-sentence consequence.
```

On `no` → exit no-op (outcome `skipped-per-user-choice`). On `yes` → continue.

### 3. Subprocess the primitive

Run `"${LAZYCORTEX_PYTHON:-python3}" "${CLAUDE_PLUGIN_ROOT}/bin/lazycortex-specs" flip-gate <asset_dir> <gate>`, appending `--off` when regressing. Do NOT pass `--auto` from the interactive path — `--auto` is only for the non-interactive callers that skipped step 2. Report the primitive's result verbatim: on success, the flipped gate and new value; on refusal, the primitive's refusal message (`unknown gate: <gate>`, `gate <gate> is not on the '<role>' ladder`, `gate <gate> is not on a design-only ladder`, `asset is cancelled`, and on `spec_cancelled`: the asset's running job could not be cancelled, a review in the asset folder could not be stopped, another release of the same owner is open, the release sits in the releases archive, or the release is published) — do NOT retry or work around it.

## Output

- The resolved asset directory.
- The flip outcome: `flipped` (gate + new value) or `refused` (primitive's message) or `skipped-per-user-choice`.
- On `spec_cancelled`, the result keys as the primitive prints them: on the cancel `cancelled` (documents moved to `cancelled`), `stopped` (documents whose review was stopped) and `refused` (each `{doc, reason}` left where it was), plus `killed_job` — the `last_job` record — on a refused or crashed cancel that had already killed the asset's running job; on the un-cancel `drafted` (documents returned to `draft`), `restored` (documents returned to `empty`, `deferred` or `rejected`), `resumed` (documents whose review was re-opened, the fresh writer-round reviews of documents recorded at `approved` included) and `refused`.

## Failure modes

- **`/lazy-spec.flip-gate` refuses with "asset is cancelled"** — `spec_cancelled: true` freezes all gates, on or off, except the un-cancel `spec_cancelled --off` itself → un-cancel the asset first with `"${LAZYCORTEX_PYTHON:-python3}" "${CLAUDE_PLUGIN_ROOT}/bin/lazycortex-specs" flip-gate <asset> spec_cancelled --off` (the documents the cancel marked return to the stage each had), then flip.
- **`/lazy-spec.flip-gate` refuses with "gate `<gate>` is not on a design-only ladder"** — a middle gate (`spec_plan_done`, `spec_develop_done`, `spec_tests_passing`, `spec_built`) was asked on any note but a release's → nothing to flip; a design-only asset's code lands through a release, whose own note carries those gates.
- **`/lazy-spec.flip-gate` refuses with "unknown gate" or "is not on the `<role>` ladder"** — the gate name is a typo, or belongs to the other ladder (an asset gate on a level note, or a level gate on an asset note) → pass a gate the note's own ladder carries.
- **`/lazy-spec.flip-gate` refuses the cancel because the asset's running job could not be cancelled, or a review in the asset folder could not be stopped** — nothing was written: the reviews already stopped got their bytes back and their wakes raised again, and nothing is left uncommitted → find the job (`/lazy-expert.list-jobs`) or the review (`/lazy-review.status`) the result names, settle it, then cancel again. When the result carries `killed_job`, the asset's running job was already killed: `active_job` is null, `last_job` reads `outcome: cancelled`, and `pending_wake: job-done` is raised, so the coordinator sees the job gone.
- **`/lazy-spec.flip-gate` refuses the cancel because the release is published, or refuses either crossing because the release sits in the releases archive** — a published release is frozen and an archived one is closed history → nothing to cancel or restore; changes go into the next release.
- **`/lazy-spec.flip-gate` refuses the un-cancel because another release of the same owner is open** — one release is open per product at a time → cancel or publish the open release first, then un-cancel.
- **`/lazy-spec.flip-gate` cannot resolve the asset** — the input maps to zero or more than one asset → pass an unambiguous asset directory or slug.
- **A gate was flipped that shouldn't have been** — the primitive trusted the caller; there is no precondition to have caught it. Flip it back with `--off` (also unconditional apart from the gate-name, note-ladder and cancelled-asset refusals; on a cancelled asset only `spec_cancelled --off` itself is accepted), then check `${CLAUDE_PLUGIN_ROOT}/references/lazy-spec.coordination-playbook.md` Chapter 3 for what the gate's readiness actually requires before flipping forward again.
