# lazycortex-core — pending changes

**Status**: changed — `plugin.json` version `6.0.0` has not been published yet (last recorded release: `5.20.4`).

## Highlights since `5.20.4`

- A job now has to say it finished before the runtime believes it did. Until now a job that wrote no outcome at all counted as a success: the dashboard showed it green, and an inbox routine deleted the file the job was supposed to import — a document could disappear because the expert reported its failure in words the runtime never read. Anything short of an explicit outcome is a failure now, an inbox file is destroyed only against a proven success, and a job that answers in the wrong shape is handed the reason and asked once more before it is failed for good. Experts also gained a way to say "not now": work postponed with every input left untouched is neither a success nor a failure, and the file returns to the queue after a wait the routine sets. **Upgrading**: a protocol that told its expert to write a status field of its own must be changed to use `outcome` — until it is, every job it drives parks instead of finishing. `/lazy-core.doctor` lists the offending protocol files.

- An inbox file whose job died in a spawn-level fault no longer sits untouched forever. The failed bundle kept holding its dedup key, so every later tick skipped the same file until an operator consumed the bundle by hand — a document could wait a full day for an import that never came. A failure the runtime itself classified as transient is now retired an hour after it landed and the file goes back out on that very tick; a logical failure still parks as a dead letter for a human to look at.
- A settings file sitting on a version its migration ladder cannot walk now fails with the section and version named, instead of a bare `KeyError` carrying only the integer. The condition is real — a ladder gap is what a hand-edited or downgraded settings file produces — and the daemon was surfacing it as an unreadable traceback.
- Four `# guard:` comments described the branch they did not label. The worst sat above the whole job-processing path in the expert pump and read "no ready jobs at all → return early"; the others mislabelled the settings migration branch, the merge-succeeded branch of a worktree task, and a write that only happens when something was added. A comment that contradicts its code is worse than none, because every later reader and agent trusts it.
- An inbox folder is a place a person looks at — often a synced folder on their own disk — and it was quietly collecting empty bookkeeping directories left behind whenever an assistant touched it. Each scan of the inbox now clears those away; anything holding real content is left exactly where it is.
- Nine docstrings were brought back in line with their signatures: parameters that change emitted config but went undocumented, an exception that reaches the caller with no `Raises:`, a `cwd` argument documented for one of its two callers, and a `Returns:` on a function that returns nothing.
- The sandbox that confines expert runs is checked against the path the system actually resolves, so a working directory reached through a symlink — the usual shape of a data folder linked in from elsewhere — was permitted in name only, and every job writing there failed with `Operation not permitted` while the configuration still read as correct. Install now records the resolved locations behind each allowed path, including the folders linked inside a checkout, and the health check, the doctor, and the launch preflight each report and repair a scope that has drifted since. Re-run install once to have the correct scope recorded for an existing checkout.

- Every failure the runtime records now reaches a metrics endpoint instead of only a log file on the host: incidents are exported by kind and cause, so a dashboard can show them and an alert can fire on them. The counter survives the ledger's own hourly pruning — before, a pruned journal would have quietly stopped the count until the file grew back past where the reader had stopped.
