# Asset creation — conditional chapter of the coordination playbook

Extracted chapter 12 of `lazy-spec.coordination-playbook.md`, loaded on demand: read this file when an accepted document surfaces an `[!asset-proposal]` callout to materialize, or before scaffolding an asset for any reason other than a routing spawn (routing carries its own chapter). Every "Chapter N" cross-reference below names a chapter of that common playbook.

**Experts never create assets — none, ever.** The single mechanism for proposing a new asset is a callout an expert drops in its own document, shaped per the signals protocol (Chapter 15) — working type `> [!asset-proposal]`. An architect proposes child assets in the document it is writing; a tester proposes bugs in its report; the mechanism is available to any expert in any doc it owns.

**Bugs get a three-way choice.** Because a bug may already be known, a tester's proposal is one of: create a new bug asset, link to an existing one (duplicate), or reopen a closed one (regression). The tester searches existing bug assets before proposing. At materialization time the coordinator re-checks the same candidates and MAY convert a proposed `create` into a `link` or `reopen` if a better match turns up — a disputed conversion goes to the operator as a `[!question]` rather than being silently decided.

**Materialization happens after the proposal's own doc is accepted.** For a living doc that means the ordinary review approval; for a report that means the acceptance cycle of Chapter 8 closing (approve). Only then does the coordinator act: `create` runs the scaffold verb, `link` wikilinks the existing asset, `reopen` clears the target's cancelled stage or rolls its gates back per the target type's own playbook (via `lazy-spec.set-stage` and `flip-gate --off`) — and every case ends with the originating callout replaced by a `[[...]]` link to the materialized (or linked, or reopened) asset. A `create` that materializes a proposed CHILD of a decomposer asset (Chapter 10) has one further step: the coordinator appends the new child's token to the parent's own `spec_depends_on` via `note-set-key`, before replacing the callout — the parent's dependency graph must name the child the same tick it is born, never a later catch-up. A `link` proposed in a decomposer's own defining document (an existing asset covering part of the decomposition — the architect's decomposition exception in `lazy-core.markdown-style.md`) gets that same append step, ALWAYS: a link-proposal in Dependencies & children IS a decomposition dependency by construction — an edge onto an already-implemented target is trivially satisfied, onto an unfinished one it correctly blocks implementation; an asset merely worth mentioning is prose in the document, not a proposal, so no edge question ever arises at materialization time. **The token's leading segment is always the FOLDER the child actually sits in**, not the `[!asset-proposal]` callout's own type field verbatim — a shipped type's folder is the pluralized form (`bug` → `bugs`, `feature` → `features`, `change` → `changes`), while an operator-declared type's folder is whatever its `default_path` (or the operator's own `path=`) put it in. Writing the callout's bare type value (e.g. `bug/<slug>` instead of `bugs/<slug>`) produces a token that never resolves — silent to `spec_depends_on`'s own writer, a doctor WARN at best (`lazy-spec.doctor`'s unresolvable-`spec_depends_on` check), and invisible to both the context fold-in and the bottom-up AND.

**Rejection is clean.** If the containing doc's review rejects it, nothing was ever born — there is nothing to clean up.

**The complete list of asset creators.** The operator, through the product/type/asset creation wizards; and the coordinator, either spawning per a routing decision (Chapter 9) or materializing an approved proposal (this chapter). No expert, no script, no other path creates a spec asset.
