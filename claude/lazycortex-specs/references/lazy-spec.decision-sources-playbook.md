# Decision sources — conditional chapter of the coordination playbook

Extracted chapter 14 of `lazy-spec.coordination-playbook.md`, loaded on demand: read this file when a job's `DONE` carries a `blocked` field, when a produced document carries `[!decision-candidate]` markers, or when a decision-source question is open on the asset. Every "Chapter N" cross-reference below names a chapter of that common playbook.

**Decisions live only in living docs.** An asset's defining documents and the product's `tech.md` are the only sources a decision can be promoted FROM. A plan is a decomposition of decisions already made elsewhere; a report is a journal. Both are mortal by design — a plan dies with the build it planned, a report is an append-only record — so neither is ever a decision's source of truth. The test: a decision is something that must outlive the plan that used it; anything that dies along with the plan was a decomposition detail, not a decision.

**`[!decision-candidate]` is a signal, not a record.** When an expert takes a call its job wasn't told to make ("used X instead of Y"), it is a candidate for a decision, never a decision on its own — legalizing it means editing the living doc through that doc's own review, nothing else counts. Any expert may drop the marker in the document it is itself writing or reporting into. On the job's `DONE`, the coordinator sees any `[!decision-candidate]` markers in the produced document and dispatches the designer/architect to formalize the candidate as an edit to the relevant living doc; a disputed one goes to the operator as a `[!question]` rather than being auto-applied.

**The planner's missing-decision ladder — three rungs, all on existing mechanics:**

1. **`planner_review`** — a validation slot in the defining documents' review classes (mirroring how `developer_review` / `tester_review` already work) that checks whether the doc carries enough decisions to decompose into a plan at all, BEFORE a planner job is even dispatched.
2. **Mid-write question — signalled in the planner's OWN doc, carried across by the coordinator.** If the planner discovers a gap while actually writing the plan, it never writes into the source doc itself — the expert-side canon (`lazy-core.markdown-style.md`'s callout and tag registry) forbids a `[!question]` in a sibling doc, full stop, and that prohibition is never waived for an expert. Instead the planner drops its `[!question]` in the plan it is already writing (or, when it cannot even start, sets the `blocked` field on its own `response.json` — rung 3 below). On that job's `DONE`, the COORDINATOR reads the question and is the one that carries it across: it writes the SAME question into the SOURCE doc and re-submits that doc into review (`Skill(lazycortex-review:lazy-review.submit, ...)`) — a cross-file write the coordinator is licensed to make under its own `sibling-doc-waiver` (Chapter 15, and `lazy-spec.expert-signals-protocol.md`'s waiver clause), never something the planner does directly.
3. **Last resort — the `blocked` outcome.** A planner job that cannot proceed at all reports a blocked-on-missing-decision outcome (format: signals protocol, Chapter 15); the coordinator drives the round trip back up the chain — carrying the blocking reason into the source doc exactly as rung 2 does, then re-review, then the planner is redispatched — the same generalized counter-check shape a change's cascade convergence uses, applied here to a plan blocked on an absent decision.

**The planner's `already-covered` verdict — refusal to plan the already-built.** The `blocked` field's second subtype (format: signals protocol, Chapter 15) arrives when the planner's mandatory code reading found EVERY goal of the source doc already implemented; no plan was written, so Chapter 6's `lazy-review.submit` call is skipped — there is nothing to submit. The coordinator's response, in order:

1. **Verify, never trust.** Re-check the planner's evidence (`error.message`, code paths per spec goal) through the same research routes Chapter 9's duplicate-behavior check uses — `lazy-spec.lookup`, `lazy-wiki.structure` query mode, `/lazy-wiki.domains`. The verdict is the planner's claim; the coordinator's own pass is what earns it an operator question.
2. **Escalate — options adaptive to what verification found.** Drop a `[!question]` on the asset's folder-note (Chapter 11 shape, attribution line included):
   - Verification found an existing spec-tree asset covering the same capability → offer **cancel + link**: this asset was a routing miss, the capability lives at `[[<covering asset>]]`. On the tick: `note-set-key <asset> spec_cancelled true`, a wikilink to the covering asset in `# History` and `# Status brief`; deleting the folder stays the operator's own manual act, never the coordinator's.
   - No covering asset, but the code covers the goals → offer **accept as a retro-spec**: the asset stays alive as the spec of what the code already does. On the tick: dispatch `lazy-spec.sync-with-code` in its asset mode to check the defining documents against the code, then flip `spec_develop_done` forward on that signal (Chapter 4's human-signal rule); the plan stays absent — absence is "no plan needed", `spec_plan_done` is free — and the ordinary ladder continues from there (tests, release).
   - Always, regardless of what verification found → offer **"the planner is wrong — plan it"**: redispatch the plan checkbox with the operator's comment folded into `context`.
3. **Never silently cancel — the same asymmetric risk as Chapter 9's `reference` rule.** A wrong plan wastes a review round the operator sees; a wrong cancel is INVISIBLE — the asset is quietly marked already-done and nobody builds it. Every outcome above lands only on the operator's tick.
4. **While the question stands unanswered, do not re-hang the plan checkbox** — a hanging checkbox invites a tick that redispatches the planner into the same verdict; Chapter 18's "Same dispatch, unchanged cause" signal is the backstop if it happens anyway.
