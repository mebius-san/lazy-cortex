# Request routing — conditional chapter of the coordination playbook

Extracted chapter 9 of `lazy-spec.coordination-playbook.md`, loaded on demand: read this file on a Routing wake — the terminal group of a request's own review cycle — BEFORE composing any routing decision. Every "Chapter N" cross-reference below names a chapter of that common playbook.

Request routing is a coordinator MODE, dispatched at the terminal group of the request's own review cycle (the routing block, after the operator's `[!question]` confirmation) — the position in the review pipeline does not change; what changes is that `spec.coordinator` runs it directly, instead of a separate agent dedicated only to routing.

**Tools, unchanged.** `lazy-spec.request-classify` and `lazy-spec.request-find-candidates` remain the coordinator's instruments in this mode — the same classification (a closed meta-class set plus the target product's open asset-type set) and the same candidate search over every declared asset type.

**Target descriptions.** Every spawn or attach line the coordinator proposes carries a short `:: <description>` — a couple of sentences on what the target does today, or what this request changes about it. The apply step later seeds this description as the target's draft content; the request body itself is never copied wholesale into the doc, only referenced (`spec_source_requests`).

**Duplicate-behavior check.** Before proposing a spawn, the coordinator checks whether the request already describes something the code does today, through the same research routes any expert's research-aspect uses against the target product — `lazy-wiki.structure` query mode, `/lazy-wiki.domains`, `lazy-spec.lookup`. A spawn whose capability the check finds already implemented gets that noted in its own `:: <description>` line rather than a silent new-asset proposal; when the overlap is ambiguous — code that partially matches, or a candidate that may or may not be the same thing — the coordinator raises it through the same operator `[!question]` confirmation this chapter already gates routing behind, rather than guessing.

**Upstream-origin requests run the research pass unconditionally, before ANY spawn decision.** A request whose body names an upstream unit (`- Unit: \`upstream/<repo-key>/<mount>/<unit-path>\``, written by `lazy-spec.upstream-tick`'s Phase C) is never routed straight to spawn on the strength of its own prose — an incoming design's own wording says nothing about whether the capability already shipped. Before proposing even one spawn line, the coordinator runs BOTH `lazy-spec.lookup` (bounded spec-tree search) AND `lazy-spec.coverage` in its read-only reporting mode (gap-scan against the target product's `docs/structure.md` / domain groups) over every candidate target product, on top of the ordinary duplicate-behavior check above — `lazy-spec.coverage`'s own code-side view is what a spec-tree-only search misses, and it is the one this chapter requires specifically for an upstream-origin request, not the ordinary intra-repo one (whose own designer already knows the code it's asking for). A first landing on a freshly-mirrored source routinely finds most units already implemented; skipping this pass on the excuse that "the design looks new" is exactly the failure mode `reference` exists to prevent (below).

**The `kind` of a spawn line is an asset TYPE, read from the declarations.** Never an invented word, never a folder name the coordinator guessed: the legal kinds are exactly the types declared for the target product (Chapter 10's registry).

**`docs=` is mandatory on every spawn line.** It names the documents the new asset starts with, each as `<file>:<doc_type>`, and its value comes from the target type's own `start_doc` declaration. A spawn line without `docs=` is rejected at apply time — the coordinator writes it every time rather than relying on any fallback.

**`path=` is optional and names a PLACE.** Absent, the target type's `default_path` decides where the asset lands. This is a hint on write only: nothing ever resolves an asset's type back out of the folder it ended up in (Chapter 2).

**`tools=` is optional.** The coordinator writes it when routing ALREADY knows what the work is made of — the request itself is explicit, or the target type declares `default_tools`. Absent, `spec_tools` is simply not written, the asset starts "not determined", and the type playbook's own moment of determination decides it later (Chapter 2).

**`drop=` rides on an attach line.** It names the documents to remove from the existing target when the request is folded into it — a pre-launch rollback list, supplied by the TARGET type's playbook. An attach line with no `drop=` means exactly "drop nothing": absence is a decision, not an omission to be filled in by the apply worker.

**`product=` field — routing across several products in one decision.** Valid on ANY spawn line (any kind), a `<product-key>` naming which registered product the target spawns into. This is the sole way one request's routing decision fans out across several products in the same apply run: a design that decomposes into an inventory-slots feature in one product and a save-schema change in another names each with its own `product=` on its own spawn line, in the same `<!-- routing-decision -->` block. Absent `product=`, the apply worker falls back to its own single-product default — safe on a vault with exactly one registered product, a silent wrong guess on a multi-product one, so the coordinator ALWAYS states `product=` explicitly the moment more than one product is registered, never relying on the fallback to guess right. An unregistered `product=` value is an apply-time hard failure, not a silent drop — the coordinator confirms the key against the vault's own registered product set before writing the line.

**`targets=` field.** Valid only on a `change`-kind spawn line — comma-separated `<folder>/<slug>` tokens naming the assets the change's design will cascade into. This is the sole way a change-spawn populates `spec_targets`; what the cascade then does with them is the `change` type playbook's business.

**`reference` decisions — "already implemented", not a new asset.** A third routing-decision verb, alongside `spawn` and `attach`: `reference <folder-note-path> [:: <description>]`. It names an EXISTING asset (found through the very research pass above, or the ordinary duplicate-behavior check on a non-upstream request) that the coordinator judges already implements what the request describes. Applying a `reference` line registers only a link — via `spec_targets` on the REQUEST's own frontmatter, the same list-typed key a change's design-cascade already writes — and touches NOTHING on the referenced asset: no body edit, no `spec_source_requests` attribution, no review re-opened. A request whose routing decision is entirely `reference` lines is a full accept, exactly like a request that only spawned or only attached — the unit that produced it goes green having produced no new asset, which is the correct outcome for a source that mirrors mostly-already-built design.

**A `reference` decision is formulated LOUD, every time.** Every `reference` line's `:: <description>` states, in full sentences, which existing asset covers the request and what evidence backs that call (a spec doc section, a code path, a prior feature's own scope) — never a bare path with no rationale. The reason is asymmetric risk: a wrong `spawn` produces a redundant asset an operator notices and can merge or cancel; a wrong `reference` produces NOTHING VISIBLE — the design is quietly marked "already done" and nobody builds it. Ambiguous evidence (a partial match, a candidate that covers only part of the request) is never resolved by picking `reference` anyway "to be safe" — it goes through the same operator `[!question]` confirmation as any other disputed routing call, per the duplicate-behavior check above, and Chapter 13's disputed-reference scenario governs what happens when the operator disagrees with a `reference` call after the fact.

**Grammar note — one structured block, three verbs.** The routing-decision block's full grammar (parsed by `apply_request.py`, documented verbatim in `lazy-spec.request-protocol.md`'s "Routing-block grammar" section) is:

```
spawn <asset-type> <slug> [product=<key>] [path=<dir>] [tools=<tool>[,...]] [targets=<folder>/<slug>[,...]] docs=<file>:<doc_type>[,...] [:: <description>]
attach <repo-relative-folder-note-path> [drop=<file>[,...]] [:: <description>]
reference <repo-relative-folder-note-path> [:: <description>]
```

The optional fields on a spawn line are order-independent (any, all, or none); `targets=` only takes effect on a `change`-kind spawn; `docs=` is required. `reference` takes the same path shape as `attach` — a resolvable repo-relative folder-note path, not a bare `<folder>/<slug>` token, since a reference target is not scoped to the routing request's own product the way a change's cascade targets are.

**The launched-asset rule.** Before proposing a direct attach onto an asset, the coordinator checks the same three launched signals the router used to check: `spec_develop_done: true`, a tracked `active_job` whose `checkbox` is an implementation-side label, or an existing implementation report. Any one true means implementation has already started — the coordinator does NOT offer a plain attach; it proposes a change-spawn naming the asset via `targets=` instead. An asset with none of these signals stays a normal attach candidate.

**Pre-launch rollback is a coordinator decision.** Whether to roll a not-yet-launched asset's ladder back (dropping the documents its type playbook lists for `drop=`, flipping downstream gates off) versus modifying it in place versus routing through a change despite the asset technically not being launched — that judgment belongs to the coordinator in routing mode, weighed against the rules layers in scope. The rollback ITSELF stays an atomic primitive verb (Chapter 1's closed verb set) that refuses on its own when the target is cancelled or halted, no matter who calls it — the coordinator's judgment picks whether to invoke it, the primitive still enforces its own safety.

**Conflict with an active change on the same target.** Same call as the `change` type playbook's conflicting-changes rule — the coordinator decides wait / cancel / fold, escalating to the operator via `[!question]` when the rules layers don't settle it.

**Any DECLARED type, always.** Spawn kinds are not limited to a built-in shortlist: every type declared for the target product (Chapter 10's registry — never an invented one) is a legal spawn kind, exactly as the classifier's open set already allows.
