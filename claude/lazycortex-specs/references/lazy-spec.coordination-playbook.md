# Coordinator playbook — how `spec.coordinator` decides

This document IS the coordinator's COMMON brain — the procedure and the invariants that hold on every asset, whatever it is made of. What a particular kind of asset actually DOES — which documents define it, which steps run in which order, what closes each gate, which launch checkboxes exist — is not here: it lives in the asset's own type playbook and in the playbook of each tool the asset uses (Chapter 2). Every scenario the spec system needs to handle across assets — a change touching a feature, a report awaiting acceptance, a request needing a home, a bug an expert spotted — is decided by reading this playbook plus those, and acting through a small closed set of primitive verbs, never by bespoke script logic. A new scenario is a new chapter (or an edit to an existing one) in whichever of the three owns it, not a code change. `lazy-spec.drive` (the no-daemon session orchestrator) reads and follows the same set when driving an asset by hand.

## 1. Role, invariants, verbs, boundaries

**What the coordinator is.** One persona (`spec.coordinator`, agent + expert record in `lazycortex-specs`, sonnet-tier). Any state transition on any spec asset dispatches its job: read what changed, update `# Status brief` in plain product-language prose, check related assets, and act — but ONLY through the closed verb set below. Inter-asset interaction of every kind (change cascades, request routing, asset creation, acceptance cycles, decision escalation) goes through the coordinator; there is no bespoke script for any of it.

**Topology.** The daemon that dispatches the coordinator runs in its own checkout, named by `daemon.run_here` — not the checkout the operator edits in (a separate Obsidian vault clone, a separate working copy). Every gesture named in the trigger list below reaches the coordinator only as a commit the operator has already pushed and this checkout's daemon has already pulled in on a prior iteration; there is no dirty-tree signal to read here, because an uncommitted edit sitting in the operator's own checkout is invisible to this one. The coordinator's own answers travel the same path in reverse — a commit under its own bot identity, pushed by the daemon, pulled by the operator (or their vault's own sync) before it is visible to them.

**Triggers — the closed set of things that wake the coordinator:**

1. A commit by a non-`@bot.` author that has reached this checkout and touches the asset's folder outside an active review: the status note itself, or — on a grouped tick naming several changed members at once — a sibling doc that does NOT carry `review_active: true` (operator decision 2026-08-15: a sibling under active review is the review loop's own business, not a wake signal, until its review ends — the moment trigger 6 already covers). See § Self-suppression below for why a coordinator-authored (or any other bot-authored) commit never re-triggers itself.
2. Request routing reaching the terminal review group (the request's routing block, once the operator approves).
3. A non-empty `# Coordinator commands` section on an asset folder-note.
4. A ticked answer to one of the coordinator's own `[!question]` callouts.
5. A launch-checkbox job's terminal marker landing — `lazy-spec.gate-tick` clears the asset's `active_job` marker and raises `pending_wake: job-done` in the runtime sidecar in its place, and that raised flag is what the watch worker reads. It wakes the coordinator regardless of who authored the commit the tick landed alongside; the bot-suppression rule exists to ignore the coordinator's own idle re-triggers, not to hide a real state transition (see the `job-done` trigger token, `spec_keys.CoordinatorTrigger`). A wake that a higher-priority trigger preempts keeps its flag and fires on a later tick rather than being swallowed.
6. A sibling authored doc's `review_result` appearing or changing against the value this system last recorded for it — a review approval (or re-approval) landing on a defining document, a plan, or a report of this asset (product-level `tech.md`, still out of scope — no coordinator job tracking exists at that level yet). Wakes REGARDLESS of the sibling commit's own author, the same per-transition exemption as trigger 5: a commit that never touches `review_result` (an operator's prose edit, a writer's draft) simply carries no transition, so no separate author check is needed to exclude it. That same prose edit only reaches THIS coordinator via trigger 1 once the touched sibling is no longer `review_active: true` — while the review is active, neither trigger fires on it, and trigger 6 is the moment the wake resumes (see the `doc-transition` trigger token, `spec_keys.CoordinatorTrigger`).
7. `lazy-spec.drive` invoking it directly in the no-daemon session mode.
8. A dependency asset's own wake resolving — one hop of reverse-edge dispatch, when this asset names that dependency in its own `spec_depends_on` (Chapter 10's dependency graph). Synthetic: never derived from an `item`, so it carries no author of its own to check (see the `dependency-ready` trigger token, `spec_keys.CoordinatorTrigger.DEPENDENCY_READY`, payload names the ready dependency).

A no-op tick (nothing changed that the coordinator cares about) and automation on a halted asset do NOT wake it — halt silences automation, not the trigger check, but a halted asset's own automation stays dormant per § Halt below.

**Self-suppression.** The commit-author check that gates trigger 1 compares the folder-note's changed-file author against the `@bot.` substring — the same convention every existing bot identity in this plugin already uses (`lazy-spec.flip-gate@bot.invalid`, `lazy-spec.gate-tick@bot.invalid`, and the coordinator's own `spec.coordinator@bot.invalid`). An author whose email contains `@bot.` never re-triggers the coordinator on its own write — otherwise every coordinator-authored edit would wake a fresh coordinator job on itself.

**Where the two job markers live.** Neither is frontmatter. The asset's launch-checkbox job (`active_job`) and the coordinator's own job (`coordinator_job`), plus the `pending_wake` flag trigger 5 reads, live in a gitignored runtime sidecar at `<repo>/.runtime/lazy-specs.jobs.json`, keyed by the note's repo-relative path and written through the `mark-job` verb. Two consequences: an operator hand-editing a folder-note cannot break the mutex or lose a live job's record, because the markers are not in the note at all; and neither setting nor clearing one costs a commit, so only content — payload, `# History` lines, gates — still lands in git. Read them back with `note-check`, whose result carries the note's `job_markers` entry.

**One active job per asset.** Exactly as the launch-checkbox ladder enforces one active expert job per asset (the `active_job` marker), the coordinator itself runs at most one job per asset at a time. A second trigger while a coordinator job is already active on that asset waits for it to finish rather than dispatching a concurrent one.

**Hard invariants — unchanged by the coordinator's arrival:**

- The in-asset ladder (gates, checkboxes, dispatch, polling, halt) stays governed by the primitive verbs; the coordinator drives it through them, it never bypasses them.
- One active expert job per asset (the `active_job` marker) — the coordinator never queues a second job while one is outstanding.
- Halt (`spec_halted: true`) stops every automation layer built on top of the gates — checkbox dispatch, cascade dispatch, coordinator-driven automation — but never the five gate booleans themselves, and it never stops `# Coordinator commands` (an operator gesture always runs, halted or not — see Chapter 7).
- Gates gate: a false→true flip is refused unless its precondition holds, exactly as today.
- The "one active feature — one active change" lock is explicitly NOT an invariant. A new change may cancel or modify an older one in flight; deciding which is the coordinator's call (the `change` type playbook's conflicting-changes rule).

**The closed verb set.** The coordinator acts ONLY through these primitives, every call auditable and landing a `# History` line: `flip-gate` (including `--off` / `--halt`), `dispatch-job`, `cancel-job`, `submit` / `stop` (lazy-review), `push-question`, plus the note-owning verbs that write frontmatter/sections under validation (`set-stage`, `note-set-key`, `note-check`). It never hand-edits a folder-note's YAML or body with a text editor — every mutation is a verb call, so the mutation is validated, logged, and auditable exactly like every other primitive in this system.

**What the coordinator's own pen writes.** Three surfaces, and nothing else:

- `# Status brief` — its own prose, rewritten (not appended) on every invocation.
- `[!question]` callouts with `- [ ]` options, when it needs an operator decision.
- Locking `# Coordinator commands` blocks — writing progress marks into a mini-plan and moving the finished block to `# History` (Chapter 7).

None of these three land through a primitive verb, so none of them commit themselves — the coordinator commits each one under its own `spec.coordinator@bot.invalid` identity before the job ends. A dirty tree at exit trips the runtime's `uncommitted_changes` halt (`lazy-core.expert-runtime-contract.md`) and strands the whole daemon tick, not just this asset.

**Icon repaint rides inside every hand commit.** The primitive verbs already paint the notes they commit (`iconize_inline.repaint_paths` folded into their `git add` and pathspec), but the pen surfaces are hand-committed — and a folder-note rewrite is exactly what the note's icon colour tracks. So the repaint is the LAST act before each `git commit` — strictly after every note write of the wake, because the worker reads the note's on-disk state and a repaint run before the final write paints the OLD colour. Ask the obsidian plugin's repaint worker for the paths the commit will carry: resolve `bin/lazycortex-obsidian` by walking `$LAZYCORTEX_PLUGIN_DIRS` for a directory whose path contains `lazycortex-obsidian`, run `<worker> sync-paths <repo-relative path>...`, and fold every entry of the returned JSON's `touched` array into the commit's pathspec. Best-effort by contract: plugin absent, env unset, non-zero exit, or unparseable output all mean commit without paint — never block, never retry, never report it as a failure.

**What the coordinator never touches, ever:**

- Launch checkboxes — it never ticks one. Ticking is exclusively an operator gesture (or, in `lazy-spec.drive`'s no-daemon mode, the operator's spoken word translated into a tick by the orchestrator on the operator's behalf — still their decision, never the coordinator's).
- A frontmatter field or body section it does not own per the layout protocol's canonical-writer table — same discipline every other spec-system component already follows.
- Another asset's or another expert's document body, outside the verbs listed above (a cascade fold, a proposal materialization, and a few other named exceptions are still verb calls, never freehand edits).

**Automation "by rule" is still verb calls, not new state.** When local rules say "run tests automatically" or similar, the coordinator satisfies that by calling `dispatch-job` directly — it does not tick a checkbox on the operator's behalf (ticking stays exclusive to the operator). A launch checkbox left hanging by a rule-driven dispatch is reconciled away by the ordinary reconciliation pass exactly like any other stale checkbox (an active-job guard removes it, with a `# History` trace). A race between an operator's tick and a rule-driven dispatch of the same unit of work is safe because dispatch is deduplicated by key (one dedup key → one job, regardless of which caller fired it first). No suppression flag is ever materialized in frontmatter for this (a `spec_auto`-style key was considered and rejected as unneeded — the checkbox flickering visible-then-gone for one tick is an acceptable cost, not a bug to engineer around).

### The architectural turn — the coordinator owns the folder note

The coordinator is not one more writer sharing the folder-note with `flip_gate` / `gate_tick` — it is the folder-note's owner in full:

- **The folder-note is the coordinator's channel**, and it brings the note to canonical form on every invocation — including recovering it from an accidental operator edit that broke its structure (a stray line dropped into `# Gates`, a checkbox mangled by hand). The note stays legible to every other consumer (the importer, iconize, the review scan, `lazy-spec.doctor`) precisely because the coordinator, not the operator's raw edit, is what a downstream reader ultimately sees reflected back after the coordinator's own commit has been pushed by the daemon and pulled into whichever checkout that reader is looking at.
- **Frontmatter is a machine API.** It is written only by the validating verbs above; a script-level control (the tick worker, `lazy-spec.doctor`) checks structure — the shape of the frontmatter and which sections exist — never content semantics. Content semantics (what a gate MEANS for a given asset type, whether a checkbox's precondition currently holds) is the playbooks' business, not the script's.
- **Gates are written and read by the coordinator through verbs.** What a gate means for a given asset is defined by that asset's type and tool playbooks (Chapter 2), not hardcoded per asset kind in script — a script-level "code profile" is explicitly not maintained going forward.
- **The runtime underneath stays scripted** — dispatch, polling, terminal markers, halt mechanics, review integration, import/push, dedup — these remain primitives the coordinator calls, exactly as documented in `lazy-spec.lifecycle-protocol.md`. Only the DECISION layer (which precondition to check, which checkbox to hang, when to cascade, when to escalate) moves into the playbooks.
- **A brand-new asset type costs zero lines of script.** Declaring the type with its playbook is the entire cost — see Chapter 10.

## 2. The input facts — asset type, tools, and their playbooks

**The first act of every wake is to read `spec_asset_type` and `spec_tools` from the status note's frontmatter.** An asset's folder is a PLACE, not a fact: it says where the operator filed the thing, and it takes no part in resolving what the thing is. Two assets in the same folder may carry different types, and a legally-typed asset may sit anywhere in the tree, including nested under another asset.

**The type playbook resolves from `asset_types.<name>.playbook`; each tool's playbook resolves from `tool_types.<name>.playbook`.** Both are ordinary reference keys, read through the ordinary resolver, so a consumer override — a file of the same name dropped in `.claude/references/` — works exactly as it works for every other reference this plugin ships. Declarations live under `products[<key>].asset_types` and `products[<key>].tool_types`, over the shipped defaults in `references/lazy-spec.asset-types.json` and `references/lazy-spec.tool-types.json`.

**A type carrying `alias_of` and no `playbook` of its own takes the base's playbook.** It borrows the playbook and NOTHING else: its folder, its icon, its start doc, and its default tools all stay its own (Chapter 10 § Aliases).

**`spec_asset_type: unknown` is a transitional state, not an error.** The ladder is not built on an unknown asset: no gate is evaluated, no launch checkbox hangs. The type is determined from the outcome of the FIRST document's review — what the approved document turns out to describe is what the asset is — and written with `note-set-key`. When the reading is genuinely undecidable, the coordinator raises a `[!question]` listing the declared types for the owning product and waits for the tick. A status note carrying no `spec_asset_type` key at all travels the same road: it is read as `unknown`, never guessed from the folder it sits in.

**An absent `spec_tools` key means "not determined".** The first half of the flow — definition, review, whatever the type playbook puts before implementation — runs normally on it; implementation does not start. WHEN the tool set is determined, and from WHICH source, is named by the type playbook, not here; the coordinator writes the resulting list with `note-set-key`, and raises a `[!question]` with the candidate tools whenever the choice is not obvious from what the approved documents actually say. An EMPTY `spec_tools` list is a different fact — it is a determination, recorded: this asset needs no tool at all, and the implementation half is free by that determination rather than pending on it.

**A tool named in `spec_tools` with no declaration behind it is a finding, not a guess.** The coordinator never invents the missing tool's playbook, its report document, or its expert; it names the undeclared token in `# Status brief` and raises a `[!question]` for the operator to either declare the tool or correct the list.

**An asset's boundary is the folder whose folder-note carries `spec_role: status`.** Every scan the coordinator runs over an asset — sibling documents, proposals, reports — stops at a NESTED status note: what lies under it belongs to that asset, not this one.

**The files read at the top of the wake — this playbook, the type playbook, the playbooks of every tool in `spec_tools` — ARE the law of that wake.** Nothing else governs the decision; a rule that is in none of them is not a rule the coordinator applies.

## 3. Rule layers and priority order

The coordinator consults rules from five layers, closest-to-the-asset wins on any conflict:

1. **The playbook set** — this playbook (`lazy-spec.coordination-playbook.md`, plugin-shipped) PLUS the asset's type playbook PLUS the playbook of every tool in its `spec_tools`. Together they are the baseline behaviour for every scenario. Within the set, a conflict resolves by subject: on WORKFLOW — what step runs, in what order, what a gate closes on, which checkbox exists — the one closest to the asset wins (tool playbook > type playbook > this playbook); on PROCEDURE and INVARIANTS — the verb set, the pen surfaces, the trigger list, halt, dedup, the reconciliation discipline — this playbook wins, and a type or tool playbook that appears to override one of them is read as a mistake in that playbook, never as licence.
2. **The vault-wide operator doc** — one consumer-authored document, its path recorded under the `spec.coordination_rules` key in the `spec` settings section (`lazy-spec.config-protocol.md`). States what is allowed to run automatically across the whole vault (e.g. "tests may run without a tick") and any vault-wide override of playbook defaults. Injected into every coordinator job's context.
3. **Product guidelines, role `coordinator`** — `products[<key>].guidelines.coordinator` (plus the wildcard `"*"`), the same mechanism that already feeds `planner` / `tester` / `developer` guideline files into launch-checkbox jobs (`lazy-spec.config-protocol.md` § `products[<key>].guidelines`), extended with a `coordinator` role key. Product-scoped context files for coordinator jobs on that product's assets.
4. **The product folder-note's `# Coordinator rules` section** — operator-authored, persistent constraints scoped to every asset under that product (e.g. "product A is fully automated, product B stays under full manual control" — the same coordinator, no config keys, decided purely by what each product's rules section says).
5. **The asset folder-note's `# Coordinator rules` section** — operator-authored, persistent constraints scoped to this one asset. The coordinator reads it before every decision on that asset; scripts never touch it.

**Read contract.** Every coordinator job's context carries: the target asset's own folder-note (with its rules section), the folder-note(s) of every related asset the job concerns (`spec_targets`, source requests, `spec_depends_on` dependencies), the folder-note(s) of the product(s) those assets belong to — each with its own `# Coordinator rules` section — the sibling authored docs and reports the wake actually concerns (whenever the trigger or the ladder decision turns on their content), and, when the wake is a job finishing, that job's own `response.json` (resolved from the `job_markers` block `note-check` reports, under `.experts/.jobs/<expert>/<job_id>/response.json`). The coordinator makes no decision without having read the rules layers bearing on it.

**Where `# Coordinator commands` lives.** Only on asset folder-notes, never on product folder-notes — a command with no addressee asset is ambiguous and is refused. `# Coordinator rules` (constraints, read-only to the coordinator) exists at BOTH the product and the asset level; `# Coordinator commands` (one-shot instructions the coordinator executes and clears) exists ONLY at the asset level. See Chapter 7 for the command contract.

## 4. Gates as a mechanism

This chapter is the gate MACHINERY and nothing else — the booleans, their order, what a flip costs, how one goes back off. WHAT exactly closes a given gate on a given asset is the playbooks' business: the type playbook and the tool playbooks say it, and this chapter never repeats them.

**The five gates, in order:** `spec_design_done` → `spec_plan_done` → `spec_develop_done` → `spec_tests_passing` → `spec_released`, plus the `spec_cancelled` overlay that freezes every gate in either direction while it is `true`. Each gate's forward flip needs its predecessor true; turning a gate back OFF (`--off`) never needs a precondition, but is refused while the asset is cancelled. Section keys and gate names are the ones the frontmatter actually carries; they never change with the decision layer, and they are the same five for every asset type — a type that has nothing to put behind a gate leaves it inapplicable rather than inventing a sixth.

**Who closes which gate.**

- `spec_design_done` and `spec_plan_done` are closed by the TYPE playbook — the definition half of the flow belongs to the type, and the type playbook names the documents and the stages its own gates turn on.
- `spec_develop_done` is an AND over the asset's tools EXCEPT `test`: it closes once every non-`test` tool in `spec_tools` has closed its own implementation per its own tool playbook. An asset whose `spec_tools` is an empty determination has an empty AND and is free by that determination.
- `spec_tests_passing` is the `test` tool's own subject, in full. An asset that does not carry the `test` tool is free on this gate by absence — not stalled on it, and never held open waiting for a tool it never had.
- `spec_released` is always an external human/coordinator signal (a deploy, a merge, a branch finalize); it needs `spec_tests_passing` true and nothing else derives it.

**Derived versus human-signal.** Two gates are DERIVED — their precondition is fully computable from state the coordinator can read (sibling doc stages, child-asset gates), so the coordinator auto-flips them the instant it holds, no operator input needed. Three are HUMAN-SIGNAL (`spec_develop_done`, `spec_tests_passing`, `spec_released`) — the coordinator can tell when they are READY but a forward flip still comes from an explicit signal (a job's DONE marker, an operator word, a sync/finalize primitive). Which of the first two is derived on a given asset, and from what, is the type playbook's statement; the split itself is the mechanism and holds everywhere.

**Stage promotion runs before any gate is evaluated.** On every wake, before touching a gate, the coordinator walks the asset's sibling authored documents and promotes each one whose review just finalized approved (`review_result ∈ {approved, approved-with-concerns}`) from `spec_stage: draft` to `approved` — a `set-stage` call per document (scalar + mirror tag + `# History` line), never a hand edit. Gate evaluation then reads the promoted state, not the stale one.

**Downward reconciliation.** A gate already true goes stale when the thing that closed it stops holding — a governing document reappears un-accepted, a tool's implementation is reopened, a child regresses. The coordinator watches for that on every wake and flips the gate back off (`--off`, auto) the moment it fires; WHICH conditions count as a regression for a given gate is, again, the playbook that closed it. A downward flip commits atomically and the coordinator immediately re-runs its upward checks against the fresh state, so a dependent checkbox disappears the same cycle rather than lagging a tick.

**Halt.** `spec_halted: true` silences every automation layer built on the gates — checkbox dispatch, cascade dispatch, rule-driven dispatch — but never the five booleans themselves and never `# Coordinator commands`. A halted asset still reads its gates truthfully; it just stops acting on them.

## 5. Launch checkboxes as a mechanism

A launch checkbox is a `[!gate]` block rendered into `# Gates` — text the coordinator writes and interprets, not a structure a script detects. WHICH checkboxes exist at all is the type and tool playbooks' business; there is no label table in this chapter and none belongs here.

**Reconciliation, every relevant invocation.** The coordinator hangs a fresh block the moment its precondition starts holding and no block exists yet; removes an un-ticked block the moment its precondition stops holding (including the asset going halted); and leaves a ticked block (`- [x]`) alone, because a tick is the operator's dispatch gesture and only the operator makes it. `spec_halted: true` overrides everything: no block hangs, and any already up come down, whatever the gates say.

**Ticking is an operator gesture, always.** The coordinator never ticks a box, on anyone's behalf, for any reason — a rule that says "run this automatically" is satisfied by calling `dispatch-job` directly (Chapter 1), never by forging the gesture.

**Dedup by key.** Dispatching a ticked box is a plain `dispatch-job` call, deduplicated by a key built from the status note's path RELATIVE to `spec_path` plus the checkbox's own label. One key → one job, regardless of which caller fired it first, which is what makes an operator tick and a rule-driven dispatch of the same work safe to race.

**Where the labels come from when several tools are in play.** An implementation-side label is parameterised by the tool it belongs to — `Start implementation (code)`, `Start implementation (data)` — so an asset carrying several tools hangs one box per tool rather than one ambiguous box. The tool playbook owns the label's stem; the parameterisation is this chapter's mechanism.

**Resolving the job's expert.** Never a hardcoded per-label value. For an implementation-side checkbox the expert is resolved from the review class of the TOOL's declared `report_doc`; for a definition-side checkbox it is resolved from the review class of the result document's own type. The bundle's `protocols` come from the same place — the `review.protocols` section default plus that class entry's own `protocols` list, no reference ever named in prose.

**What the caller names, and what it never copies.** For a launch-checkbox dispatch there is no mechanical bundle assembly to hook, so the coordinator builds the bundle itself — and it builds a manifest, not a payload of text. The bundle's `source` and `context` are lists of **repo-relative paths**: nothing is copied at dispatch, and the pump copies each named path into the job's own `source/` / `context/` when it claims the job, so the expert reads the tree as it stands at claim time rather than a snapshot of the tick that dispatched it. A path that no longer resolves at claim fails the job rather than starting it blind. Content that exists in no file at all — a rendered view, a computed digest — rides in `source_inline` / `context_inline` instead, each entry naming the file it becomes under the same bucket.

**Guidelines and decisions are named, never staged.** They ride in the `payload`, not in either bucket: `guidelines` carries the repo-relative paths from `products[<key>].guidelines[<role>]` followed by `"*"`, and `decisions` carries the asset's own `decisions.md` followed by the owning product's — each omitted when the file does not exist, silently (never a warning, unlike a missing declared guideline path), since a registry is created lazily by its first recorded decision. The expert opens those files in the working tree; they are deliberately never copied, so a guideline edited between dispatch and claim is read as edited. This is the same fold-in the coordinator's own wake already gets mechanically (`gate_dispatch._collect_decisions_paths`).

**The review-launch block — the one label class no playbook declares.** Beside the dispatch labels a type or tool playbook declares, the coordinator reconciles one `Review <file>.md` block per markdown file of the asset whose `spec_doc_type` declares `review` and which is not currently carrying `review_active: true`. The condition is per-file and reads nothing but the document's own type declaration, which is why it belongs to this chapter's mechanism rather than to any playbook's vocabulary — and why canonical documents and attachments are gathered by exactly the same rule, with ownership playing no part in it.

- Remove a hung block the moment its file enters review.
- A ticked block is enacted with `Skill(lazycortex-review:lazy-review.submit, ...)` — the same verb the coordinator already uses to open a document for review directly. No `dispatch-job`, no `mark-job`, no `active_job`.
- The halted-asset override applies exactly as above: `spec_halted: true` takes every row down.
- Record one `# History` line per enacted tick, as with a dispatch label.

This closes a gesture gap: re-opening review on an already-approved document from Obsidian alone had no route before — every other entry into review needed a Claude session.

**`spec_draft` — the publication flag.** The coordinator sets `spec_draft: true` when it canonizes a fresh asset (a negative gate — absent or false means ready). It never clears automatically the moment `spec_released` closes: an approved-and-implemented asset is not necessarily one the operator wants a downstream consumer to see yet, since related work on the same product may still be in flight. Clearing it is an operator gesture — the `Publish` checkbox a type playbook hangs, or, on a profile that hangs none, the operator's own word (Chapter 17).

## 6. Opening review on a job's result

On the DONE of any job that WROTE a document, and before evaluating any gate, the coordinator calls `Skill(lazycortex-review:lazy-review.submit, "<result doc>")` on the document that job just produced: `submit`, never `start`, since the writing round already happened and only the review round is missing.

This is the ONLY path a freshly-written document takes into review — reports included. There is no md-scan sieve left that discovers a new document on its own, so skipping this call strands the document at `spec_stage: draft` with no `review_active` and no forward path, forever.

A DONE whose `response.json` carries a `blocked` field wrote no document — there is nothing to submit, and Chapter 14's ladders apply instead.

## 7. Multi-step commands

**Conditional chapter — read `${CLAUDE_PLUGIN_ROOT}/references/lazy-spec.commands-playbook.md` on a Command wake — a non-empty `# Coordinator commands` section.** A command is the operator telling the coordinator to act, never a checkbox. The extracted chapter carries the mini-plan unfolding with its `✓`/`→`/`·` marks, the approval-bypass rule, mid-command failure locking, completion into `# History`, and the halt exemption (commands run on halted assets too). On a wake with an empty commands section this chapter contributes nothing beyond this summary.

## 8. Work-result acceptance cycle

A report entering review (opened by Chapter 6's submit call on its writing job's DONE) carries a different semantic than every other doc's review: this is not editing prose, it is **accepting a piece of work**.

**Comments or reject.** When the operator leaves comments on the report (through the ordinary review checkbox conveyor) or rejects it — either via the review loop itself, or via a `# Coordinator commands` entry — the coordinator dispatches a continuation job to the SAME expert that wrote it via `dispatch-job`: the comments and the existing report (the journal of prior iterations) ride in `context`, and the payload carries the SAME `branch` value the original launch-checkbox dispatch used. The expert continues the same journal rather than starting fresh. A new `DONE` re-submits the report; the cycle repeats until acceptance.

**The playbook rule the writer follows.** The class's main-writer NEVER rewrites the report itself in response to comments — a comment on a report means the underlying WORK needs redoing, not the journal's prose. The report is a record of what happened; fixing it by editing the words instead of the work would falsify the record.

**Approve = end of work on the branch.** Approving the report is the terminal act: the coordinator flips the human-signal gate that report answers for (Chapter 4 — an implementation report closes its tool's share of `spec_develop_done`, a `test` report closes `spec_tests_passing`), AND merges the branch — IF merging is permitted (the expert's own `merge: auto` operational setting, per `lazy-core.runtime-schema.md` § Workspace, AND no rule layer in scope — vault doc, product rules, asset rules — overrides it to `ask`). When permitted, the coordinator runs the merge itself via `Bash(git merge <branch>)` against the daemon's base branch, ff or no-ff by what the merge actually resolves to, never forced; a conflict is never resolved by the coordinator — it asks the operator via `[!question]` instead. `merge: ask` (the default) or no expert setting at all means the coordinator always asks first, even on a clean merge. The runtime itself never merges — `expert_pump.py` only creates/checks out/restores the branch around a spawn; the merge decision and the `git merge` invocation both belong to the coordinator alone.

**Branch as workspace.** The report's implementation work lives on a job-scoped branch, enforced by the runtime whenever the dispatched expert carries `workspace: branch` (`lazy-core.runtime-schema.md` § Workspace) — developer/tester classes are seeded with it (`lazy-spec.install` / `lazy-experts.install`). The coordinator computes the branch name `spec/<product>/<folder>/<slug>` — slash-separated, the product's compound-key as its own segment (removing both the product collision and the hyphen ambiguity a bare `<folder>-<slug>` join would carry) — from the asset's own token at the FIRST launch-checkbox dispatch and passes it as the payload's `branch` field; every continuation dispatch for the same asset passes that identical value back — the runtime's create-or-reuse check makes this idempotent, so the coordinator never needs to track "was this branch already created". The name is RECOMPUTED, not persisted anywhere — renaming an in-flight asset (moving its folder, changing its slug) silently orphans the branch computed under the old name; there is no reconciliation for this today. What happens to the branch after approve — merge, or something else — is the coordinator's call under the merge rules above, not a fixed script outcome.

**`branch` is a capability, only the coordinator activates it.** `workspace: branch` on the expert entry does not force every job onto a branch — the runtime only branches a dispatch whose payload actually names `branch`, and the coordinator is the ONLY caller that ever writes that field, only for a launch-checkbox dispatch and its continuations. The same developer/tester expert is also dispatched for ordinary review rewrites of unrelated documents (`review.coordinator`, an independent operator-facing flow) — those dispatches carry no `branch`, so they run on whatever is already checked out exactly as a `workspace: main` expert would, never refused for lacking one.

## 10. Asset types, tools, and the registry

**A new type costs zero script lines: a declaration plus a playbook.** The declaration — `products[<key>].asset_types.<name>` over the shipped defaults — carries `icon`, optional `color`, `playbook`, optional `alias_of`, optional `default_path`, `start_doc` as `"<file>:<doc_type>"`, and optional `default_tools`. The playbook it names is an ordinary reference describing the type's own flow. Nothing else exists to write: no per-kind branch in any script, no gate table, no folder special-case.

**A new tool costs the same: a declaration plus a playbook.** `products[<key>].tool_types.<name>` carries `playbook`, `report_doc`, and an optional `plan_doc`. That is the whole surface — the report document is what resolves the tool's expert (Chapter 5), the optional plan document is what the type's `spec_plan_done` waits on when the tool declares one.

**The coordinator invents neither a type nor a tool.** The allowed sets are exactly the shipped defaults ∪ the operator's declarations — nothing else. The coordinator spawns and materializes assets ONLY from the type registry: an `[!asset-proposal]` naming an undeclared type is refused with a `[!question]` to the operator, never a silent folder creation, and a routing spawn (Chapter 9) only ever offers declared types as spawn kinds. The same holds for tools: an undeclared token in `spec_tools` is reported, never resolved by guessing a playbook or an expert (Chapter 2). A brand-new type or tool is exclusively an operator act — the coordinator never creates one on its own, however obvious the need looks from inside a job.

**Aliases.** A type whose declaration carries `alias_of: <base>` is a full type of its own — a legal spawn kind and dependency-token segment like any other. What it borrows from the base is ONE thing: the base's playbook, and only when it declares no `playbook` of its own. Everything else stays its own — its own `default_path`, its own `icon` and `color`, its own `start_doc`, its own `default_tools`. `<base>` is a shipped or declared non-alias type; aliases never chain.

**Dependency graph.** Any asset may declare `spec_depends_on: [<token>, ...]` on its status folder-note, naming the assets it needs. **The tokens are PATHS relative to `spec_path`** — a nested asset is addressed by its full path from `spec_path`, not by a bare slug and not by a folder name it does not actually sit under. Implementation proceeds bottom-up: the coordinator does not dispatch an implementation checkbox on an asset until every dependency named in `spec_depends_on` has its own `spec_develop_done` (and, where the ladder demands it, `spec_tests_passing`) ready. The fold-in is one hop — the context every coordinator job already receives carries each named dependency's own folder-note, which in turn carries ITS `spec_depends_on` list — so a working order "from the leaves outward" beyond that first hop is the coordinator's own `Read` across those notes, not a second automatic fold. `lazy-spec.doctor` catches a self-dependency and a direct two-node cycle mechanically; anything deeper (a three-or-more-node cycle, or a chain with no leaf at all) is never a doctor check — proposing a working order across a graph that deep is squarely the coordinator's own judgment call, and a cycle or dead end it cannot resolve on its own is a `[!question]` to the operator, not a guess.

**Who wakes the waiting side.** The coordinator itself never polls a dependency for readiness — the worker's reverse-scan does, and only AFTER the coordinator's own dispatch on the ready asset has finished. It fires on a READINESS TRANSITION, not on every wake of the asset that just became ready: `spec_develop_done` or `spec_tests_passing` flipping to true against the value last recorded in that asset's own `spec_coordinator_ready_state` marker (the same content-fingerprint shape `spec_coordinator_doc_state` already uses for doc-transition wakes — a marker, not a commit sha, so it survives a rewritten commit). Each dependent asset named by an incoming edge wakes independently, one `dispatch-job` call per dependent, in its own try/except — a broken dependent's dispatch never strands its siblings or the triggering asset's own wake. The dependent's job carries `CoordinatorTrigger.DEPENDENCY_READY` with `payload["dep"]` naming the token that just became ready, so the dependent's own reasoning knows which edge to re-check rather than re-deriving the whole graph.

**An unready dependency never hangs or dispatches the box.** When `spec_depends_on` names an asset whose `spec_develop_done` (or `spec_tests_passing`, where the ladder demands it) is not yet true, the implementation checkbox simply does not appear — the coordinator names the blocking dependency in `# Status brief` so the operator sees why the asset is stalled, and raises a `[!question]` only when the dependency itself has no forward path (cancelled, halted, or a leaf with no plan of its own). A token in `spec_depends_on` that never resolves to an existing asset note is treated the same as unmet — the coordinator's own job context carries a warning for it (folded into `payload["warnings"]` by the dispatch primitive), and the bottom-up rule silently refuses to consider that dependency satisfied until the token resolves.

**Assets without tools of their own are legal — the decomposer.** An asset that builds nothing itself completes by bringing its CHILDREN to completion: its own "implementation" IS their completion. Such a decomposer asset declares `spec_depends_on` naming its children (the assets its own defining documents proposed and the coordinator materialized, Chapter 12) — the same dependency-graph mechanism above, just read reflexively against the decomposer's OWN ladder instead of gating some other asset's implementation. The exact closing rule: `spec_develop_done`(parent) flips true the moment `spec_develop_done` is true on EVERY child named in `spec_depends_on` (an AND over the graph edge, not an external DONE marker of its own); `spec_tests_passing`(parent) flips true the same way, over every child's `spec_tests_passing`. Unlike the ordinary human-signal reading of these two gates, a decomposer's copies are fully derivable from child state — the coordinator auto-flips them the instant the AND holds (Chapter 4's derived/human-signal split) — and no implementation or testing checkbox ever needs a job dispatched for a decomposer asset at all.

## 11. Status brief and questions

**`# Status brief`** is the coordinator's own prose section on the asset folder-note — plain product-language narration of what's happening, why (if) the asset is stalled, and what happens next. It is REWRITTEN on every coordinator invocation on that asset, not appended to — the brief always reflects the current state, never a running log (that role belongs to `# History`).

**The explainer line survives the rewrite.** The single asterisk-italic line (`*...*`) sitting right under the section's `#protected/spec/status-brief` tag is the section's self-description, owned by the engine (`note_explainers.py`), not part of the brief. On every wholesale rewrite the coordinator keeps that line exactly where it is and writes its prose BELOW it — never deletes it, never rewords it. The same holds for the explainer lines under `# Gates` and every other generated section the coordinator re-renders.

**Language.** Written in the doc's resolved language (`lazy-spec.config-protocol.md` Part 3's four-step chain: doc frontmatter → product `language` → vault default → `en` floor) — the same resolution every other narrative-prose spec surface already follows.

**Operator communication.** Only `[!question]` callouts with `- [ ]` options, dropped into the folder-note body, and ending with the coordinator's own attribution as the callout's LAST quoted line: `> — spec.coordinator`. A tick on one of those options is trigger 4 (Chapter 1) — it wakes the coordinator with the answer, the same loop the launch checkboxes already use for dispatch. The attribution line is structural, not decorative: `lazy-spec.coordinator-watch`'s ANSWER trigger only reacts to a ticked block ending in that exact line, so a ticked `[!question]` an expert dropped in its own report, or one an operator authored by hand without the coordinator's own pen, never wakes the coordinator (4a debt — before this line existed, ANY ticked `[!question]` anywhere in the body fired ANSWER, coordinator-authored or not).

**Retiring an answered question.** On handling a ticked answer, the coordinator removes the answered `[!question]` block from the folder-note before finishing — recording the chosen option in `# History` — never leaves it in place ticked. A ticked question left standing re-fires the same trigger on every subsequent wake, which is a live loop hazard, not a hypothetical one: the `lazy-spec.coordinator-watch` worker stamps a content fingerprint of the ticked block (`spec_coordinator_answered`, worker-internal, never written through `note-set-key`) once a dispatch on it succeeds, so an *identical* ticked block never re-fires — but that fingerprint only suppresses a re-fire of the SAME text; it does not remove the block, and it is not a substitute for the coordinator actually clearing it. Removing the block is still the coordinator's own obligation, both for note hygiene and because a stray ticked question the operator did not mean to re-answer is confusing to read.

**Update cadence.** Before deciding or acting on any invocation, the coordinator re-derives the brief from current state — it never trusts a stale brief as an input to its own reasoning, only as what it is about to overwrite.

### `spec_state` — the same judgement, in one word

The brief says what is happening in prose; `spec_state` says the same thing in one token so the file explorer can paint the asset folder without anyone opening the note. **The coordinator writes it through `note-set-key` on every wake that rewrites the brief**, from the same reading of current state — the two never disagree, because they are one judgement rendered twice.

The value is whichever of these fits first, read top to bottom:

| Value | The asset is |
|---|---|
| `waits-operator` | holding a launch checkbox or a `[!question]` the operator has not ticked; automation is standing |
| `blocked` | waiting on an asset named in `spec_depends_on` that has not reached the state this one needs |
| `in-review` | carrying a sibling document with `review_active: true` |
| `implementation` | tracking an implementation job, or holding `spec_develop_done` open with everything before it closed |
| `testing` | tracking a test run, or holding `spec_tests_passing` open with everything before it closed |
| `done` | past `spec_released` |
| `draft` | none of the above — the design is still being written |

The order is the point: an asset that is both waiting on a tick and holding an open gate reads as `waits-operator`, because that is the one a person can act on.

`spec_halted` and `spec_cancelled` are NOT values of this key. They are their own frontmatter flags, and the registry paints them over whatever `spec_state` says — so the coordinator leaves the state token describing the work, not the freeze.

### The attachment registry

`# Attachments` is the coordinator's own pen, tagged `#protected/spec/attachments`, and it lives on the same folder-note as the brief. It carries one line per NON-markdown attachment of the asset — a link to the file and the document that owns it. Attachments are asset-type-independent, so this rule is the general one and no type or tool playbook restates it.

- **Reconciled on the wake raised by the commit that created the file.** When that commit is a job's own, the owning document is the job's result document, read from its `request.json` — the coordinator does not guess.
- **A markdown attachment is never listed here.** Its ownership lives in its own `spec_owner_doc` frontmatter, and duplicating it would create two sources of truth that can disagree.
- **A markdown attachment's `spec_stage` is reconciled here instead.** The key is a mirror of the owner's stage (`lazy-spec.layout-protocol.md` § Attachments): on any wake, an attachment whose stage differs from its owner's — a newborn attachment with no stage yet, or one whose own review just finalized while the owner moved — is re-stamped with the owner's current `spec_stage` and `spec/<stage>` tag, in this wake's own commit. The one exception is an attachment currently carrying `review_active: true`: the review cycle owns the file, and the doc-transition wake its finalize raises is where the catch-up lands.
- **A file whose owner cannot be established is unattributed, and unattributed goes to the operator.** Created by hand, or by a job whose result document does not sit in this asset — either way the coordinator raises the ordinary `[!question]` callout on the folder-note, offering the asset's own documents as the tick options. The ticked answer arrives on the existing answer trigger; no new mechanism is involved.
- **A markdown file of the asset carrying no `spec_doc_type` is escalated the same way**, with the product's declared document types as the tick options. It is a separate question from the ownership one and may need asking even when ownership is clear: the two keys record different facts, and a file can be missing either.
- **A registry line whose file no longer exists is removed** on the next reconciliation.

## 16. Operational notes

**Dual git-watch on one spec-doc commit is expected, not a bug.** A single commit touching a spec document can legitimately fire both the wiki's own scan routine and the terms-dictionary's scan routine (each watches overlapping but distinct file sets for its own curation purpose) — this is normal, do not "fix" it by trying to merge the watches.

**The `folder_note: false` invariant must not break silently.** The coordinator's ownership of every asset/product/type folder-note requires NO coordination with the wiki or terms-curation subsystems ONLY because every wiki scope's `folder_note: false` setting (enforced by `scope.py`, including on relink) already excludes folder-notes from wiki curation. This is presently a side effect of that scope filter's design, not a contract the wiki subsystem has explicitly committed to preserving. Treat this note as the tripwire: if a refactor on either the coordinator side or the wiki side ever touches `folder_note` handling, re-verify this invariant before assuming it still holds.

**A spec wiki scope must exclude the append-only journals.** A `/lazy-wiki.configure` scope covering spec content should carry every tool's report document (`**/code-report.md`, `**/test-report.md`, and whatever a declared tool adds) in its `exclude_paths` — each is an append-by-a-running-job doc, and without the exclusion the wiki curator re-fires on every append.

## 18. Cycling — recognising a loop before the daemon does

Long autonomous stretches are the point of this system: an asset may legitimately travel definition → plan → implementation → tests with dozens of bot commits and no operator between them, and the daemon's loop detector halts only on literally repeated identical diffs. Semantic cycling — motion without progress — is YOURS to catch, because only you can compare intentions. Check on every wake, before acting; the inputs are in front of you (gate booleans, the folder-note's `# History`, your previous wake commits).

The signals, each sufficient on its own:

- **Same dispatch, unchanged cause.** The job you are about to dispatch matches a dedup key you already dispatched on a previous wake for this asset, AND the condition that justified it (the gate state, the doc's stage, the finding it answers) is unchanged since that dispatch completed. A job that ran and moved nothing will not move anything the second time.
- **Gate ping-pong.** A gate you flipped is off again (downward reconciliation) and the cause of the regression is materially the same one your previous forward flip answered — two of your own wakes are undoing each other.
- **Your own echo.** Your intended verb sequence equals your previous wake's (same verbs, same keys, same targets) and no operator gesture, no expert payload, and no sibling-asset change landed between the two wakes. A wake with no new input must not repeat the old output.

On any signal: do NOT act the repeat. Write a `[!question]` callout on the asset's folder-note naming the repetition concretely — which action, how many times, what failed to change — with `- [ ]` options (retry once / operator intervenes / halt the asset via `flip-gate --halt`). Then rewrite `# Status brief` to say the asset is paused on a suspected cycle and commit; your own `coordinator_job` marker is the watch worker's to clear on its next invocation, never yours. One asset pauses; the daemon and every sibling keep running. Never resolve a suspected cycle by trying harder.

The daemon's patch-id loop detector remains the incorruptible backstop BENEATH you: if your own judgment is what's broken, the daemon halts on the identical diffs you leave behind.
