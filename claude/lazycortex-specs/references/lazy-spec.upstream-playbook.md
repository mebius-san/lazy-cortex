# Upstream cross-asset scenarios — conditional chapter of the coordination playbook

Extracted chapter 13 of `lazy-spec.coordination-playbook.md`, loaded on demand: read this file when the asset in scope is an upstream unit, or when a request under routing originates from `lazy-spec.upstream-tick`. Every "Chapter N" cross-reference below names a chapter of that common playbook.

`lazy-spec.upstream-tick` is the "hard" layer — the within-unit ladder of statuses, phases, and the request it opens — and carries NO inter-asset judgment of its own. Every scenario below reaches from a unit across to the asset(s) its requests produced (or failed to produce); it lives here, as prose the coordinator reasons from during ordinary routing, never as routine code. All four scenarios reuse Chapter 9's own mechanics (spawn/attach/`reference`, the `[!question]` gate, the research pass) — nothing here introduces a new primitive.

**Drifted unit with descendant assets already spawned.** A unit reaches `drifted` (its source changed after `processed`) while its own `# History` already names asset(s) earlier accepted requests produced. Once the operator's "Process update" tick opens a fresh request and it reaches routing, the coordinator's FIRST move — before any generic candidate search — is to walk the unit's `# History` for every asset it previously produced and run the duplicate-behavior / research pass (Chapter 9) against those specific assets first: a drifted delta most likely belongs on the asset the unit already produced, not somewhere new. The ladder: **(a)** the delta reads as a genuine addition to an existing produced asset's own scope → propose a `change`-spawn naming it via `targets=` (the `change` type playbook's cascade is exactly this shape); **(b)** the delta reads as a materially new capability the prior asset never covered → propose a fresh spawn, with the `:: <description>` stating explicitly why this is NOT folded into the prior asset (so the operator can tell "genuinely new" from "the coordinator missed the connection"); **(c)** the delta is non-functional (a drift that touched only skipped files, a rename, a comment) → `reference` back onto the produced asset, description naming what changed and why it needs no new work. Whenever (a) and (b) are not clearly one or the other, the coordinator raises the call rather than guessing:

> [!question] #review/question
> Unit `<unit-path>` drifted; it previously produced [[<asset-path>]]. Does this drift belong on that asset (change-spawn, `targets=[[<asset-path>]]`) or is it a new capability (fresh spawn)?
> - [ ] Fold into [[<asset-path>]] as a change
> - [ ] Spawn a new asset instead
> — spec.coordinator

**Orphaned unit with descendant assets already implemented.** The unit's directory vanished from the source, yet its `# History` shows real assets it produced, possibly already `spec_released`. Upstream's own doc is explicit that an `orphaned` unit produces nothing and leaves the call to the operator — the coordinator makes NO automatic move against a produced asset on an orphan alone: no cancel, no halt, no gate flip. A design source disappearing upstream says nothing about whether the capability already shipped should be removed; those are independent decisions with independent costs, and conflating them would delete working code because a designer's folder got renamed. The coordinator's job on an orphaned unit with descendants is VISIBILITY ONLY: name every produced asset from `# History` plainly in `# Status brief` on the unit's own next wake, and raise a `[!question]` proposing removal of a specific named asset ONLY when the operator's own words, or an explicit rule layer, ask for that judgment — never unprompted. Absent that ask, an orphaned unit with shipped descendants stays exactly as it is: the source went away, the product built from it did not.

**Disputed reference — the operator disagrees after the fact.** A `reference` decision already landed (request `accepted`, `spec_targets` written per Chapter 9, unit `processed`) and the operator later concludes the referenced asset does NOT actually cover what the request described — Chapter 9's loud-formulation requirement lowers how often this happens, but a later reviewer catching a wrong call is the ordinary safety net, not a mechanism failure. Recovery never retroactively rewrites the closed request: `request_status: accepted` and its `spec_targets` link stay exactly as decided — a historical record of what WAS decided, not something silently corrected in place. The operator's dispute is instead routed as a FRESH request. Trigger: a `# Coordinator commands` entry on the unit's note naming the dispute ("the reference to [[<asset>]] was wrong — treat this state as unimplemented"). The coordinator's response is a manual re-entry outside the ordinary tick's own checkbox ladder — the unit is `processed`, not `new`/`drifted`, so no checkbox is hanging for it — calling the same primitive `lazy-spec.upstream-tick`'s Phase C uses to open a body-only request from the unit's current `source/`/`processed/` state (trivially empty on the mirror side, since nothing changed there; the request body instead carries the dispute's own reason verbatim). Once that fresh request reaches routing, the coordinator proposes the corrected outcome (a real spawn or attach) WITHOUT re-proposing the disputed `reference` — its own attribution stands independently of the original. Both the dispute's own materialization and the corrected routing decision go through the SAME operator `[!question]` confirmation gate as any other routing call (Chapter 9) — a disputed reference is never resolved by the coordinator unilaterally.

**Retry after a failed or stopped routing.** Phase A already returns a unit whose request's routing technically failed (no target named — `apply_request.py`'s `REJECT_REASON_DEFAULT`) or whose review the operator stopped without a verdict, releasing it to `drifted`/`new` with a `# History` line naming the failed attempt (`_release_unit`). This chapter names what happens NEXT — the routine's own job ends at "released"; it never retries on its own. A released unit sits exactly like any other `new`/`drifted` unit: the operator re-ticks "Take into work" / "Process update" when ready, producing an ordinary fresh Phase C request (the same diff-from-`processed/` shape any request on this unit gets — the failed attempt never wrote to `processed/`, so there is no partial state to resume from). The one thing the coordinator owes on the RETRY's own routing pass: read `# History` for the prior failure line before proposing anything, and if the SAME routing shape (identical spawn kind/slug, identical attach target) is about to be proposed again with nothing new to justify it, that is Chapter 18's own cycling signal ("Same dispatch, unchanged cause") — stop, and raise a `[!question]` naming the repeated failure rather than re-proposing the identical routing a second time. A retry proposing something DIFFERENT from the failed attempt (a different target, a `reference` instead of a spawn, a narrower scope) is not a repeat and proceeds normally.
